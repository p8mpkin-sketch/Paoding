# 异议报告 006：执行层出站闸门与访问摘要

日期：2026-11-18。来源：质量提升第一阶段的 P0-4（出站白名单做到端口级）。对应实现见 `executor/SPEC.md` 的"出站闸门"。

每项给出：规格怎么写、实现时碰到的不清楚之处、这次采取的做法、请裁决的问题。在裁决之前，实现按"采取的做法"运行。

## 1. 没写端口的 `net` 规则

- **规格**：§3.1.1 的 `scope.pattern` 是字符串，内核不解释；§3.6.2 的 `egress_allow: string[]`；HMI 设计 §3 的例子写的是 `"<主机>:<端口>"`。`compile.py` 原先的注释写"pattern 是 host 或 host:port"。
- **不清楚之处**：只写主机名的规则是什么意思。读成"整台主机全部端口"，就又回到了审计指出的问题（同一容器的端口要么都通要么都不通）；而且闸门是逐端口监听的 TCP 转发，没有"全部端口"这一档。
- **采取的做法**：`net` 规则的 `pattern` 必须是 `host:port`（端口 1–65535）。没写端口的规则在授权编译时报 `ScopeError`，会话与判官容器起不来（判官一侧记 `inconclusive(env_error)`），不默认放行。
- **请裁决**：是否把 `host:port` 写进规格，并让图服务在 `open_problem` 与 `approve --scope-amend` 时就拒绝没写端口的 `net` 规则（现在要到起容器时才报错）。这需要内核经资源种类登记表校验 `pattern`，属于图服务的改动，本次没有做。

## 2. 闸门是 TCP 转发，目标端口没开时 `connect()` 仍然成功

- **规格**：§3.6.2 只说"出站白名单"，没有规定实现手段；任务书指定"出站代理容器（DNS + TCP 转发）作为唯一出口"。
- **不清楚之处**：TCP 转发在接受连接之后才去拨上游。目标端口没在监听时，执行容器看到的是"连接成功，随后被重置"，而不是"连接被拒"。只看 `connect` 返回值的端口探测会得出"端口开着"的错误观察。
- **采取的做法**：上游接不通时闸门立刻以 RST 关闭，并在逐连接记录里记 `ok=false`。没有去掉这个差异：要做到完全透明需要在闸门里做内核级转发（NAT 加包过滤），闸门就得带 `NET_ADMIN` 能力和包过滤工具，信任面更大，也更依赖宿主内核配置。
- **请裁决**：是否接受这个差异（并在任务包的工具说明里提醒"判断端口是否开放要读到数据为准"），还是要求改成内核级转发。提醒文字在 Adapter 的任务包里，本次没有改。

## 3. `actions` 里除 `connect` 之外的动作

- **规格**：`scope.actions: string[]`，内核不解释。现有题目与测试里出现过 `connect`、`*`、`read`、`write`。
- **不清楚之处**：`net` 资源上 `read`、`write` 这类动作指什么、由谁执行。TCP 转发分不出一条连接是"读"还是"写"。
- **采取的做法**：按任务书"`connect` 放行、其余拒绝"：闸门只为 `actions` 含 `connect` 或 `*` 的规则开端口。只写了别的动作的 `net` 规则不开任何通路（规则仍然交给闸门并记在它的启动记录里）。`workspace` 资源的 `actions` 仍然没有执行手段（工作区是整目录读写挂载），不在本项范围内。
- **请裁决**：`net` 资源的动作词表是否就定为 `connect` 一个；`*` 是否保留。
