# M0 异议报告 001：仓库骨架与 EDR-001 D-4 的三处缝隙

> 状态：**已裁决，三项全部采纳**（2026-11-17，PR #10 评审方评审）｜提出方：M0 实施线程｜性质：实现中发现的规格缝隙，代码里未私改，按下列"暂行做法"先走，裁决后照改。

## 1. 司南没有目录

D-4 的九个目录里没有司南（§4.1，外壳）。D11 要做"司南最小循环"。司南不属于 Adapter（会话边界）也不属于 graph（基质），放进任何一个都会让外壳状态进入下层，违反 §2.1 的"信任根不读外壳的任何状态"。

- **提议**：新增顶层目录 `sinan/`，依赖 `graph.contract`（读 `/work`、申请租约），不被任何组件依赖。
- **暂行做法**：D11 之前不建目录，不影响 D1–D10。

## 2. reference-model/ 的位置

D-4 把 `reference-model/` 列在仓库顶层"已有"，实际在 `docs/design/reference-model/`，规格与 README 的链接都指向那里。搬家会和 PR #8 冲突，也会断掉规格里的链接。

- **暂行做法**：原地不动。`graph/` 里的等级函数与消费门是 `kernel.py` 的逐字节副本，CI 比对两者一致，保证"搬运不重写"且不会悄悄分叉。
- **备选**：#8 合并后整体移到顶层并改链接。

## 3. `lean_check` 是内建判官，名字里带领域词

> 勘误（2026-11-17）：初稿写成“§3.3.3 把它列为内建判官”，引错了出处。规格 §3.3.3 第 836 行本来就把它写作配置（全文见 6.4）；冲突只在 EDR-001 D-4 的目录注释里。

EDR-001 D-4 的目录注释把 `lean_check` 列为内建判官（`judgebox/ … 内建判官（replay/exact_match/seal_check/lean_check）`），与"判官 = 配置目录、内核零领域词"（红线 3）在字面上冲突；按本线程的 CI 领域词扫描，它进 `judgebox/` 源码就会失败。

- **提议**：M3 时把它做成配置目录里的一条判官（`runner.type = container`，镜像 `lean-pinned`），内建判官只留 `replay`、`exact_match`、`seal_check` 这类不含领域词的。
- **暂行做法**：M0 不涉及，只记录。

## 裁决（2026-11-17）

1. **`sinan/` 目录：采纳。** 已新增，SPEC.md 同标准；排序循环是纯代码，规则表是感知官 [T-1]。依赖方向表加 `sinan → graph, adapter`。
2. **reference-model 暂留原地：采纳。** 逐字节副本加 CI 比对已解决漂移；成为维护负担时再议。
3. **`lean_check`：采纳，立即生效。** 内建判官只有 `replay`、`exact_match`、`seal_check`；`lean_check` 在 M3 以 `judges.d/` 配置条目存在。judgebox/SPEC.md 已改。
