# 一页结论
## 0. 一页结论

**上游怎样在上下文快满时压缩。** 历史是一条只追加的事件日志。压缩不改旧事件，只追加一条 `Condensation` 事件，记下四样：忘掉哪些事件的 id、摘要正文、摘要插在下标几、是哪一次模型回复生成的。每次请求模型之前，`View` 把日志重放一遍，得到"现在该发给模型的那些消息"。触发有三类：token 超限、事件条数超限、显式请求（模型端报"上下文超限"或"历史结构坏"也归入显式请求）。压多少有规矩：以回到上限的一半为目标，最前面几条和系统提示永不压，只在不会拆散"工具调用与结果"的位置下刀，压不掉一成就索性不压；非压不可又压不出来时，把整段历史重置成一份摘要，还失败就把每条事件截短了再试。摘要由一次独立的模型调用生成，提示词固定分节。折叠记录本身带出处，但摘要正文不带锚；在我读到的范围内，上游也没有给模型提供取回被忘事件的工具。

**上游怎样换会话接力。** 分三层。第一层，同一个会话重启后原样接上：状态快照加文件型事件日志，打开即恢复，冷加载时全量重建视图，在途的工具调用补一条"被中断、没完成"的合成错误。第二层，外部 CLI 类智能体（他们叫 ACP）：把它的会话 id 和工作目录记进账，重启后凭这两样恢复，恢复失败就明确报错，不悄悄新开。第三层，跨会话，靠文件和带署名的消息：工作区里的 `AGENTS.md` 与两级 `MEMORY.md` 索引在开场加入；Project 的共享记忆用"带修订号的整文件替换"；派工必须写自包含的简报；每个会话间消息的首行写明"不是用户发的、不代表用户批准任何事"；协调者只收成员的最后一条消息，要细节再按条数去读；重启之后按两边的日志判断哪条更新没送到，补投。

**我们现在的位置。** 会话内的上下文在 CLI 手里，我们这一层不压缩。接力是把上一个求解会话的工作区拷过来，模型读它留下的 NOTES.md，每轮至多 5 个求解会话。"上下文快满"目前没有任何信号，软线只看预算和墙钟。带锚压缩已经在我们的设计里（异火榜第 2 项、验收用例乙），而且它要的底座我们都有：活动链分段入账、exec 留档能用 `show` 按区间取回、端点代理逐请求记了 token。上游这份快照与异火榜那一项对得上，我们现在手里作为"异火"的只有合成夹具 beta。

**值得集成，共九条（详见表 4-1）。** 改动小、不依赖新配置、补的是今天明确空洞的四条可以先做：接力简报由账确定性生成（戊）、被打断的调用与收尾轮如实交代（己）、宿主的话与人的话分开标（庚）、摘要骨架与带锚（丙）。折叠记录入账（乙）、按锚点取回活动（丁）、上下文用量线（甲）适合随 `h4.anchored-fold` 的炼档一起做。引擎的"到七成就交棒"（辛）是引擎线自己的欠账。折叠调用单独计量（壬）是条件性的。九条的落点按 `KERNEL_PATHS` 的路径前缀逐条核对过，都不相交。

**不值得，共七条（详见表 5-1）。** 多数是因为我们不持有会话历史（CLI 持有），上游那套"投影日志"的做法没有对象；其余是我们的内核规则已经更严，或对应能力我们已经有了。

**最需要知道的三处拿不准。** 一是我们认不认得出 CLI 自己的压缩事件，这决定"记录折叠"能不能覆盖 CLI 原地压缩这条路。二是收尾轮的 `--resume` 在上下文溢出之后会不会再次溢出，我没有真 CLI 可试。三是引擎的 `checkpoint_at_context` 与"单元摘要逐句带锚"在设计里有、在快照代码里没找到，可能是没落地，也可能是我漏看。全部见 §6。
