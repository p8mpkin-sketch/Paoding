# 09 吞噬引擎：执行识火、萃意、入位的智能体

> 焚决设计 v0.2 的第九篇（待裁决）。上位：[README](./README.md)；算法见 [08](./08-algorithms.md)，数据形状见 [10](./10-schemas.md)，验收见 [11](./11-acceptance.md)，与 `lianhua.py` 和实现线的交接见 [12](./12-handoff.md)。
>
> **分界**：引擎交出的只有设计文档与结构化数据（候选清单、火意、入位方案、交接包、异火榜的更新提议）。它不写代码、不推 PR、不改功法与火位注册表、不导入资料库。验体、融火、散火照旧由 `lianhua.py` 的确定性代码跑，不加模型。
>
> 本篇不涉及在途任务钉住功法与进化读数页（FJ6 与 04 §7），那两件由另一条设计线负责；这里只在需要时引用。

## 0. 一页结论

1. **引擎是一组火，不是体质组件。** 一团会话形态火 `h1.tunshi`（绑定已有的 solve 席位）加一团工具面火 `h3.tunshi-tools`，跑在开放道上。体质改动 0 行：它用的每一条经脉、每一种事件今天都已存在（§1）。
2. **跑在单独的分析实例里**，而不是主实例。原因是内核按席位记形态（`lease.form` 由 `Config.forms` 按席位取），同一个 solve 席位在一个实例里只能有一种形态；单独实例用自己的功法文件，形态记录如实，外部代码也与用户任务隔离（EN1）。
3. **工作流七步三闸**：立项 → 快照 → 勘察聚焦 → 识火 →【cz 挑】→ 萃意 →【cz 确认或修改】→ 入位与火序 →【cz 裁决】→ 交接。每一闸都是一次交付加一次追问：引擎用 `deliver` 交出这一步的产物，cz 用追问（`follow_up`）带一段固定格式的决定块回答，决定进事件账（§2）。
4. **试算模式**一口气走到入位，中间不停、不分配炼档号、预算约正式的一半，产出“如果吞会怎样”的报告；结果进异火榜，状态“试算过”；转正式时复用观察，萃意与入位重做并过闸（§3）。
5. **引擎自己的工程**：运行状态文件 `run.json` 就是检查点，按单元（火位 × 轮次、候选）推进；上下文到七成就收尾这一单元、交棒给接力会话；三级预算（整题硬顶 T3、每步软顶、每单元上限）；耗尽时带检查点部分交付，追问加预算即续；每一步都可重试、可退回上一闸（§4–§6）。
6. **输出过确定性校验才交给人**：十二条（结构、引用真实、公式复算、禁词、许可证、清单、体质、预登记……），交付前一道、导入炼档时一道。校验器是量具，引擎改不到它（§7）。
7. **异火榜**是仓库里的一份 JSON，经 `lianhua.py bang` 写；cz 说“找点什么吞”，引擎先查榜，有存货直接进闸点 1；失败的分析也留下，并防止同一理由被反复提起（§8）。
8. **并发**：不同外部系统各开一题并行；同一系统的多个候选设计一次做完，进实现线按火序串行，前一团定阶后后一团做确定性的“入位复核”；火位锁防止两条线同时改一个火位（§9）。
9. **引擎可以被替换**：它是火，有清单、有入库四问、有读数；新版走全流程，上一版进常设留出（ε = 10%）；校验器与验收夹具归药鼎，引擎的炼档不得改它们（§10）。
10. **一次吞噬的估算**（中型库、选中 3 个候选）：约 300 万输入 token、19 万输出 token，其中重档约 261 万 / 15 万；机器时间约 1 小时，另加 cz 三次闸点；试算约正式的一半、半小时（§5.3）。全部〔占位〕。

## 1. 定位

### 1.1 引擎是哪几团火

| 火 | 火位 | 绑定 | 是什么 |
| --- | --- | --- | --- |
| `h1.tunshi@1` | H1 会话策略 | solve 席位 | 引擎的会话形态：工具集合、提示词资产、三闸的结束规则、接力与检查点规则、丹方 |
| `h3.tunshi-tools@1` | H3 工具集 | — | 引擎专用的固定模板工具：`intake`、`probe`、`read_excerpt`、`probe_service`、`obs`、`profile`、`check`（§2.3） |

两团火组成一个火组（[08 §5.2](./08-algorithms.md#52-十二步)）。它们之外，引擎用到的表（火位签名、能力剖面、决策原子、机制原语、冲突探针、拒收表、专名通用表）是**量具侧表**，放在 `paoding_fenjue` 里，不是引擎的资产；引擎的升级改不到它们（§10）。

清单草稿（实现线定稿）：

```json
{

 "ports": ["M1:deliver", "M1:request_scope", "M2", "M3", "M4", "M7"],
 "params": { "forms": { "solve": {
   "tools": ["intake", "probe", "read_excerpt", "probe_service", "obs", "profile", "check",
             "show", "kb_search", "kb_read", "request_access", "deliver"],
   "prompt": { "files": ["tunshi.md"] },

   "gates": ["identify", "distill", "place"],
   "stage_share": { "identify": 0.45, "distill": 0.35, "place": 0.20 },
   "pills": { "reader": "light", "main": "heavy", "distill_extra": { "tier": "heavy", "n": 2 },
              "blind": "mid", "placer": "mid" },

 } } },
 "assets": [{ "name": "adapter/prompts/tunshi.md", "sha256": "（实现时填）" }],

   "enable_when": "分析实例的开放道",
   "control_arm": "h1.solo@2（同一份立项原话，通用独行会话，没有引擎工具面）",
   "retire_signal": "通用独行会话在验收夹具上的召回、萃意检验通过率与引擎持平（占位）" },
```

### 1.2 为什么跑在开放道上

把引擎做成开放道上的一种会话形态，体质五项自动承接它，不需要另写一套信任机制：

| 体质 | 怎么承接引擎 |
| --- | --- |
| T1 判 | 引擎的结论是开放道交付，判定来源恒为 `self`，到不了 `solved`/`accepted`；吞不吞由 cz 在闸点与 `lianhua.py jue` 决定 |
| T2 闸 | 开题零出站；抓快照、探测服务都要经扩权卡由 cz 批；钥匙环里的金丝雀密钥照旧不得出现在任何产物里；外部代码只在执行容器里 |
| T3 顶 | 整题预算是硬顶，端点代理计量与拒绝；引擎工具面里的丹调用也经端点代理、用这一题的任务令牌，计入同一本账 |
| T4 账 | 每一闸的交付与 cz 的决定都是事件，逐字节可回放；没有新事件种类；主实例的事件账完全不碰 |
| T5 证 | 引擎写的东西都是 authored 类；它交付里的主张只能引用 exec（勘察输出、快照抓取、探测响应）与 input（cz 上传的快照与原话），内核照旧校验引用 |

### 1.3 为什么要单独的分析实例

内核在开租约时把形态写进 `lease.form`，取值是 `Config.forms` 里**按席位**查到的那一个（`graph/…/reducer/lease.py`，F3 体质修炼 001 的 T4-2）。主实例的 solve 席位已经绑定 `h1.solo@2`。若把 `h1.tunshi` 也绑到主实例的 solve 席位，二者只能留一个，否则租约记下的形态与实际跑的不一致，审计就错了。

三个选项（EN1）：

| 选项 | 体质改动 | 代价 | 推荐 |
| --- | --- | --- | --- |
| a. **单独的分析实例**：同一套代码，另起一个栈，数据目录独立，功法文件为 `gongfa.engine.json`（主功法 + solve 席位换成 `h1.tunshi`、H3 加 `h3.tunshi-tools`），经已有的 `PAODING_FENJUE_GONGFA` 指定 | 0 | 多跑一个栈；界面要能切到“方案分析”工作区；异火榜与炼档在仓库里，两个实例不需要共享状态 | **推荐** |
| b. 主实例 + 体质修炼：开题可声明形态（`open_problem` 可选字段，人的令牌写入，`validate` 核对是该席位的形态之一），`Config.forms` 改为席位 → 形态列表 | 有（T4 一处字段，单列变更表） | 主实例的事件形状再变一次；但以后同一席位的多形态都能用 | 等第二个同席位形态出现时再提 |
| c. 引擎不进图服务，作独立脚本跑 | 0 | 失去 T2、T3、T4 的承接：要自己再造出站审批、预算硬顶与留档，等于另造一个体质 | 不推荐 |

选 a 还有一个好处：外部代码与它可能夹带的指令只出现在分析实例里，用户的真实任务不与它们同处一个事件账、一个资料库。

包内一致性：`h1.tunshi`、`h3.tunshi-tools` 的清单在 `fires/` 里，但不在主功法里。`tests/fenjue/test_dossiers.py` 今天要求“包里每份清单要么在功法里，要么是谁的上一团火”，实现线把这条放宽为“在任一份提交进包的功法文件里”（`gongfa.json` 或 `gongfa.engine.json`）。

## 2. 工作流

### 2.1 一张图

```
  cz：新建分析（引用 + 模式）
        │
  S0 立项 ── open_problem（开放道，分析实例），原话 + 材料 + 预算（按预算先验取）
  S1 快照 ── intake：上传的直接定版；地址类发扩权卡 → cz 批 → 抓取指定版本 → 撤权
  S2 勘察聚焦 ── probe（确定性）→ 勘察单、专名表、注入标记、读计划
  S3 识火 ── read_excerpt（读丹）→ 观察 → 差距比对 → 候选火清单
        │ deliver #1（partial）
  G1 ═══ cz 挑选：追问 + 决定块「选 C1、C3；排除 C2（理由）；预算 +x」
  S4 萃意 ── 每个选中的候选：机制骨架 → 三稿 → K1–K8 → 火意
        │ deliver #2（partial）
  G2 ═══ cz 确认或逐栏修改：追问 + 决定块「确认 C1；改 C3.essence.statement = …」→ 修改过的重跑 K1–K8
  S5 入位与火序 ── 拆原子 → 归位 → 冲突 → 清单草稿 → 预登记 → 实现步骤 → 火序
        │ deliver #3（answered）：交接包
  G3 ═══ cz 裁决：每个候选「交实现线 / 搁置 / 排除（理由）」；可勾“报告存入资料库”
  S6 交接 ── 实现线：lianhua.py import → 炼档到“入位”状态 → 设计 PR → cz approve → 写代码
                     → 既有 yanti → ronghuo → jue →（sanhuo）
```

### 2.2 每一步的输入、输出、谁决定

| 步 | 输入 | 输出（Schema） | 谁决定 | 预算份额〔占位〕 | 过不去怎么办 |
| --- | --- | --- | --- | --- | --- |
| S0 立项 | cz 给的引用（上传的归档、仓库地址加版本、服务地址、文档、或一段描述）与模式（正式或试算） | `open_problem`；立项单 `intake.json`（[10 §7](./10-schemas.md#7-立项单-intake)） | cz | — | 命中拒收表（本机题库与校准目录等）当场拒收 |
| S1 快照 | 立项单 | 快照（exec 或 input 类 Artifact）及其身份；许可证探测结果 | cz 批扩权卡（只对地址类） | 识火份额内 | 抓取失败重试 3 次；cz 不批则改为请 cz 上传 |
| S2 勘察聚焦 | 快照 | 勘察单、外部专名表、注入标记、读计划 | 自动（确定性） | 0 token | — |
| S3 识火 | 勘察单、读计划、能力剖面、功法与火位注册表、异火榜 | 候选火清单 `candidates.json` + 人读报告 + 覆盖报告（[10 §4](./10-schemas.md#4-候选火清单-candidates)） | 引擎推荐；**cz 挑选** | 45% | 校验不过重写 ≤ 2 次；仍不过带“未过”交付 |
| G1 | 候选清单 | 决定块：选中、排除及理由、对候选的改动、追加预算 | **cz** | — | 决定块解析不了：引擎以 `needs` 列出问题，再等一次追问 |
| S4 萃意 | 选中的候选及其观察 | 每个候选一份火意 `essence.json`（[10 §5](./10-schemas.md#5-火意-essence)）+ 检验报告 + 三稿分歧 | 引擎；**cz 确认（可修改后继续）** | 35% | 同 S3 |
| G2 | 火意 | 决定块：确认、逐栏修改、退回某候选重做、放弃某候选 | **cz** | — | 同 G1 |
| S5 入位与火序 | 确认过的火意、功法与注册表、原子归属表、在途炼档 | 每个候选一份入位方案 `placement.json`（[10 §6](./10-schemas.md#6-入位方案-placement)）+ 火序 + 交接包 `handoff.json`（[10 §9](./10-schemas.md#9-交接包-handoff)） | 引擎；**cz 裁决** | 20% | 同 S3 |
| G3 | 交接包 | 决定块：每个候选交实现线、搁置或排除；报告是否存入资料库 | **cz** | — | — |
| S6 交接 | 交接包与 G3 决定 | 炼档（`placed` 状态）、清单草稿、异火榜更新、设计 PR | 实现线执行命令；**cz 裁决设计 PR** | 主实例之外 | 导入校验不过拒导入 |

### 2.3 工具面

引擎会话的工具（`h3.tunshi-tools` 加既有的几件）。没有通用 `exec`：每个会碰外部内容或执行环境的工具都是固定命令模板（[08 §4.4](./08-algorithms.md#44-对抗防护外部代码是数据不是指令) D3）。

| 工具 | 经脉 | 做什么 | 参数只能是 |
| --- | --- | --- | --- |
| `intake` | M4、M2、M1:request_scope | 读立项单；上传的材料直接定版；地址类按来源发扩权申请，批后以固定模板抓取指定版本（`git` 浅克隆到给定提交；文档用 HTTP GET），抓完即撤权 | 立项单里登记的来源编号 |
| `probe` | M2 | 对快照跑勘察（[08 §3.2](./08-algorithms.md#32-勘察确定性零-token)）的固定脚本，输出登记为 exec 类 | 快照编号 |
| `read_excerpt` | M2、M3 | 按读计划取一段或至多 8 段原文（固定的读文件模板），在工具里调读丹（无工具、定界包裹），解析成观察记录写进观察库；**原文不返回给会话** | 快照编号、路径、行区间、火位 |
| `probe_service` | M2 | 跑 cz 批准过的探测计划里的一条请求，响应登记为 exec 类，再交读丹成观察 | 探测计划编号、条目编号 |
| `obs` | M4 | 按 id、火位、能力维、候选取观察；只返回观察记录 | 过滤条件 |
| `profile` | M4 | 读功法、火位注册表、能力剖面、原子归属表、在途炼档、异火榜 | — |
| `check` | M4 | 对一份产物跑校验器（§7），返回逐条结果；`deliver` 之前必须调，且最后一次结果为全过（或带“未过”标记） | 产物路径 |
| `show`、`kb_search`、`kb_read` | M4、M7 | 既有 | 既有 |
| `request_access` | M1:request_scope | 既有；但目标先比对立项登记的来源，不在其中的不发出 | 来源编号 |
| `deliver` | M1:deliver | 既有；工具面在提交前确认 `check` 已过 | 既有 |

萃丹、盲审丹、位丹不是单独的工具，它们在 `check` 之前由形态的固定流程调起（[08 §2](./08-algorithms.md#2-丹方每一步用哪种模型用多少要什么质量)）。所有丹调用都经端点代理，计入本题预算。

### 2.4 闸点：交付加追问

每一闸由两个已有的事件完成，不需要新事件：

1. **引擎交付**（`deliver`）：`answer` 是这一步的人读报告（authored 类 Artifact），结构化产物（`candidates.json` 等）作为 authored 类登记并在报告里列出 sha256；`claims` 里每一条关键判断引用勘察输出或快照（exec、input）；`outcome` 在 G1、G2 前为 `partial`，G3 前为 `answered`；`needs` 写“请在下列候选中挑选”一类的话。
2. **cz 追问**（`follow_up`，人的令牌）：正文里带一段**决定块**。界面按产物生成决定块（cz 点选、改字），不需要 cz 手写；手写也能解析。追问可带 `budget_add_usd_milli` 给下一步追加预算（开放道剩余低于收尾保留时必带，内核既有规则）。

决定块的格式（≤ 2000 字，追问的既有上限）：

```
【决定 v1】闸点 1
选：C1，C3
排除：C2（已在地图待办里，不必走吞噬）
改：C1.title = 阶段证据确认
备注：C3 先看压缩，不看接力
```

```
【决定 v1】闸点 2
确认：C1
改：C3.essence.statement = 上下文快满时把较早的过程折叠成带锚点的摘要，后续凭锚点取回原文
退回：无
放弃：无
```

```
【决定 v1】闸点 3
交实现线：C1
搁置：C3（等 C1 定阶后再看）
存入资料库：报告
```

解析是确定性的（实现线的 `paoding_fenjue.engine.decision`）：行首关键字、候选编号、`编号.栏 = 值`。解析不了的行列进下一次交付的 `needs`，引擎不猜。决定块是人的令牌提交的追问正文，进事件账，所以“cz 当时选了什么、改了什么”逐字节可回放。cz 在 G2 的修改同样跑 K1–K8；不过的照样显示给 cz，cz 可以坚持（记“人改，检验未过：K2”），因为人的决定在闸点上高于检验，但这一标记会一路带进炼档。

### 2.5 一次运行结束时

- G3 之后，引擎做最后一次交付：交接包定稿（`outcome: answered`），会话以 `deliver` 结束；
- 任务等人：cz 关题（附反馈），或按既有的交付后闲置自动关（`idle_close_s`）；
- 交实现线的候选由实现线执行 `lianhua.py import`（[12](./12-handoff.md)）；搁置的进异火榜“已识别”并记理由；排除的进“已排除”。

## 3. 试算模式

试算回答“如果吞会怎样”，不承诺吞噬。

| 方面 | 正式 | 试算 |
| --- | --- | --- |
| 闸点 | 三闸，cz 逐闸决定 | **不停**：识火后按 P 自动取前 3（〔占位〕）进萃意与入位，一口气走完 |
| 读预算 | 按分档全额 | 一半；只做广度轮与一轮深度 |
| 萃意 | 三稿互证 + 盲审 + 至多 2 次重写 | 单稿；K1–K5、K7、K8 照跑，K2–K5、K7 不过只标不重写；K1（结构）、K8（指令痕迹）不过照样重写（至多 2 次）。重写后仍不过分两类：九栏不齐（缺必填栏、类型不对）的标“提炼不出”、不进入位，记在报告的 `not_placed`；九栏齐全而 K1 其余规则（用词、栏目间一致性）没过的照常入位，表里标“检验未过”与原因（[13 §9.1](./13-kernel.md)）；不调盲审 |
| 入位 | 完整：清单草稿、预登记、实现步骤 | 简版：主火位、火组、替换谁、冲突、体质影响预判、预估难度；不写实现步骤 |
| 校验 | 全部，作门 | 全部，只标不拦 |
| 产出 | 交接包，可导入炼档 | **试算报告**（[10 §8](./10-schemas.md#8-试算报告-dry-run)）：候选、各自的火意草稿、映射与冲突、体质影响预判、可能的结局（按新生维是否成立给“有望火莲”“至多合炼”“可能并火”三档）、正式走一遍的预估成本与时长 |
| 档号 | 导入时分配 | **不分配**；不能直接导入炼档 |
| 预算 | 100% | 约 50%（`dry_run_share`，〔占位〕） |
| 异火榜 | 选中、交接、排除逐一记 | 每个候选记一条，状态“试算过”，附报告 |
| 转正式 | — | cz 点“正式走一遍”：开新题，复用同一快照的勘察与观察（按快照哈希命中，不重读），识火重做差距比对（公式，不花 token），从 G1 开始走正式流程 |

试算报告的“可能的结局”只是对 [03 §3](./03-huolian.md#3-四种结局) 的预判：新生维的两条“按构造为零”理由都写得出、且 A′ 可做 → 有望火莲；只有胜出的共有维 → 至多合炼；写不出任何一维会胜过 A′ → 可能并火。预判不进任何读数。

## 4. 上下文管理

分析大库会耗尽上下文。引擎自己需要上下文压缩，做法是“状态外置、按单元推进、带锚交棒”：

1. **状态在文件里，不在上下文里。** 工作区的 `run.json`（[10 §10](./10-schemas.md#10-运行状态-run)）记：当前步、每个单元的状态（未做、在做、完成、失败）、每个完成单元的产物 sha256 与一段单元摘要、已花的预算、闸点的决定。观察在只追加的 `obs.jsonl` 里。
2. **按单元推进。** 识火的单元是“火位 × 轮次”（广度轮 8 个、深度轮至多 8 个）；萃意与入位的单元是候选。每个单元开始时，会话的上下文只装：固定提示与表（约 1 万 token）、由 `run.json` 确定性生成的状态摘要（≤ 3 千）、本单元的观察（≤ 2 万）。
3. **单元摘要带锚。** 每个单元结束时，主丹写一段摘要，每一句后面挂观察 id 或产物的 sha256；`check` 核对每个锚都存在。下一个单元只读摘要，需要细节时按锚取观察。
4. **到线就交棒。** 上下文用量到七成（`checkpoint_at_context`），或轮数到上限，形态告诉会话“收尾这一单元并写检查点”，然后结束会话。开放道既有的接力起一个新会话（引擎形态放宽到至多 8 个接力会话），新会话只读 `run.json` 与单元摘要，从第一个未完成的单元继续。接力笔记由 `run.json` 确定性生成，不靠模型自由书写，所以交棒不丢状态，丢的只是模型没写下来的思路。
5. **每一步只看自己需要的。** 萃意不读勘察单全文，只读该候选的观察；入位不读观察，只读火意与表。

这套做法与异火榜上的“带锚压缩”（Y-002）是同一个思路，但这里只是引擎内部的工程，不算吞噬了那团火；Y-002 真的入功法后，引擎可以换用它（那是引擎的一次升级，走全流程）。

## 5. 成本控制

### 5.1 三级预算

| 级 | 是什么 | 谁执行 | 到了怎么办 |
| --- | --- | --- | --- |
| 整题 | 题的预算（开题时按预算先验取，追问可追加） | **体质 T3**：端点代理计量，到顶拒绝；收尾保留 10% 留给最后的交付 | 会话被拒后，收尾轮做一次部分交付，带检查点 |
| 每步 | 整题 × `stage_share`（识火 45%、萃意 35%、入位 20%，〔占位〕） | 形态（功法），按端点代理的计量读数判断 | 收尾当前单元，带检查点部分交付，`needs` 写“追加预算继续”或“缩小范围”（例：只萃意 C1） |
| 每单元 | 每次丹调用的 token 上限；每个火位的读预算 | 工具面 | 单元标“预算截断”，照实写进覆盖报告 |

**断点续传**：任何一级耗尽，都以部分交付结束，交付里引用当时的 `run.json`。cz 追问并追加预算，接力会话从第一个未完成的单元接着做；已完成的单元不重做，已登记的观察不重读。

## 6. 中断、重试与回滚

`run.json` 是状态；每个单元的产物是内容寻址的 Artifact；闸点的决定在事件账里。所以每一步都能说清三件事：

| 步 | 中断（会话死了、进程重启、被叫停） | 重试 | 回滚 |
| --- | --- | --- | --- |
| S0 立项 | 题没开成就什么都没有 | — | 关题 |
| S1 快照 | 快照没定版（没登记 sha256）就丢弃已抓的部分，重抓同一版本 | 网络错误按 2、4、8 秒退避重试 3 次；扩权过期则重新申请 | 撤权；已登记的快照保留但在 `run.json` 里标弃用 |
| S2 勘察聚焦 | 确定性，重跑得同一结果（快照哈希相同） | 同 | — |
| S3 识火 | 从第一个未完成的单元（火位 × 轮次）继续；已完成单元的观察与摘要都在 | 读丹输出不合 Schema 重读至多 2 次；主丹产物校验不过重写至多 2 次 | cz 在 G1 可写“重做识火：…（指示）”：旧清单标作废但保留，新清单另起 |
| G1 | 等人，不花预算 | — | cz 可以再追问一次改选；已做完萃意的候选若仍被选中，产物复用 |
| S4 萃意 | 候选粒度续做 | K 检验不过重写至多 2 次；三稿之一出错时用其余两稿互证 | 退回 G1（追问写“退回闸点 1”） |
| G2 | 等人 | — | 逐候选退回重做；或放弃某候选（进异火榜“已排除”，附理由） |
| S5 入位与火序 | 候选粒度续做；火序是确定性的，重算即可 | 同 S3 | 退回 G2 |
| G3 | 等人 | — | 交接之前随时可改 |
| S6 交接 | `lianhua.py import` 先写临时文件、校验通过后原子改名，失败不留半份 | 导入校验不过直接拒，给出逐条原因 | 设计 PR 未合：关 PR 即回滚（炼档只随 PR 进 `main`）；已 approve：按 `lianhua.py` 既有流程（融火判不收即 `rejected`；入功法后散火） |

**两类横切的中断**：

- **预算耗尽**（任何一级）：见 §5.1，部分交付带检查点，追问加预算续做。
- **cz 叫停**（既有的 `halt`）：在途会话收到收尾轮，写检查点并部分交付；之后追问即解除叫停、接着做。

**一致性规则**：任何一步重做，下游的产物全部标作废（保留不删），`run.json` 里每个产物都记它依据的上游产物 sha256，校验器拒绝“依据已作废”的产物进交付。

## 7. 输出质量校验

引擎的每一份产物在交给人之前都过校验器。校验器是确定性代码，放在 `paoding_fenjue`（实现线的 `paoding_fenjue.engine.check`），属于药鼎，不在引擎火的资产里。两道：引擎工具面的 `check`（交付前），与 `lianhua.py import`（导入炼档时）。

| # | 检 | 内容 |
| --- | --- | --- |
| V1 | 结构 | 按 [10](./10-schemas.md) 的 JSON Schema 校验 |
| V2 | 编号 | 候选、观察、单元编号唯一；作废的不复用 |
| V3 | **引用真实** | 观察 id 在观察库里；证据引用的路径在勘察单的文件清单里、行区间在文件内、区间原文的 sha256 相符；Artifact id 属于本题且类别相符；`id@ver` 在包里存在，声称“生效”的在功法里；能力维在剖面里；体质项在 T1–T5 里；预登记读数里写的既有测试名在仓库里（导入时核对） |
| V4 | 公式复算 | V、C、D、P 与差距类型按 [08 §3.7](./08-algorithms.md#37-差距价值置信难度) 重算一致；火序按 [08 §6](./08-algorithms.md#6-火序) 重排一致 |
| V5 | **禁词** | 遮蔽视图过 K2（外部专名）、K3（代码结构）、K8（指令痕迹）；**给人看的摘要栏**（`plain_summary`）不出现内部设计名词（[07](./07-naming.md) 的名词表与界面用词对照里列出的那些），用常规技术词 |
| V6 | 不抄写 | 所有栏（不只遮蔽视图）与快照文本的最长公共片段 < 12 词元；不出现代码围栏 |
| V7 | 许可证 | 每份产物带出处与许可证状态，状态取值合法；与快照勘察结果一致 |
| V8 | 清单 | 清单草稿过 `paoding_fenjue.contract.check`（形状、经脉不越席位上限）；`params` 里没有预算绝对值（金额、token 数一类的键名与数值模式） |
| V9 | 体质 | 体质影响预判为空；实现步骤提到的文件区与 `KERNEL_PATHS` 不相交；冲突探针命中的步骤都已化解或拆出 |
| V10 | 预登记 | 每个新生维有门槛与两条“按构造为零”理由；必登的本火维齐全 |
| V11 | 与决定一致 | 萃意的候选 ⊆ G1 选中的；G2 的修改逐字体现在火意里；交接包只含 G3 “交实现线”的候选 |
| V12 | 金丝雀 | 验收模式下：产物里没有金丝雀词元；运行期间没有越出立项来源的扩权申请 |

不过的处理：交付前不过，形态让主丹重写（至多 2 次）；仍不过，交付带“未过”标记与逐条原因，界面把它显示在最上面。导入时不过，直接拒导入。

## 8. 异火榜

### 8.1 是什么、放哪

持续维护的候选登记簿。放仓库 `docs/design/fenjue/yihuobang.json`（同名 `.md` 由它生成），只由 `lianhua.py bang` 一组子命令写（实现线），随 PR 审，与炼档同一习惯（FJ11）。引擎读它（`profile` 工具），在交接包里**提议**更新，由导入命令写入（EN11）。条目形状见 [10 §11](./10-schemas.md#11-异火榜条目-bang)。

首批条目由 [05 §2](./05-cases.md#2-异火榜) 迁入（Y-001 至 Y-006），加验收用例 A（Y-007），见 `engine/examples/yihuobang.seed.json`。

### 8.2 状态

```
 identified 已识别 ──▶ selected 选中 ──▶ handed_off 已交实现线（炼档 NNN）──▶ absorbed 已吞噬（品阶 N）──▶ reverted 已散火
      │  ▲                │                       │
      │  └── dry_run 试算过 │                       └──▶ rejected 不收（并火或反噬，炼档 NNN）
      ▼                   ▼
   excluded 已排除（理由）   superseded 并入 Y-NNN
```

### 8.3 排序与“找点什么吞”

- 榜按 P 排序（[08 §6](./08-algorithms.md#6-火序)）。P 依赖能力剖面与功法：剖面或该火位的生效火变了，条目标“需复算”，下次读榜时按条目里存的观察重算差距（纯公式，不花 token）。
- cz 说“找点什么吞”：开一题，模式“从榜上取”。引擎读榜，取状态为已识别或试算过、未被排除、未被火位锁挡住的前 N 个（〔占位〕3），复算后直接进 G1；榜上没有存货（或都被挡住）才问 cz 要一个外部系统。
- 条目的观察依据的快照仍可取时直接复用；取不到时（例：只记了摘要）在 G1 标“观察需重取”，选中后先补读。

### 8.4 失败的分析也是经验

- 每一次运行都在条目的 `runs` 里留一行：分析实例的题号、产物 sha256、走到哪一步、结局与原因。
- 不收（并火、反噬）的，把炼档的 `outcome_why` 抄进条目的 `lessons`。
- **防反复**：已排除与不收的条目，只有下面三种情况之一才会被再次提起：该火位的生效火变了（功法摘要不同）；有了新的外部快照（不同的快照身份）；cz 明说要再看。否则引擎在识火去重时把命中的模式直接挂到旧条目上，标“曾因…排除”。
- 分析报告存在分析实例的事件账与 Blob 里，永远可回放；cz 在 G3 勾“存入资料库”的，界面以 cz 的身份把报告导入资料库（资料库的导入照旧只由人做），作 knowledge 类供以后参考，不作依据（EN12）。

## 9. 并发

| 情形 | 规则 |
| --- | --- |
| 不同外部系统 | 各开一题，并行。每题自己的预算、快照、观察库 |
| 同一外部系统，两次运行 | 立项时按快照身份查重，提示“题 X 正在分析同一快照”；cz 可以继续（例：一次试算、一次正式）。观察库按快照哈希共享只读缓存 |
| 同一外部系统的多个候选 | 萃意与入位在一次运行里做完（都是设计）；**进实现线按火序串行**：前一团的炼档定阶（`adopted` 或 `rejected`）之后，后一团才导入或才进验体 |
| 前一团定阶之后 | 对后一团做**入位复核**（确定性）：按新功法重算原子归属与冲突；被替换的火、原子的拥有者、兼及火位都没变 → 直接继续；变了 → 标“需重新入位”，开一题以“重新入位”模式只跑 S5（便宜，约 25 万重档 token） |
| 跨系统、同一火位 | **火位锁**：`lianhua.py import` 发现该火位已有在途炼档（`placed` 到 `readings_ready`）时拒导入，或按 `--queue` 记进异火榜“已交实现线（排队）”，等锁释放 |
| 与其他设计线 | 引擎不改功法、不改注册表，所以不与功法的版本钉住、读数页等设计线争同一份文件；它只读 |

## 10. 引擎自己的火位

引擎是功法里的火（`h1.tunshi`、`h3.tunshi-tools`），可以被更好的版本替换。自我改进仍走全流程：模型出方案 → 人裁决 → 确定性试炼 → 融火。

- **出身**：首版是自研火，以本设计为出身（`lineage.design`），不经吞噬、不加品阶，只在分析实例的功法里生效（EN13）。
- **之后的版本**：从外部系统吞来更好的分析做法（例：更好的大库聚焦），或删简（例：盲审丹退役），都开炼档。引擎可以分析一个外部系统并提出“替换引擎”的候选，但这类候选标**自指**：火序把它排在同一运行的其他候选之后，入位方案必须登记验收夹具上的读数，裁决只由 cz 做。
- **药鼎不随引擎改**：校验器、八条检验的模式表、能力剖面、决策原子表、机制原语、冲突探针、验收夹具，全是量具。引擎的炼档若触到它们，入位的体质影响预判把这些路径也列为禁区（与 `KERNEL_PATHS` 并列的“量具路径”），不合格。量具的改动单独提、单独裁（[01 §2](./01-boundary.md#2-三个部分不是两个)）。
- **读数**（引擎的炼档预登记用）：

| 维 | 类 | 方向 | 怎么量 |
| --- | --- | --- | --- |
| 验收召回 | 共有 | ↑ | [11](./11-acceptance.md) 三例 × 四形态 |
| 萃意硬检验首次通过率 | 共有 | ↑ | 校验器 |
| 诱饵误报 | 共有 | ↓ | 夹具 |
| 注入服从数 | 本火 | ↓（门槛 0） | 金丝雀 |
| 凭据泄漏数 | 本火 | ↓（门槛 0） | 金丝雀密钥 |
| 每次运行花费、机器时间 | 共有 | ↓ | 端点代理计量 |
| cz 闸点修改率 | 共有 | ↓ | 决定块里“改”的行数 ÷ 产物栏数 |
| 推荐被采纳率 | 共有 | ↑ | G1 选中的 ∩ 推荐的 ÷ 推荐的 |
| 下游结局（滞后） | 共有 | ↑ | 交实现线的候选里最终火莲或合炼的比例 |

- **常设留出**：新版引擎入功法后，分析实例里 ε = 10% 的题（按题号的确定性哈希）用上一版引擎跑，用 F5 已有的留出机制（`holdout`、`arm_of`），两边读数对照，跌破门槛出告警，由人决定是否散火。

## 11. 体质承接一览

| 硬约束 | 怎么做到 |
| --- | --- |
| 信任内核五项不可绕过，引擎也被体质承接 | §1.2：引擎是开放道上的一种会话形态，经脉与事件全是既有的；体质改动 0 行 |
| 引擎不写代码、不推 PR | 工具面里没有写仓库、推送、通用执行的工具；交接由实现线执行 |
| 后三步照旧确定性 | 引擎只到 S5；`yanti`、`ronghuo`、`jue`、`sanhuo` 一行不改 |
| 已有事件回放逐字节不变 | 不新增事件种类与字段；分析实例的事件账是新的；主实例只在导入时改仓库里的文件（git 历史） |
| 外部代码是数据不是指令 | [08 §4.4](./08-algorithms.md#44-对抗防护外部代码是数据不是指令) 的 D1–D8 |
| 许可证标注 | 快照勘察时探测，每份产物带出处与许可证状态（V7）；实现线的参考规则见 [12 §4](./12-handoff.md#4-许可证与出处) |
| 不读本机题库与校准目录 | 摄入的拒收表；引擎从不请求设备文件夹；炉题与预算只来自可插拔数据源 |
