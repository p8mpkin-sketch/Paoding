## 0. 一页结论

1. **三分，不是两分。** 体质（信任内核，五项不可变）、功法（能力层，八个火位，可替换）、药鼎（量具：读数、评测台、体质试炼）。量具单列的理由只有一句：**被度量的东西不得修改度量它的尺子**，否则“吞了变强”无从证明（[01 §2](./01-boundary.md#2-三个部分不是两个)）。
2. **体质五项**对到现有的不变量与强制点：判（I2、I4）、闸（I5 与钥匙环）、顶（I6）、账（I1、I3）、证（I2、I7、I8）。体质对功法只开七条经脉，每一条今天都已经存在，焚决不新开端口（[01 §3–§4](./01-boundary.md#3-体质五项)）。
3. **功法有八个火位**：会话形态、编排、工具面、上下文、知识源、观察面、报告形态、起草。今天每个火位都已经装着火，只是散在 `if role == "solve"` 这类分支里。焚决把它们写成带清单、带摘要、带开关的“火”（[01 §5、§8](./01-boundary.md#5-功法八个火位)）。
4. **席位与形态分开**，这是“不再每次改内核”的关键一刀：内核只认现有的七个席位（`role`）作为权能上限；新的会话形态绑定已有席位，不动内核；真需要新席位才算体质修炼（[01 §6](./01-boundary.md#6-席位会话的权能上限)）。
5. **吞噬协议六步：识火、萃意、入位、验体、融火、散火。** 前三步是设计稿，裁决后才写代码；验体是确定性的体质试炼（T1–T5 对抗剧本，不调模型）；融火跑对照读数；散火是常备的一键回滚。每次一份炼档（[02](./02-lianhua.md)）。
6. **萃意是最重要的一步**：吞的是“火意”，一句不提实现的本质，不是代码。检验方法：把出处遮住，设计还成立吗（[02 §4](./02-lianhua.md#4-第二步萃意提炼火意)）。
7. **火莲判据**照四臂思想设五条臂：本火 B、异火单炼 A′、合火 F、同火对照 B′（噪声底）、原形参照 A°（只作参考）。四种结局：**火莲**（出现两源按构造都为零的新生维）、**合炼**（同维度胜过两源）、**并火**（只是收藏，不收）、**反噬**（体质不过或本火维退步，不收）。读数与门槛在写代码前预登记（[03](./03-huolian.md)）。
8. **进化度量**：体质试炼是门（永远 100%）；严格道四臂照旧，G1 口径不动；开放道用吞噬前后同一组提示词配对对照，加 cz 的盲评；入功法后上一团火进常设留出，跌破门槛出反噬告警，散火由人决定（[04](./04-evolution.md)）。焚决自己的生死线是**体质改动行数**：吞噬要做到不改内核。
9. **首炼推荐“可回放的实时性”**：#115 就是它的异火单炼 A′；合火只加三处（条目成链、分段以 authored 类入账、执行行可点到留档），**体质改动 0 行**，三条新生维都按构造为零，有资格判火莲（[05 §1](./05-cases.md#1-案例一可回放的实时性)）。
10. **迁移五步**：F1 体质试炼与按道补录黄金日志 → F2 火位立名（零差迁移，品阶 1）→ F3 功法摘要入开题事件（焚决自身唯一一次体质修炼）→ F4 首炼 → F5 炼档流程化。旧事件一条不改写，信封不升版，新字段只加可选的，缺省值在读端推（[06](./06-migration.md)）。

## 2. 与庖丁现有设计的关系

- **三层六契约**（规格 2.1）：体质 = 信任根 + 协调基质 + 会话边界里的守门部分（端点代理、钥匙环、双容器、代理工具的校验）。功法 = 规格第 4 节的外壳机制 + 会话边界里的感知部分（提示词、任务包、工具面的组合）+ 起草 + 观察面。三层的划分不变，焚决是在它之上把“外壳”整理成可替换的火位。
- **官知止**（总纲 v1.2）：焚决不是它的反面。功法里每团火都是一个官，照旧回答入库四问；守门官只在体质。官知止说“退位即进化”，焚决说“吞噬即进化”，两者在品阶上同记一笔，用同一套读数（FJ12）。系统变强的方式有两种：吞进更好的做法，或撤掉模型已经不需要的器官。
- **红线 5 诚实对照**：火莲判据是它在“吸收”这件事上的形态。融合的产物赢不过照搬（并火）就不收，赢不过本火就不收。
- **工作台地图**（宪章 v0.5，#111 在途改到 v0.10）：焚决不加站，不改地图。#111 合入后由地图线出一次修订，站表加一列“火位”。改变人看到的流程的吞噬，照旧走地图修订规程。
- **开放道**：开放道本身就是一次没有协议的吞噬。[05 §0](./05-cases.md#0-案例零补档-000一个会话做到底) 按六步给它补了档，暴露两件事：吞噬与体质修炼混在一个 PR 里；没有异火臂。

## 6. v0.2：核心算法与吞噬引擎

> 起因：cz 2026-11-21 设计任务“焚决核心算法与吞噬引擎（丹药层）”。治理骨架（六步）已经够了，缺的是让识火、萃意、入位自动运转的两块：一套算法，一个执行它的智能体。模型在这里是“丹药”：不是火（外部创新才是火），是让炼化成功率更高的催化剂，不同步骤用不同的药、不同的量。
>
> 依据 `main` 486832e：功法第 2 阶，十五团火，H6 常设留出 `h6.activity@1`、ε = 10%；`scripts/lianhua.py`（#125）；炼档 001（火莲，第 2 阶）。本节只出设计，不写实现；实现线的切分见 [12 §7](./12-handoff.md#7-实现线要做的事建议的-pr-切分)。不涉及功法版本钉住与进化读数页（另一条设计线）。

### 6.1 一页结论

1. **确定性优先，模型只做确定性做不了的判断**：摄入、勘察、聚焦、差距公式、八条检验、冲突比对、火序、校验器都是纯函数；模型只读懂原文、判断机制、写成我们的话、拆决策原子（[08 §1](./08-algorithms.md#1-总流程与原则)）。
2. **丹方**：读原文用轻档、无工具的读者；主会话重档；萃意三稿互证；盲审中档、只看遮住出处的火意；入位拆原子用中档（[08 §2](./08-algorithms.md#2-丹方每一步用哪种模型用多少要什么质量)）。
3. **外部代码是数据**：主会话永远看不到外部原文，只看读者交回的结构化观察；主会话没有自由执行；出站只到立项登记的来源；两道确定性输出校验（[08 §4.4](./08-algorithms.md#44-对抗防护外部代码是数据不是指令)）。
4. **引擎是两团火**（`h1.tunshi` 绑定 solve 席位、`h3.tunshi-tools`），跑在开放道上，体质五项自动承接，体质改动 0 行；跑在单独的分析实例里，因为内核按席位记形态（[09 §1](./09-engine.md#1-定位)）。
5. **七步三闸**：cz 挑候选、确认火意、裁决入位方案；每一闸是一次交付加一次带决定块的追问，进事件账（[09 §2](./09-engine.md#2-工作流)）。
6. **一次吞噬**（中型库、3 个候选）约 300 万输入、19 万输出 token，机器时间约 1 小时，另加 cz 三次确认；试算约一半、半小时（[09 §5.3](./09-engine.md#53-一次吞噬的估算)，〔占位〕）。
7. **交接**：引擎交出交接包；实现线跑 `lianhua.py import` 把它变成“入位”状态的炼档，之后开设计 PR、写代码，验体、融火、定阶、散火一行不改（[12](./12-handoff.md)）。

### 6.3 待裁决（EN1–EN20）

> **裁决（cz 2026-11-21）**：EN1–EN20 全部采纳推荐项（#130 合入后）。实现按 [12 §7](./12-handoff.md#7-实现线要做的事建议的-pr-切分) 的 E1 → E7。

每项先写推荐。

1. **EN1 引擎在哪跑。** a. 单独的分析实例（同一套代码，独立数据目录，功法文件 `gongfa.engine.json`）；b. 主实例 + 体质修炼（开题可声明形态）；c. 不进图服务，作独立脚本。**推荐 a**：体质改动 0 行，租约记下的形态如实；外部代码与用户任务隔离。c 会失去出站审批、预算硬顶与留档（[09 §1.3](./09-engine.md#13-为什么要单独的分析实例)）。
2. **EN2 外部系统怎么进来。** a. 首选 cz 上传快照作材料（零出站）；地址类只在扩权卡批准后一次性抓取**指定版本**，抓完撤权；服务只跑 cz 逐条批准的探测计划；b. 引擎按需出站读。**推荐 a**：快照定版，同一份快照重跑结果相同；出站面最小（[08 §3.1](./08-algorithms.md#31-输入的四种形态)）。
3. **EN3 对抗防护的强度。** a. 数据面与控制面分离（主会话看不到外部原文，只看读者的结构化观察）+ 主会话没有自由执行 + 出站只到登记来源；b. 主会话直接读原文，靠提示词与输出检查。**推荐 a**：b 只是原则，a 是可测的机制（[08 §4.4](./08-algorithms.md#44-对抗防护外部代码是数据不是指令)）。
4. **EN4 能力剖面放哪。** a. 量具侧表 `paoding_fenjue/engine/profile.json`，按 `id@ver` 键，校验器核对与功法一致，引擎只能提议修订；b. 写进每团火的清单（摘要会变，每团火升版）。**推荐 a**：剖面是对火的读数，属于量具；火位注册表仍是“现状”的唯一来源（[08 §3.6](./08-algorithms.md#36-我们的能力剖面)）。剖面初值见 [08 附表 A](./08-algorithms.md#附表-a-能力剖面初值)，请 cz 校。
5. **EN5 差距、价值、置信、难度、优先级。** a. 用 [08 §3.7](./08-algorithms.md#37-差距价值置信难度) 与 [§6](./08-algorithms.md#6-火序) 的确定性公式，权重〔占位〕由 cz 定；b. 由模型打分。**推荐 a**：可复算、可审计，模型只给外部的级与注释。
6. **EN6 跨火位模式。** a. 行为有变的每个火位一团火，组成火组，同一份炼档同裁同散（`lianhua.py` 扩展）；b. 每团火一份炼档，靠依赖边串起来。**推荐 a**：一个模式的几部分分开定阶，会出现“只装了一半”的功法（[12 §2.3](./12-handoff.md#23-火组)）。
7. **EN7 需要新火位怎么走。** a. 照 cz 本次的说法走规格变更表（流程同体质修炼，逐条可否决），但单独计为“结构修炼”，不计入体质改动行数；b. 按 06 §5 作功法层结构修订，不走变更表。**推荐 a**：守住“不能硬塞”，同时不让体质改动行数这条生死线被不改体质的事污染（[08 §5.4](./08-algorithms.md#54-需要新火位)）。
8. **EN8 萃意检验哪些是硬门。** a. K1–K5、K7、K8 硬门，K6 盲审只作读数；b. 全部硬门；c. 只 K1–K3。**推荐 a**：K6 会被“模式本来就广为人知”误伤；K4、K7 防的是抄写与只想得到一种实现（[08 §4.3](./08-algorithms.md#43-八条检验)）。
9. **EN9 cz 在闸点的决定怎么传。** a. 用既有的追问带一段固定格式的决定块，界面生成，进事件账；b. 新增人的操作事件（体质修炼）。**推荐 a**：不加事件种类，回放不变（[09 §2.4](./09-engine.md#24-闸点交付加追问)）。
10. **EN10 丹方。** a. 读者轻档、主会话重档、萃意三稿、盲审中档、拆原子中档，用量按预算先验数据源；b. 全部同一档。**推荐 a**：质量瓶颈在差距判断与抽象，用量大头在读原文，分档能省一半以上的重档用量；每颗丹登记退役信号（[08 §2](./08-algorithms.md#2-丹方每一步用哪种模型用多少要什么质量)）。
11. **EN11 异火榜存哪。** a. 仓库 `docs/design/fenjue/yihuobang.json`，只经 `lianhua.py bang` 写，随 PR 审；b. 资料库；c. 事件账。**推荐 a**：与炼档同一习惯（FJ11），可审、可回溯（[09 §8](./09-engine.md#8-异火榜)）。
12. **EN12 引擎能否往资料库存东西。** a. 不能，只提议；cz 在闸点 3 勾选，由界面以 cz 的身份导入（资料库的导入照旧只由人做）；b. 给引擎会话导入权。**推荐 a**：b 要改席位权能（T5 与 M7），是体质修炼。
13. **EN13 引擎首版的身份。** a. 自研火：以本设计为出身（`lineage.design`），不经吞噬、不加品阶，只在分析实例的功法里生效；之后的版本走全流程；b. 先给引擎补一份炼档。**推荐 a**：引擎不是从外部吞来的，硬补炼档会编出一个不存在的“异火”（[09 §1.1](./09-engine.md#11-引擎是哪几团火)）。
14. **EN14 引擎自我改进的门。** a. 校验器、八条检验的模式表、剖面、原子表、夹具都归药鼎，引擎的炼档不得改它们；新版引擎用 ε = 10% 的常设留出对照；“替换引擎”的候选标自指、排在同一运行的最后；b. 允许同一份炼档一起改。**推荐 a**：被度量者不得改度量（[09 §10](./09-engine.md#10-引擎自己的火位)）。
15. **EN15 试算的范围。** a. 走到入位、中间不停、按 P 自动取前 3、预算约正式的一半、不分配档号、结果进异火榜“试算过”；b. 只做识火。**推荐 a**：cz 要的是“如果吞会怎样”，只做识火回答不了体质影响与可能的结局（[09 §3](./09-engine.md#3-试算模式)）。
16. **EN16 界面。** a. 用 [09 §12](./09-engine.md#12-界面用词) 的用词（方案分析、候选方案、发现/抽象/映射、核心机制……），界面本身排进界面线，在引擎形态（E4）之后；b. 与引擎同一期做。**推荐 a**：先让引擎在夹具上过线，界面再按真实产物做。
17. **EN17 验收过线标准。** a. 按 [11 §6](./11-acceptance.md#6-过线标准)：代码与文档形态召回 3/3、萃意硬检验 100%、火位与火组全对、注入服从 0、诱饵全进“已有不差”；b. 只看召回。**推荐 a**：只看召回会放过“把已有的当成缺的”“新生维造假”“被注入”这三种最要紧的错。
18. **EN18 许可证参考规则。** a. 产物一律只含火意；宽松许可的实现线可参考原码并注明，其余（弱/强 copyleft、专有、没找到、不明）一律只借思想、不打开原码；b. 一律不打开。**推荐 a**：与 02 §4 一致，宽松许可下参考原码能少踩坑（[12 §4](./12-handoff.md#4-许可证与出处)）。
19. **EN19 同一系统多个候选的串行粒度。** a. 萃意与入位一次做完（都是设计），进实现线按火序串行；前一团定阶后对后一团做确定性入位复核，变了才重跑入位；b. 每一团都从识火起严格串行到定阶。**推荐 a**：设计便宜、实现昂贵，只串行贵的部分（[09 §9](./09-engine.md#9-并发)）。
20. **EN20 H1 的新形态与既有形态。** 内核按席位记形态，同一席位在一个实例里只能有一个形态。a. 接受这一点：H1 的语义或参数冲突只能“替换”（旧形态进常设留出）或“不收”，不能按题分区并存；等真有同席位多形态的需要时再单提体质修炼；b. 现在就提体质修炼（开题声明形态）。**推荐 a**：验收用例甲就是替换；分区的需求还没出现，不为假设的需要改体质（[08 §5.3](./08-algorithms.md#53-冲突检测)）。

〔占位〕项不单列裁决，各自在首次用到时由 cz 给值：c₀ 与置信上限、聚焦权重与阈值、读预算与 token 上限表、价格表、每步预算份额、试算比例、痛点乘数、K4 的阈值、去重的 Jaccard 阈值、验收的过线门槛、剖面初值与权重。
