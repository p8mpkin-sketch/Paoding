# 02 炼化：吞噬协议

> 焚决设计 v0.1 的第二篇。上位：[README](./README.md)；边界与数据形状见 [01](./01-boundary.md)。本篇把“看到别家好东西 → 变成我们的能力”写成一个标准动作：六步，每步有输入、产出、谁负责、过不去怎么办；每次吞噬一份炼档、一组读数、一个散火点。

## 1. 为什么要一个标准动作

回看这几天的轨迹：入口拒题（#106 开放道）、会话形态不合用（solve）、没有答案键判不了（#94 外部裁决、#103 人工验收）、外部时限卡住（`bind_deadline`）、活动不可见（#115）。每一次都对，但每一次的过程不同：有的先写设计再改内核，有的直接在适配层加分支，有的到验收才发现读数口径要改。没有一处写下“这次吸收的本质是什么、比之前强在哪、怎么证明、怎么撤回”。

炼化协议不让吸收变慢，它让吸收**可比、可查、可撤**：

- 可比：每次都用同一组对照读数（[03](./03-huolian.md)、[04](./04-evolution.md)），好不好不靠印象；
- 可查：每次一份炼档，半年后还能看出为什么当时吞了它；
- 可撤：每次一个散火点，撤回不需要再改一次代码。

## 2. 总流程

```
  异火榜 ──▶ ① 识火 ──▶ ② 萃意 ──▶ ③ 入位 ──▶ ④ 验体 ──▶ ⑤ 融火 ──▶ 定阶（cz 裁决）
  （候选）    看见了什么   本质是什么   落在哪个火位   过体质五项    试火读数
                │            │            │             │ 不过       │ 不达标
                ▼            ▼            ▼             ▼            ▼
              不收         转体质修炼    改设计        反噬：不收     并火：不收
                          （守门性质）   （越出经脉）   （记档）       （记档）

  已入功法的火 ──▶ ⑥ 散火（随时）：开关指回上一团火；炼档记一行；品阶记降
```

每一步都在炼档里留一节。前三步只产出文字（设计稿），第四步起才有代码与读数。第一到第三步的产出就是一份设计稿的骨架，所以**一次吞噬的设计 PR 就是炼档的前三节**，与今天“先设计后裁决”的习惯一致。

## 3. 第一步：识火

**输入**：一个外部系统的可观察优势。来源可以是同类开源系统的文档与行为、论文、评测榜、cz 的实际使用体验、或我们自己的验收里暴露的缺口。

**产出**：炼档第一节，四行：

| 栏 | 写什么 | 例（会话活动） |
| --- | --- | --- |
| 出处 | 哪个系统、哪个版本或日期、在哪里看到 | 若干编码智能体的终端与网页界面（2026 年 11 月所见） |
| 现象 | 用户看得到的差别，一句话 | 执行时能实时看到它在调什么工具、想什么 |
| 我们缺什么 | 对上庖丁的哪一处空白，带证据 | cz 2026-11-20 实测：开放道“什么进度也看不到”，图台空白直到会话结束 |
| 是否异火 | 是不是一个**模式**，而不是一个功能点或一段代码 | 是：“执行过程的实时表面”是一类做法，不绑定某一家 |

**收与不收**：只是“别家多一个按钮”的，不算异火，进普通需求（地图修订规程）。异火必须是一种做法，能在别的场景里复用。

**不读本机评测数据。** 识火的证据可以来自 cz 的使用描述、仓库里已有的读数与报告、公开资料；不来自任何本机题库或校准目录。

## 4. 第二步：萃意（提炼火意）

**这是整个协议里最重要的一步。** cz 的原话：吞噬的对象是创新与方法，不是代码。萃意要回答“它的本质是什么”，答案是一段不提任何实现的描述。

**产出**：炼档第二节：

1. **火意**：一句话本质。好的火意能让人想到不止一种实现。例：“执行的每一步在它发生时就对人可见”，而不是“有一个 WebSocket 推送面板”。
2. **它依赖的前提**：在它的原系统里，这个做法依赖什么才成立。例：原系统的实时流来自工具进程本身，因此可信度等于工具进程的可信度；它是易失的，刷新页面就没了。
3. **它的代价**：原系统为它付了什么。例：流不留档，事后看不到当时看到的；流里可能带出凭据。
4. **与本火的重叠与冲突**：我们哪团火已经在做相近的事；放进来会和体质的哪一项冲突。例：重叠 T4 的 `as_of` 回放（我们能回放，但只能回放事件，看不到过程）；冲突 T2（流里的凭据）、T5（流是叙述，不是证据）。
5. **融合假设**：本火与异火合在一起，能出现一个**哪一方单独都没有**的性质。写成可以检验的一句话。例：“实时看到的每一行，事后能逐字节回放出来，并能点进去看到对应的执行留档”，即“可回放的实时性”。
6. **守门性质检查**：火意里有没有守门性质的部分（新的出站规则、新的证据类别、新的席位权能）。有就把那一部分拆出去，转[体质修炼](./01-boundary.md#7-体质修炼不经吞噬协议)，剩下的继续。

**不照搬代码的三条落实**：

- 炼档第二节不贴外部代码，只写机制。需要说明机制时用伪代码或我们自己的数据形状。
- 实现时如果参考了外部代码，按其许可证判断能否借鉴，并在炼档里写明；与 Apache-2.0 不兼容的一律只借思想。
- 验收时问一句：把出处一栏遮住，这份设计还成立吗？成立才说明吞的是火意。

## 5. 第三步：入位（映射到火位与经脉）

**产出**：炼档第三节，一张映射表：

| 栏 | 写什么 |
| --- | --- |
| 火位 | 落在哪个火位（H1–H8）。跨两个火位的拆成两团火，各自一份清单 |
| 席位 | 仅 H1：绑定哪个已有席位。需要新席位的，退回第二步拆出体质修炼 |
| 经脉 | 申请哪几条经脉（M1–M7），逐条说明用途 |
| 清单草稿 | [01 §8](./01-boundary.md#8-一团火的数据形状) 的 `Fire` 形状，除摘要外全部填好 |
| 入库四问 | 哪类官（感知官或量具）、退役信号、启用条件、对照臂 |
| 替换谁 | 这团火上去之后，原来那团火是退到常设留出、还是保留为对照臂、还是并存（同一火位两团火按题分配） |
| 预登记读数 | 第五步要看的读数与门槛，**在写任何代码之前登记**（[03 §4](./03-huolian.md#4-预登记)） |

入位过不去的两种情况：申请的经脉超出席位的权能上限（改设计）；找不到火位（说明这不是能力层的事，可能是量具或体质的事，分别单独提）。

**到这里为止是设计 PR。** 前三节写完，开 PR 给 cz 裁决“值不值得炼”。裁决通过才进第四步。

## 6. 第四步：验体

**验体是确定性的、不调用模型的、可重复的检查。** 它回答一个问题：这团火装上之后，体质五项是否全部仍然成立。过不了就是反噬，不收。

验体分两段，全部写成测试，进 CI：

### 6.1 静态验体（读清单与代码）

| 检 | 做什么 | 现成的依据 |
| --- | --- | --- |
| 清单形状 | `Fire` 每个字段齐全、类型对、摘要可复算 | 同 `wire_schema` 的做法 |
| 经脉越界 | `ports` ⊆ 席位权能上限表（[01 §6](./01-boundary.md#6-席位会话的权能上限)） | 新增 |
| 依赖方向 | 火的代码只 import 各组件的 `contract` | `ci/check_deps.py` |
| 体质内部不可达 | 火的代码不 import 事件日志、钥匙环、闸门内部、判官运行器内部；不直接开网络套接字 | 在 `check_deps` 上加一张禁止表 |
| 领域词 | 火的代码与资产不含领域词（红线 3） | `ci/check_domain_words.py` |
| 入库四问 | `organ` 四栏非空；`class` 不是守门官 | 新增 |
| 资产寻址 | 每个资产的 sha256 与文件一致 | 新增 |

### 6.2 动态验体（体质试炼）

在假 CLI 与假上游上起全栈，让装了这团火的系统跑一组**对抗剧本**。每项体质一组，每组若干条，任一条失败即反噬：

| 体质 | 剧本要验证的 | 已有可复用的测试 |
| --- | --- | --- |
| T1 判 | 火的会话无论提交什么，严格道题都到不了 `solved`/`accepted`，除非判官或人；开放道交付的判定来源恒为 `self`；严格道的判官路径对这团火无感（同一道严格道题，装与不装，判官收到的候选逐字节相同） | `graph/tests/test_open_lane.py`、`test_acceptance.py`、`eval/tests/test_open_lane_isolation.py` |
| T2 闸 | 开题零出站：火的会话发起的任何外部请求，未批前都被闸门拒；金丝雀密钥（钥匙环里放一个已知假密钥）不出现在事件、会话记录、活动流水、交付、导出物里；原话里的凭据在扩权卡与交付里被遮盖 | `test_scope_grants.py`、`adapter/tests/test_solve.py`、金丝雀测试（AC-M5） |
| T3 顶 | 火的会话尝试超支：代理到额即拒，总花费不越硬顶；墙钟到点被回收；收尾保留生效 | 代理 429 与哮天犬的测试 |
| T4 账 | ① 全部既有黄金日志逐字节回放（状态哈希、各前缀哈希、`/work` 与状态视图摘要）；② 装了火的系统把同一剧本跑两遍，两份日志在去掉时间戳后逐字节相同；③ 火没有在 `reducer` 之外写过一条事件 | `test_m1_log_replays_byte_for_byte`、`test_reducer.py`、新增黄金日志（[06 §3](./06-migration.md#3-旧事件回放逐字节不变)） |
| T5 证 | 火不能登记 exec 或 judge 类；authored 与 knowledge 不入依据；交付引用只认 exec 与 input；四列读数不合并；开放道读数不进严格道统计与 G1 | `test_isolation.py`、`reducer/deliver.py` 的测试、#114 的“引用不进执行记录分子” |

这一组测试叫**体质试炼**（代码里 `tests/fenjue/trials.py`，按 T1–T5 列出各组件里的对抗测试；F1 已落地）。它的大部分条目今天已经散在各组件的测试里，第一步迁移（[06 §2](./06-migration.md#2-分期)）只是把它们收拢成一个以“火”为参数的套件：同一套剧本，换一团火再跑一遍。

**验体不判断好坏，只判断安全。** 好不好是第五步的事。

## 7. 第五步：融火

**产出**：合火（新的一团火）、炼档第五节（试火读数）、品阶提议。

1. **实现合火。** 按第三步的清单写代码。代码进功法所在的组件，开关缺省关。
2. **试火。** 按预登记的读数跑对照：本火臂、异火臂、合火臂，外加同火对照估噪声（[03](./03-huolian.md)）。严格道的四臂照旧跑；开放道跑吞噬前后同一组提示词的对照（[04](./04-evolution.md)）。试火所用的题与提示词来自可插拔的炉题数据源，不来自本机题库；每次运行的预算取自预算先验数据源，设计里用〔占位〕表。
3. **定性。** 按 [03 §3](./03-huolian.md#3-四种结局) 把结果归为火莲、合炼、并火、反噬之一。只有火莲与合炼可以入功法。
4. **定阶。** 炼档连同读数交 cz 裁决。通过后开关打开、功法摘要更新、品阶加一（[04 §2](./04-evolution.md#2-品阶)）。

## 8. 第六步：散火（回滚）

散火是常备的，不是事故时才想起来的。

- **怎么散**：把火位的开关指回清单里 `lineage.from` 记下的上一团火。功法摘要随之变回上一个值。不需要改代码、不需要重启（设置层热生效）。
- **对在途任务**：题在开题时钉住了功法摘要（[01 §9](./01-boundary.md#9-功法怎么进事件又怎么不影响回放)）。散火只影响之后新开的题；在途的题按开题时的功法跑完。紧急情况下人可以对在途的题“降一阶”，由人的令牌发起，下一次派工起生效，已经在跑的会话不被杀（与 D12 叫停同一思路：先让它收尾）。是否提供这个紧急操作见 FJ6。
- **锁定怎么落地（FJ6，2026-11-21）**：每一版上线过的功法按摘要存档在 `fenjue/src/paoding_fenjue/archive/`（`gongfa/<摘要>.json`、它引用的每团火 `fires/<id>@<ver>.json`、火的资产即提示词原文 `assets/<sha256>`），只增不改。在跑的题每次派工、每个会话都经 `paoding_fenjue.for_problem(题)` 按开题事件里的摘要取那一版：会话形态、提示词原文（按那一版清单里的 sha256 取，不读此刻的文件）、工具面顺序（H3）、是否入账与常设留出的比例（H6）、司南的事项顺序与预留规则（H2）。焚决之前开的题（没有摘要）与存档里找不到的摘要退回此刻的功法。`lianhua.py jue` 与 `sanhuo` 先存档再改功法；手改功法或本火修订之后跑 `lianhua.py archive`；CI（`tests/fenjue/test_archive.py`）核对此刻的功法已存档、每份存档按摘要重算得出、存档的火与此刻同版本的清单一字不差。
- **还没做的两件（都要动内核，待裁）**：① 租约事件里的 `form` 由内核从启动时的配置抄（F3），H1 换过之后、在跑的老题领租约时抄到的是新功法的形态，与会话实际用的（锁定的那一版）不一致；要按题的摘要查形态，内核的 Config 得能按摘要给形态表。② “在途降一阶”要一个人的令牌发起的事件，把一道题改钉到上一版。两件合成一次体质修炼提给 cz。
- **记录**：炼档追加一行（谁、何时、为什么、读数依据）；品阶记一次降阶，不抹去原来的升阶记录。
- **自动的反噬告警**：入功法后，常设留出（规格 8.6 的 N2）按小比例把题分给上一团火。合火的读数在留出对照上跌破预登记的门槛时出告警，由人决定是否散火。**系统不自动散火**：散火改变产品行为，是人的决定。

## 9. 炼档

每次吞噬一份，放在 `docs/design/fenjue/dossiers/` 下（FJ11），文件名是档号加短名，例 `001-replayable-live.md`，旁边一份同名的 `.json` 存机器可读的部分（清单、预登记、读数、裁决）。炼档不手写：`scripts/lianhua.py` 每一步一条命令（`new`、`cuiyi`、`ruwei`、`approve`、`yanti`、`ronghuo`、`jue`、`sanhuo`），把这一步的产出写进 JSON，`.md` 由 JSON 生成；字段的说明见同目录的 `TEMPLATE.md` 与 `TEMPLATE.json`。CI 里 `tests/fenjue/test_dossiers.py` 逐份核对（F5）。

```
炼档 001：可回放的实时性
一、识火      出处 / 现象 / 我们缺什么 / 是否异火
二、萃意      火意 / 前提 / 代价 / 重叠与冲突 / 融合假设 / 守门性质拆分
三、入位      火位 / 席位 / 经脉 / 清单草稿 / 入库四问 / 替换谁 / 预登记读数
四、验体      静态 7 检与动态 T1–T5 的结果（测试名与提交哈希）
五、融火      三臂读数、噪声底、结局（火莲 / 合炼 / 并火 / 反噬）、品阶提议
六、裁决      cz 的裁决、日期、附加条件
七、散火记录  （有则记）
```

炼档的度量（每一次都要记，供 [04](./04-evolution.md) 汇总）：

| 量 | 含义 |
| --- | --- |
| 炼化周期 | 从识火到定阶的天数 |
| 体质改动行数 | 本次吞噬对体质组件的改动行数。**目标是 0**；非 0 说明这次其实夹带了体质修炼，应拆开 |
| 火位改动面 | 改了几个火位、几个文件 |
| 试火花费 | 三臂与噪声底的总花费 |
| 结局 | 火莲、合炼、并火、反噬 |
| 散火次数 | 入功法后被撤回的次数 |

“体质改动行数为 0”是焚决成功与否最直接的读数：它就是 cz 说的“不用每次改内核”。

## 10. 与现有规程的关系

- **地图修订规程**（[宪章 §3](../task-lifecycle/README.md#3-修订规程新需求等于修订地图)）：一次吞噬如果改变了人看到的流程（新的卡片、新的结果页区块），仍要按规程修订地图。炼档引用地图修订的 PR，不重复写站表。
- **入库四问**（规格 2.3）：原样保留，是第三步的一栏。
- **官知止审计**（总纲 §1.4）：每个里程碑重跑消融臂时，把功法里每团火当作一个官，一并算退役距离。
- **异议与裁决**（`docs/m0/dissent-*.md`）：实现中发现设计缝隙，照旧写异议；吞噬中发现体质缝隙，写体质修炼提案，不在炼档里改。
