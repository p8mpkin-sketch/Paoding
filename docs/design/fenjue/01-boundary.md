# 01 两层边界契约：体质与功法

> 焚决设计 v0.1 的第一篇。上位：[README](./README.md)。本篇定义什么在信任内核（体质，不可变），什么在能力层（功法，可插拔），两者之间只经哪几条端口（经脉）相连，以及能力层里“一团火”的数据形状。
>
> 现状依据：`main` 17b2217（#113 已合）。在途未合的按“即将落地”对待并逐处注明：#111（地图 v0.9–v0.10 与 L3 第三步）、#114（资料库第二期）、#115（会话活动面板）、#105（续期门）。

## 1. 一句话

**体质守“什么为真、什么可放行、花多少、记在哪”；功法决定“怎么做”。** 体质只出许可，功法只做选择。功法里的任何东西被换掉、被撤掉，系统仍然正确，只是变好或变差；体质里的任何东西被换掉，系统就不再是庖丁。

这与[官知止总纲](../paoding-allegory-mapping.md) §1.1 的第一条律令是同一件事换个说法：官不得进入正确性路径。焚决只是把“官”从一个个散落在代码里的分支，收拢成一层有接口、有清单、可整体替换的功法。

## 2. 三个部分，不是两个

cz 的需求写的是两层。落到现有代码上，需要把第三样东西单独拎出来，否则吞噬协议会自己给自己打分：

| 部分 | 名字 | 包含什么 | 能不能被吞噬改动 |
| --- | --- | --- | --- |
| 信任内核 | **体质** | 五项（§3）及其强制点 | 不能。只能经“体质修炼”这条单独的、更重的流程增强（§7），永不削弱 |
| 能力层 | **功法** | 八个火位上的火（§5） | 能。吞噬、换火、散火都只发生在这里 |
| 量具 | **药鼎** | 归因表、读数投影、四臂评测台、开放道对照台、验体套件 | 不能被一次吞噬顺手改动。量具的改动单独提、单独裁 |

**为什么量具不能跟着功法变：被度量的东西不得修改度量它的尺子。** 一次吞噬如果同时改了它自己的读数口径，“变强了”就无从证明。现有的规格已经把量具单列为第三类官（规格 2.3：量具永不退役、永不守门），焚决沿用这个划分，只是给它一个在架构图上的位置。

## 3. 体质五项

cz 列的五项，逐项对到规格不变量与代码里的强制点。这张表是体质的全部；没有列在这里的，都不是体质。

| # | 名 | 守的是什么 | 对应不变量 | 强制点（代码） |
| --- | --- | --- | --- | --- |
| T1 | **判**（独立判定） | 严格道里“做成没有”只由判官在洁净容器里重放判定，或由人按登记在先的清单验收；干活的会话永远到不了 `solved` 与 `accepted`；开放道的交付只记 `delivered`、判定来源 `self` | I2（后半）、I4 | `judgebox/` 判官运行器；`qicao/vet.py` 的判据登记；`graph/…/reducer/judge.py`、`close.py`；终态四值与 `by_authority` 四列 |
| T2 | **闸**（默认零出站与运行时扩权） | 开题零出站；出站只经执行层闸门 `gate()` 这一个出口；扩权只来自人的令牌或确定性白名单；能力 ≤ Intent 风险 ≤ 授权；真实密钥只在端点代理进程内存（钥匙环），模型容器里只有任务令牌 | I5 | `executor/` 的 `compile` 与闸门；`graph/…/reducer/grants.py`；`adapter/…/proxy.py`、`keyring.py`、`creds.py`；双容器部署 |
| T3 | **顶**（预算硬顶） | 花费的硬顶在容器之外执行；预算预留与租约原子；墙钟与停滞由哮天犬回收 | I6 | 端点代理计量与 429；`reducer/lease.py` 的预留；`watchdog/` |
| T4 | **账**（事件账） | 共享状态只经一条只追加、按题哈希链、可重放的事件日志改变；`validate` 与 `apply` 是纯函数，写入路径上没有模型；等级不存储、只派生；读端点可 `as_of` 回放 | I1、I3 | `graph/…/eventlog.py`、`envelope.py`、`replay.py`、`reducer/`；旧日志逐字节回放测试 `test_m1_log_replays_byte_for_byte` |
| T5 | **证**（证据分级） | Artifact 出处分类（exec、judge、input、authored，#114 起加 knowledge）；只有 exec、judge、input 可作依据；执行留档、输入材料、外部回执、人工验收四类读数分开计、永不合并；等级不出题；估值不进等级 | I2（前半）、I7、I8 | `graph/contract.py` 的 `ADMISSIBLE_CLASSES`；`reducer/deliver.py` 的引用校验；`views` 的分列读数；题界与封存 |

两点说明：

1. **密钥隔离归 T2。** 密钥是“出站”的另一面：出站审批管的是能去哪，钥匙环管的是凭什么去。两者是一件事。
2. **`vet()` 的判据登记归 T1，起草不归。** 起草模型（`qicao/draft.py`）是智能体站，属于功法；把草案变成事件之前的确定性校验 `vet()` 守的是“判据先行”（严格道）与“开放道不冒充已解决”，属于体质。

## 4. 经脉：体质对功法开放的七条端口

功法碰体质只有这七条路。每一条今天都已经存在，焚决不新开端口，只把它们登记成一张表，作为验体时的白名单。

| # | 经脉 | 走什么 | 体质在这条路上做什么 | 今天的实现 |
| --- | --- | --- | --- | --- |
| M1 | **提议** | 会话令牌提交 `add_fact`、`add_intent`、`deliver`、`request_scope` 等提议 | `validate` 当场确定性校验，合格才追加；谁能提交什么按席位查表 | `submit`、`deliver`、`request_access` 代理工具 → 图服务 |
| M2 | **执行** | 一条命令 | 在执行容器里按授权编译能力运行；输出自动登记为 exec 类 Artifact | `exec` 代理工具 → 执行层 |
| M3 | **模型** | 一次模型请求 | 经端点代理：换上真实密钥、计量、到顶拒绝 | 端点代理（Anthropic 兼容与 OpenAI 兼容两种格式） |
| M4 | **读** | 状态、视图、Artifact 正文、活动流水 | 只读；`as_of` 回放；不提供任何写入 | `show` 工具、HTTP 只读端点、SSE；#115 的 `/v1/leases/{id}/activity` |
| M5 | **判** | 请求一次判定 | 判官运行器另起洁净容器重放 | `request_judge` |
| M6 | **人** | 卡片（审批、扩权、续期、验收、叫停） | 人的决定只经人的令牌，带 `seen.card_hash` | 卡片投影与 `approve`、`grant_scope`、`accept` 等人的操作 |
| M7 | **知** | 检索与引用资料 | 资料以 input 或 knowledge 类登记，knowledge 不作依据 | #114（即将落地）：`kb_search`、`kb_read` |

**功法不能做的事**（验体时逐条断言，见 [02 §6](./02-lianhua.md#6-第四步验体)）：直接写事件日志；铸造或转借令牌；绕开端点代理发模型请求；登记 exec 或 judge 类 Artifact；批准扩权、抬高硬顶；读钥匙环；改量具的读数口径；import 体质组件的内部模块（`ci/check_deps.py` 已经把这一条机械化了）。

## 5. 功法：八个火位

火位是能力层里可替换的槽。一个火位在任一时刻装着一团火（或在常设留出时装着两团，按题分配）。今天每个火位里已经有火，只是没有被叫出名字，散落在 `if role == "solve"` 一类的分支里。

| # | 火位 | 决定什么 | 今天装的火（本火） | 主要用到的经脉 |
| --- | --- | --- | --- | --- |
| H1 | **会话形态** | 一个会话带哪些工具、读哪份提示词、何时结束、上下文用完怎么接力 | 三段式（bootstrap、reason、explore）；独行（solve）；判官复判；召回（无模型） | M1–M4 |
| H2 | **编排** | 给定内核派生的“可做事项”，先做哪个、开几个、接力几次、何时等人 | 司南 `loop.py` 的固定次序与 `TASK_ORDER`；开放道“预留剩余全部、接力至多 5 个” | M4（读 `/work`）、M1（租约） |
| H3 | **工具面** | 会话看到的代理工具集合与每个工具的形状 | `exec`、`submit`、`show`、`request_access`、`deliver`；#114 加 `kb_search`、`kb_read` | 每个工具必须是经脉的组合 |
| H4 | **上下文** | 会话内与会话间如何保留、压缩、交接信息 | 三层视图（任务包）；开放道工作区 `NOTES.md` 接力；无压缩 | M4 |
| H5 | **知识源** | 资料从哪来、怎么切、怎么检索 | 书库 `shuku/`（文字类导入、混合检索、hash 向量器）；通鉴记忆召回 | M7、M4 |
| H6 | **观察面** | 人在执行中与执行后看到什么 | 前沿、时间轴回放、成本仪表、任务页四分栏；#115 加会话活动面板 | M4（只读） |
| H7 | **报告形态** | 交付与结果怎么组织、怎么呈现 | `deliver` 的答案、主张、自检、未验证、需要；结果页 | M1（`deliver` 的形状由体质定，呈现由功法定） |
| H8 | **起草** | 一句话怎么变成草案 | 起草模型只指认原文区间（`qicao/draft.py`），按设置档案解析模型 | M3 |

**内核派生“许可”，功法做“选择”。** `/work`（`graph/…/work.py`）是内核从日志派生的可做事项清单，属于 T4；“开放道的题只派 solve”这类规则写在那里，是因为它约束谁能拿到什么租约。编排火位只能在 `/work` 给出的项里挑，不能凭空造一个租约种类。

**两条边界情况：**

- **`deliver` 的字段集归体质，交付页归功法。** 交付体的字段（`answer`、`outcome`、`claims[].refs` 等）由 `reducer/deliver.py` 校验，是 T5 的一部分；字段怎么排版、哪些先显示、要不要加图，是 H7 的事。报告形态的火想加一个字段，就是体质修炼，不是吞噬。
- **观察面只读。** H6 的任何火都只能经 M4 读。#115 的活动流水由适配层写在会话目录，不进事件账，这一点在 [05 案例一](./05-cases.md#1-案例一可回放的实时性) 里是融合的出发点。

## 6. 席位：会话的权能上限

`graph/…/envelope.py` 的 `ROLES` 今天有七个：bootstrap、reason、explore、verify、idler、recall、solve。它们在内核里决定“这个令牌能提交什么”（`reducer/__init__.py` 的 `_who`）。问题是：开放道加 solve 的时候，`ROLES`、`_who`、`REQUEST_ROLES`、适配层的四处 `if role == "solve"`、司南的 `_reserve` 都改了一遍。这就是 cz 说的“每吸收一个新能力都要改一次内核”。

焚决把这两件事拆开：

- **席位**（seat）留在体质，就是现有的 `role`。它只回答权能问题：能不能加 Intent、能不能执行、能不能交付、能不能申请扩权。
- **形态**（form）放进功法 H1。它回答“这个会话怎么工作”。每个形态在清单里声明绑定哪一个席位，权能以席位为上限。

**新形态绑定已有席位不动内核；需要一个新席位才算体质修炼。** 例如“带子代理的独行”仍绑定 solve 席位；“只读复核”绑定 verify 席位；如果将来某种形态需要一种今天没有的权能组合（比如既能加 Intent 又能交付），那是对 T1 与 T5 的改动，走 §7。

席位与经脉的对照（权能上限表，验体时用它判定一团火申请的经脉是否越界）：

| 席位 | M1 提议 | M2 执行 | M3 模型 | M4 读 | M5 判 | M7 知 |
| --- | --- | --- | --- | --- | --- | --- |
| bootstrap | add_fact、request_scope | 是 | 是 | 是 | 请求 | 是 |
| reason | add_fact、add_intent、abandon_intent、request_scope | 否 | 是 | 是 | 请求 | 是 |
| explore | add_fact、request_scope | 是 | 是 | 是 | 请求 | 是 |
| solve | deliver、request_scope | 是 | 是 | 是 | —（开放道无判官） | 是 |
| verify | 无（只读复核，读数由量具投影） | 是 | 是 | 是 | 否 | 是 |
| recall | add_fact（白名单） | 否 | 否 | 是 | 否 | 否 |
| idler | 按规格 4.5，未实现 | — | — | — | — | — |

表里的值以 `reducer/__init__.py` 的 `_who` 与 `grants.REQUEST_ROLES` 为准；verify 一行按开放道 §3.6 复核的设计写，复核的实现落地时以实现为准，修订本表。

## 7. 体质修炼：不经吞噬协议

外部系统的有些长处，本质是守门性质的，例如更强的沙箱、更细的出站审批、新的证据类别。它们不进功法，因为功法里的东西可以被散火撤掉，而守门性质一旦存在就不该被一键撤掉。

规则：

1. **能力层只装感知官与只产生读数的部件，守门官只在体质。** 一团火在清单里声明自己是守门性质的，验体直接不收，转体质修炼。
2. **体质修炼只许增强。** 每一项都要回答：它比现有的强制点更严在哪里，哪些既有路径会因此被拒，旧事件回放是否逐字节不变。
3. **体质修炼走规格变更表**（规格附录 C 的做法），逐条可否决，由 cz 裁决。它可以由一次吞噬的“萃意”一步发现，但不在吞噬的档案里完成。

这条线防的是一个具体的坑：把“为了接一个新能力而放宽体质”伪装成“吞噬”。

## 8. 一团火的数据形状

每团火有一份清单。清单是确定性数据，可规范化（JCS）后取 sha256 作为火的摘要；所引用的提示词、模板等资产按内容寻址。

```ts
type Fire = {
  id: string,                  // 例 "h1.solo"：火位号 + 短名
  ver: number,                 // 同一团火的修订号
  slot: "H1"|"H2"|"H3"|"H4"|"H5"|"H6"|"H7"|"H8",
  seat?: Seat,                 // 仅 H1：绑定的内核席位（权能上限，见 §6）
  ports: Port[],               // 申请的经脉，例 ["M1:deliver","M1:request_scope","M2","M3","M4","M7"]
  params: object,              // 本火的参数（接力上限、收尾保留比例、轮询间隔……），不含任何密钥或预算数字
  assets: { name: string, sha256: string }[],   // 提示词、模板、规则表，内容寻址
  organ: {                     // 入库四问（规格 2.3），沿用不变
    class: "感知官" | "量具",   // 守门官不收（§7）
    retire_signal?: string,    // 感知官：可测量的退役信号
    enable_when: string,       // 启用条件
    control_arm: string,       // 对照臂，默认取它自己的退化形态
  },
  lineage: {                   // 出身
    dossier?: string,          // 炼档号，本火（焚决之前就有的）为空
    from: string[],            // 来源：本火的 id 与异火的档号
  },
  switch: string,              // 开关路径，例 "fires.H1"；散火就是把它指回上一团火
}

type Gongfa = {                // 功法：此刻生效的整套火
  jie: number,                 // 品阶
  fires: Record<Slot, string>, // 火位 → "id@ver"
  holdout?: Record<Slot, string>,  // 常设留出：同一火位上保留的上一团火（见 04 §5）
  digest: string,              // sha256(JCS(本对象除 digest 外的部分 + 各火清单摘要))
}
```

**预算数字不进火的清单。** 一团火可以声明“收尾保留取预算的 10%”这类比例，但任何默认预算的绝对值都来自设置层的预算先验数据源（可插拔，外部注入“档位 → 默认预算”表；设计里一律用〔占位〕表）。这条与[一句话开题](../kaiti/README.md)的约定相同。

## 9. 功法怎么进事件，又怎么不影响回放

开题时，`validate` 已经把设置的版本与摘要写进 `open_problem` 的事件体（`reducer/problem.py` 第 310 行附近的 `settings: {version, digest}`）。功法沿用同一个机制：

- 新开的题，`open_problem` 的事件体多一个可选字段 `gongfa: {jie, digest}`，由 `validate` 从只读配置里取值写入。
- 它和 `settings` 一样**不进等级、消费门与画像**，内核的 `apply` 只把它原样存进题的记录，不解释它。
- 旧事件没有这个字段。没有就是“焚决之前”，读端把它显示为“第 0 阶（旧法）”，这个映射是读端的纯函数，不写回日志。
- 租约事件（`lease`）可以多一个可选字段 `form`，记下这次会话用的形态 id。缺省时由席位推出（bootstrap、reason、explore 推为三段式，solve 推为独行），同样只在读端推。

这样做到两点：一道题用哪一套功法做的，事后能从日志里查到（审计）；功法怎么换，内核的状态哈希都不变（旧日志逐字节回放）。详细的不变式与测试见 [04 §6](./04-evolution.md#6-回放不变式) 与 [06 §3](./06-migration.md#3-旧事件回放逐字节不变)。
