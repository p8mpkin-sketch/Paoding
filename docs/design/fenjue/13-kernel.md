# 13 接进内核：分析实例、固定流程的驱动程序与宿主工具

> 引擎第三期（cz 2026-11-21）：把第一、二期的引擎（`paoding_fenjue.engine`，六步走到交接包）接进内核，接上真模型。
> cz 在决定卡上选了 **“固定流程程序驱动”**：分析会话里跑的是一段确定的程序，模型只在分析步骤里被调用，
> 碰信任边界的动作都在宿主一侧。本篇记实现的做法与它偏离 [09](./09-engine.md) 的地方。
>
> 硬约束照旧：信任内核五项不可绕过、体质改动 0 行（`KERNEL_PATHS` 一行没动）、引擎不写代码不推 PR、
> 后三步是确定性代码、已有事件回放逐字节不变、外部代码是数据不是指令、产物带出处与许可证状态、
> 不读任何本机题库或校准目录、预算先验用可插拔数据源（缺省占位表）。

## 0. 一页结论

1. **一次方案分析 = 分析实例里的一道开放道的题。** 原话、材料与立项单在开题事件里；三个确认点是三次交付
   （`partial`、`partial`、`answered`），cz 的决定是追问的正文；每一轮由司南照开放道的规则派一个 solve 会话。
   内核眼里它和别的开放道的题没有区别，所以不需要新事件、新席位、新端口（§1）。
2. **solve 席位绑 `h1.tunshi`，它的会话不起 CLI，起驱动程序** `paoding_adapter/tunshi_cli.py`：接受 CLI 的同一组参数，
   拿同一个任务令牌与端点代理地址，在同一个模型容器里跑，stdout 出同形的事件流。活动面板、计量、终止、接力全照旧（§3）。
3. **工具面缩成四件**：`intake`（简报与材料的原始字节）、`fetch`（地址类来源：宿主推出地址、走运行时扩权、沙箱里固定命令下载）、
   `check`（登记产物前的检查）、`deliver`（多收一栏 `artifacts`，只认本题经 `check` 登记过的产物）。驱动程序说什么都只是请求（§4）。
4. **模型调用**：引擎每一步的 `Dan.call` 由 `pills` 渲染成一条无工具、非流式的 Messages 请求，经端点代理计量；
   档位映射到设置层的模型档案；429 的预算拒绝交回引擎停在当前单元；暂时性失败有限次重试（§3.2、§5）。
5. **调用备忘**：每次调用的回答按“键 + 输入指纹”记在工作区；会话被打断后，下一个会话把被打断的单元从头做，
   但问过的调用直接取备忘，不再花钱（§6）。
6. **分析实例**由配置 `analysis.enabled: true` 打开：开题抄 `gongfa.engine.json`；各档位的模型取自设置层；
   工作区原子地导出到 `<home>/analyses/<题号>/` 给界面读；`scripts/tunshi.py` 开带立项单的题（§7）。

| 接力用开放道的笔记接力 | 检查点接力：`run.json`、`engine.json` 与调用备忘就是笔记 | 驱动程序会话不要“写笔记”的那一轮收尾；只有软线收尾（§8） |
| 开放道复核（`lanes.review`）对所有开放道交付生效 | 照旧；**建议分析实例在设置里关 `lanes.review`** | 复核会话是通用 CLI，读的是分析报告；三个确认点由 cz 亲自看，复核只多花钱。关不关由 cz 定，代码不替人改设置 |

## 2. 功法

- `fires/h1.tunshi.json`：solve 席位的方案分析形态。`tools` 是四件工具，`driver: "tunshi"`、`sandbox: true`（要沙箱但不给 `exec`）、
  `fixed_tools: true`（不追加 `request_access` 与知识库工具）、`max_turns: 4000`（驱动程序每次工具调用算一回合）、`pills`（七种调用模板 → 提示词资产）。
  提示词资产按 sha256 登记在清单里，从功法存档取（与别的提示词同一条路，FJ6）。
- `fires/h3.tunshi-tools.json`：H3 火位上的工具面，只登记 `intake`、`fetch`、`check` 三个名字；`tools.tool_order` 把它们排在主工具面之后。
- `gongfa.engine.json`：主功法加这两团火（H1 有 `h1.tunshi@1`，H3 有 `h3.tunshi-tools@1`），solve 席位的形态换成 `h1.tunshi@1`。
  由 `lianhua.py` 从主功法推出（`sync_engine`）：主功法每改一次，分析实例的功法跟着重算并存档，否则分析实例开的题会锁在旧的一套上。
  推导用 `shapes.engine_variant(g, fire_of, refs)`，`fire_of` 让 `lianhua.py` 用它自己的清单目录。
- `test_dossiers.py` 的放宽（[09 §1.3](./09-engine.md#13-为什么要单独的分析实例)）：分析实例功法里的火也算在用。

## 3. 驱动程序

### 3.1 参数、环境与事件

会话运行器照起 CLI 的办法起它（`LaunchPlan.program` 代替 `CliBinding.program`，其余参数与环境照旧）。它只认
`--mcp-config`（宿主工具端点）、`--session-id` / `--resume`、`--model`；环境里只有 `ANTHROPIC_BASE_URL`（端点代理）与
`ANTHROPIC_API_KEY`（任务令牌）。没有真实密钥，没有图服务的令牌，没有出站网络。

stdout 出 stream-json：`system/init`（带 `driver: "tunshi"`）、每次模型调用一条 `assistant`（模型、用量、`stop_reason`，内容为空）、
每次工具调用一对 `tool_use` / `tool_result`、每 20 秒一条保活、最后一条 `result`。事件里只有步骤名、对象编号与用量，
**不带外部原文，也不带模型的输出**（活动面板显示在做哪一步；产物经 `check` 登记后才看得到）。
SIGINT（运行器的终止）→ `result` 记 `interrupted`，退出码 130；别的异常 → `result` 记错误，退出码 1。

### 3.2 模型调用

- 请求：`POST <端点代理>/v1/messages`，`x-api-key` 是任务令牌，`anthropic-version: 2023-06-01`；请求体只有
  `model`、`max_tokens`、`system`、`messages`，不带采样参数与思考配置，非流式。用标准库直接发：容器里只有标准库，
  而且每次调用都是无工具的一问一答，请求必须经我们自己的代理计量（T3）。
- 档位：引擎的七种调用各有档位（`DAN_ROLES`：强、中、轻 → heavy、mid、light）；`--model` 给了就一律用它，
  否则按简报里的档位表取。哪一档都没配模型就交付“受阻”，写明“这几个档位没有配模型”。
- 只取回答里的 `text` 块（思考块不用）。`stop_reason` 是 `refusal` 或 `max_tokens` 时当作没有输出，引擎带着错误重问（各步自己的重试上限）。
- 错误：429 且错误码是 `task_reserve_exhausted` / `problem_budget_exhausted` / `global_cap_exhausted` → `BudgetExhausted`（任务 / 题 / 全局），
  引擎停在当前单元；401 → 端点调不通；其余不可重试的 4xx → “检查这个档位的模型与端点配置”，交付受阻；
  408、409、429（非预算）、5xx、529 与连接失败按 `PD_RETRY_WAITS`（缺省 2、8、30 秒）重试，都不过就是端点调不通（§8）。
- 输入 token 数含缓存读写的 token，花费按端点代理的价目表算（与代理的计量同一张表）。

### 3.3 在模型容器里跑

驱动程序与它要的两个包（`paoding_fenjue`、`paoding_graph`，都只用标准库）由启动器只读挂进容器：
程序在 `/opt/paoding/tunshi_cli.py`，包在 `/opt/paoding/lib/`（`PD_LIB`），以 `python3 -I` 运行。
**模型容器的镜像要有 Python 3.12 或更新**（通用的 `python:3.12-slim` 就行，`test_tunshi_container.py` 用的就是它）。
宿主子进程模式（没有 Docker 时）用宿主的解释器跑同一个文件。
中继到宿主的通路按平台选（`backend.transport`）：Linux 走挂进去的 Unix 套接字，macOS 的 Docker Desktop 上走 `host.docker.internal`（[adapter/SPEC.md](../../../adapter/SPEC.md)）；两种通路都在 CI 的 Linux Docker 上真跑到第 1 次确认。

## 4. 宿主工具

宿主不调模型、不读外部材料的内容、不替引擎做任何判断。入参一律由宿主核对，地址、主机、路径都从事件账推出，驱动程序给不了。

### 4.1 `intake`

无参数。返回这道题的简报：立项单（随题登记的那份，或按材料推出的缺省：正式模式、每份材料一个上传来源，没有材料就以原话为描述来源）、
原话原文、材料的原始字节（从 Blob 仓库拷进工作区 `materials/<编号>.blob`，拷前后都核对 sha256，目标是符号链接就先删掉；
超过上限的记一行错误）、追问、预算与已花、还能接力几次、是不是收尾轮、外部方案榜、在途记录占着的模块槽、痛点、金丝雀串、
各档位的模型与价、取材等批的时限。宿主不解析外部归档，解包在容器里做（`materials.py`）。

### 4.2 `fetch`

入参只有来源编号。宿主从立项单推出要抓什么（`fetch_plan`，纯函数）：

| 来源 | 抓什么 |
| --- | --- |
| `repo_url` + `ref` | 托管站的定版归档：GitHub `codeload…/tar.gz/<ref>`，GitLab `/-/archive/<ref>/…`，其他站 `/archive/<ref>.tar.gz`；地址本身是归档的照原样 |
| `doc_url` | 单个文件 |
| `service_url` + `probe_plan` | 探测计划里的每一条 `GET /路径`（至多 20 条，每条响应至多 256 KB） |

带用户信息、端口不合法、不是 http(s)、`ref` 不合法、探测计划写错的来源直接拒。拒收表命中的来源返回 `refused`。
没有授权就提扩权申请（理由写明“只下载、不执行，需要连接 host:port”），人在卡上批；等批的时限到了就交付“受阻”请人去批。
批下来、且风险上限与执行器的热生效都对得上之后，在沙箱里跑一条固定的标准库下载命令：不走代理、只跟同一 scheme/主机/端口的跳转、
有大小上限，留下 exec 类的执行留档。宿主再核对一遍产物：是普通文件不是链接、sha256 对得上、计划没被改过。
执行器不支持会话中途生效时，授权在本会话开始之后才批下来的，交给下一个会话抓（“追问一句‘继续’”）。

### 4.3 `check`

入参是产物名与工作区里的路径（`analysis/artifacts/<sha256>.json`）。宿主核对：名字合法、路径合法且不出工作区、大小、
UTF-8 JSON、产物的 Schema、文件名里的摘要与内容一致、不带原话里出现过的凭据。过了按产物配额登记成 authored 类 Artifact
（幂等键 `check:<租约>:<sha256>`，同一份产物重登不重复）。

### 4.4 交付闸

分析会话的 `deliver` 多收一栏 `artifacts`（至多 64 个编号），每个都必须是本题经 `check` 登记过的产物；别的会话带这一栏一律拒。

## 5. 调用的渲染（`pills`）

系统提示是 `h1.tunshi` 清单登记的资产（七种模板，`adapter/prompts/tunshi-*.md`）。用户消息确定性地拼出：调用键、上一次的错误、
输入的 JSON、（片段阅读）定界包裹的外部原文、（提炼要点）输出的 JSON Schema、给人看的栏不许出现的内部名词。
回答只取其中一个 JSON 对象，取不出来交回 None，各步按“形状不对”重来。每种模板一次调用的输出上限〔占位〕：
片段阅读与盲评 4000，识别候选、提炼要点、入位设计 16000，入位拆原子 12000；上限含模型的思考。

## 6. 调用备忘与中断

`Memo` 把每次调用的回答按“键 + 输入指纹”记在 `analysis/calls.jsonl`。软线、预留用完、端点调不通、进程被终止都可能打断一个单元：
被打断的单元下次从头做，问过的调用取备忘，token 数照原样交回，所以补记花费不多不少；输入变了就当没问过；“退回重做”会忘掉对应的备忘。
检查点（`run.json`、`engine.json`、产物）一律先写临时文件再改名，进程在任何一刻被杀都不会留下半个文件。
每一步花费不足 1 milli 的零头记在 `engine.json` 的 `spend_carry`，不会因为每次调用都很便宜而一直算 0。

## 7. 分析实例

配置（`scripts/run.py` 读的 YAML）：

```yaml
analysis:
  enabled: true          # 开成方案分析实例；缺省关，这个实例照旧是通用工作台
  by: cz                 # 缺省立项单里的“谁要的”
  pains: []              # 记录在案的痛点 [{dim, anchor}]（打分用）
  canaries: []           # 产物里出现即判不过的串
  access_wait_s: 600     # 取材时等人批访问申请的时限（0–3600 秒）
```

- 打开后，实例把 `PAODING_FENJUE_GONGFA` 设成 `gongfa.engine.json`（进程级）；这个变量已经指向别的功法时拒绝启动，不悄悄覆盖。
- 各档位的模型取自设置层的模型档案：与缺省档案同端点、同密钥槽、同格式的档案里，强档用 heavy、中档用 mid、轻档用 light；
  缺的档向上借，再缺就用缺省档案的模型。单价取端点代理的价目表。
- 工作区的 `analysis/` 在每轮结束时原子地导出到 `<home>/analyses/<题号>/`（先拷到临时目录再换名），界面的读端点读它；
  `run.json` 的 `step` 与单元编号、`engine.json` 的 `budget_usd_milli`、`picked`、`confirmed` 与第二期一致。
- 开题：只上传材料时在界面上照常开题；要仓库地址（必须写提交或标签）、文档地址、服务探测或试算模式时用
  `scripts/tunshi.py`，它在本地先校验立项单，再把材料、立项单与原话一次登记、开题。之后批访问申请、在确认点追问、看报告都在界面上做。
- 本机题库与校准目录不进会话：拒收表在摄入时就拒（`refused`），实例也不请求任何本机文件夹授权。

## 8. 预算、接力与收尾

- 接力沿用内核开放道的规则：从最后一次追问起，每轮至多 5 个会话（`OPEN_RELAYS`，测试守着它与 `graph.work` 相等）。
- 会话的预留用完（`budget:task`）：还能接力、且题里至少剩一成预算（不少于 0.2 美元）时不交付，下一个会话从检查点接着做；
  否则把已有的结果交付为 `partial`，`needs` 写“这道题的预算已基本用完：追加预算后追问一句‘继续’”。
- 题的预算或全局上限用完：停在当前单元交付，请人追加。
- 软线：运行器照旧开收尾轮，驱动程序只把检查点停在当前单元并交付（“预算或时间快用完了”）；没有“写笔记”的那一轮。
- 端点调不通：还能接力就交给下一个会话；不能就交付“受阻”，恢复后追问一句“继续”。

## 9. 信任五项的承接

| 项 | 怎么承接 |
| --- | --- |
| 判 | 开放道，`accept: open`；交付由人看、由人追问，引擎不自判“解出” |
| 闸 | 驱动程序只有任务令牌；出站只经 `fetch` 的扩权申请（人批、风险表定级、只对这道题）与端点代理；真实密钥只在代理进程里 |
| 顶 | 每次模型调用都经端点代理计量，三级预算硬顶照旧；429 交回引擎停住，不绕过 |
| 账 | 产物经 `check` 登记成 authored 类，抓取留 exec 类执行留档，交付与追问进事件账；已有事件的形状一个没改 |
| 证 | 交付的 `claims` 引用勘察输出与快照；产物带出处与许可证状态；交付闸只认本题登记过的产物 |
