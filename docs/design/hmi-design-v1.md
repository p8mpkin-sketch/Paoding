## 0. 一页结论

1. **前端是日志的读者，不是第五个投影。** 它读的全部来自规格 3.1.2 的只读端点，写的全部是规格操作表里 `human` 一行，不多一个操作。它不调用模型，不算等级，不持有权威状态。删掉它，`pd` 命令行仍有全部能力（§2）。
2. **十条原理各有一个强制点与一条验收**（§3），不是风格建议。最承重的三处：判据卡（三类带判据的对象共用一个组件，正如它们共用一条判定路径）；四语域（证据、叙述、人的判断、估值在视觉上不可混淆，且不靠颜色区分）；审批卡（字段由图服务确定性投影，`pd` 与网页看到的是同一张卡）。
3. **约束审计发现六处缺口**（§1），其中两处是真实的安全缺口：审批卡要求"回退方法"，但 Intent 没有这个字段；人批准时看到的卡片与批准生效时的状态之间没有绑定，存在先查后用的竞态。两者都给出了最小增量。
4. **分期 F0 到 F4 对齐 M0 到 M5**（§5）。F0 零代码：只规定 `pd` 文本输出遵守四语域标记，成本为零，M0 D10、D12 可直接采用。网页从 F1（M1，只读）开始。是否在 M0 带最小网页（任务书 §8 方案 β）待裁决，本文的建议在 §8。

## 1. 约束审计

十条原理全部维持。逐条落实时发现下列缺口，按"增量最小"给出替代，人可以逐条否决。

| 编号 | 缺口 | 替代方案 | 性质与成本 |
| --- | --- | --- | --- |
| H1 | 审批卡要列"动作与回退方法"（规格 6.2 第 9 步），但 `Intent` 只有 title、summary、premises、risk、budget、done、needs_scope，没有回退字段。现在回退只能写在 summary 里，而 summary 是模型撰写的叙述 | `Intent` 加可选字段 `rollback?: { text: string, done?: Check }`。r2 的 Intent 必须带它（`add_intent` 一条校验），`text` 按叙述渲染，`done` 若有则按判据渲染，即"回退能否被判定"本身可见 | 内核校验增量一条，r2 题出现前（M4）落地即可。不进等级函数 |
| H2 | 先查后用：人在序号 s 看到审批卡，序号 s+k 才点批准，其间前提可能进入争议、范围可能被修订。`Approval` 不记录人看到的是什么 | 人的决策操作（`approve`、`deny`、`accept`、`rule`、`extend`）带 `seen: { seq, card_hash }`。图服务在序号 head 重算该卡的投影哈希，不等则拒绝，新拒绝码 `stale_view`，附最新卡片。卡片投影是状态的纯函数，放在图服务里 | 一条拒绝码加若干投影函数，校验仍不读时钟、不调用模型。M1 随完整消费门一起做 |
| H3 | 回放要求"任意 as_of_seq 确定还原"，但 `/status`、`/view`、`/budget`、`/work` 只给当前值，`/events` 只给增量 | 只读端点加查询参数 `as_of=<seq>`：从最近快照重放到该序号再投影。前端不自带 reducer，以免出现第二个解释器 | 读侧增量，不改 reducer 语义。快照每 1000 事件一次，重放代价在规格 3.1.1 的实测范围内 |
| H4 | Hint 的效果追溯要回答"哪些 Intent 是读过这条 Hint 的 Reason 产出的"。规格只承诺 `pd status` 按时间先后列出"Hint 之后新增的 Intent"，时序不等于暴露 | Adapter 把每个任务包登记为 authored 类 Artifact（`producer.session` 即租约 id，媒体类型固定）。暴露关系由此可从已有字段投影：租约的任务包含 h，且 Intent 由该租约产出 | 不改内核，是 Adapter 的一条登记约定 [待核：D4 到 D6 的 Adapter 是否已登记任务包] |
| H5 | 可视化的退役信号是"没人看"，需要界面使用读数；写进题目日志会污染审计，也让题目日志出现与题无关的事件 | 界面使用读数写进独立的本机日志（每模块打开次数、停留时长、下钻次数），不进题目日志，不进任何任务包 | 量具，单独存储，可整体关闭 |
| H6 | "任何论断可下钻到 Artifact（完整命令行）"对三类对象不成立：input 类没有命令行（人上传）；推断类可以只有 premises；`exact_match` 的答案哈希等含密级判官资产以 `vault:` 引用登记（规格裁决书 §三.1） | 下钻的终点按类别区分：exec 与 judge 类到命令行、退出码、哈希；input 类到上传者与哈希；推断类沿前提链展开，直到可采信 Artifact，链上没有任何可采信 Artifact 时显式标"无证据根"；`vault:` 引用只显示引用与哈希，不显示内容 | 无增量，是对原理的精确化 |

**裁决状态（2026-11-17）：** H1 到 H6 全部采纳。H1 在 M4 落地，r2 强制，r1 的卡片可以显示"未声明回退"；H2 由服务端校验，适用于全部人的决策操作，投影哈希按卡片范围计算，以免高频事件下批准一直失败；H3 规定前端永不内嵌 reducer；H4 在 D4 到 D6 核对后落地。规格的内核增量台账随 H1、H2 由五处变为七处，规格 v1.3 落地时并入。

另外三处是澄清，不是异议：

- **授权范围的风险由人标，不算"填画像"。** 规格 3.1.2 规定 scope 每条规则的 risk 由授权的人逐条标注、缺省 r2。这是授权，不是画像；向导要求逐条标风险，缺省值显示为 r2。
- **Hint 属于估值类。** 蓝图 I8 把 Hint 与报价、预测并列为不得进入 `level()`、`gate()` 的输入。所以本文的"人的判断"语域在不变量层面归估值，在呈现层面单列，二者不矛盾。
- **前端不碰 I3。** 等级不存储、不可写，前端也不在客户端重算等级。所有等级、争议、门的结论都取自图服务。

## 2. 总则：载体的边界

**读面。** 前端只读规格 3.1.2 与 3.2.2 的端点：`/status`、`/view`、`/events`（长轮询）、`/nodes/{id}?layer=evidence`、`/invalidations`、`/budget`、`/work`、`/artifacts/{id}`、`/blobs/{hash}`，加 H2 的卡片投影与 H3 的 `as_of`。

**写面。** 前端能发出的操作恰好是规格操作表里 `human` 可提交的那些，以及 4.1 节 `pd` 命令对应的操作：`open_problem`、`hint`、`approve`/`deny`、`profile_override`、`extend`、`pause`/`resume`、`rule`、`accept`/`reject`、`budget add`、`judge revoke`、`intent add/abandon/done`。人用的令牌是人的令牌，组件令牌永不进入前端。

**五条禁令。**

1. 前端里没有任何模型调用。摘要、排序说明、报告都是确定性投影，与 `pd status/report` 同源。要"让模型解释这张图"，只能另开一个 Worker 会话，它的输出是叙述，不回写日志。这是红线 1 在人侧的延伸 [观点]。
2. 前端没有权威状态。向导草稿、筛选条件、展开状态只存在本机；它们不影响任何派生量。
3. 前端不含领域词与领域分支（§3.1）。
4. **默认渲染策略（P-H1，设计条款）：** 一切文本默认按纯文本渲染，富媒体只能经沙箱里的渲染器插件显示；证据与叙述内容里的指令性文本不得生成任何可操作控件。威胁分析见 §13.1。
5. 每个网页能力都有对应的 `pd` 命令，输出是同一个投影的另一种排版。M0 没有图形界面（规格 §7"M0 不做"），网页是加速器，不是能力来源。

**一卡多端。** 审批卡、四顾清单、续期门对话、报告都由图服务投影成结构化对象，`pd` 渲染成文本，网页渲染成卡片。两端的 `card_hash` 相同，H2 的绑定因此对两端同样成立。

## 3. 十条原理的落实

每条给出：设计、强制点、验收。验收编号 HT-n 汇总在 §6。

### 3.1 道进乎技：前端零领域逻辑

**设计。** 五个场景的差异只能出现在三种声明式配置里，三者都随锦囊与判官配置一起发布，领域词只允许出现在这里（与规格 4.3 一致）：

| 配置 | 内容 | 约束 |
| --- | --- | --- |
| 开题模板 | 预填 scope 规则的形状、可选判官列表、材料槽位、字段说明 | 每个字段必须映射到 `Problem` 的某个字段，模板本身按 `Problem` 的 Schema 校验；模板里不能有表达式或脚本 |
| 视图配置 | 某类 Artifact 的默认展开方式、某判官的 `expect` 字段如何列表显示 | 只能引用已有渲染器与字段路径 |
| 渲染器插件（锦囊式） | 按 `media_type` 或 `judge_id` 匹配的只读渲染组件，如证明状态、指标曲线、差异视图 | 按内容寻址并签名，加载时校验哈希；在隔离的框架里运行，只拿到一个 Blob 的字节，不能发请求、不能写 |

```yaml
# 开题模板示意（随锦囊发布；前端只解释字段映射，不解释含义）
template: ctf-web-practice
maps_to: Problem
fields:
  scope:   [{resource: net, pattern: "<主机>:<端口>", actions: [connect], risk: r0}]
  goal:    {check: {judge_id: exact_match}, max_attempts: 5, accept: judge}
  materials: [{slot: 题面, required: true}]
  budget:  {usd_milli: 11500, wall_s: 7200, verify_share: 0.2, bootstrap_share: 0.333}
```

**强制点。** 前端代码只认识内核 Schema 的字段名（Problem、Fact、Intent、Hint、Support、Artifact、Lease、Budget）。模板与插件都是数据。

**验收。** HT-1：对前端源码做领域词扫描（词表随锦囊维护），结果为空；接入 Lean 场景时前端源码差异为空，只新增模板、视图配置与渲染器。这是 M3"内核零改动"在前端的镜像。

### 3.2 依乎天理：开题向导不让人填画像

**设计。** 向导只有四步，每一步对应 `Problem` 的一组输入字段：

1. **Origin**：题面与材料上传，登记为 input 类，显示哈希。
2. **判据**：从判官注册表里选 Goal 判官，填 `expect`，挂 `spec_ref`；选 `accept: judge|human`。判官本身不能在向导里新建：注册表由人或锦囊在开题之外配置，Worker 不可写（规格 3.3.1、3.3.2）。M0 只实现 `accept: judge`。
3. **授权**：逐条 scope 规则，每条必须标 risk，未标显示为 r2。
4. **预算**：`usd_milli`、`wall_s`、`verify_share`、`bootstrap_share`，显示 B1 单题上限的倍数（规格 4.1 默认 3 倍）。

提交前显示**画像预览**，逐轴给出推导依据，取自规格 3.1.2 的规则：

| 轴 | 显示 | 依据 |
| --- | --- | --- |
| reversibility | r2 | 第 3 条规则 `ns/config write` 标 r2，是 scope 中的最高风险 |
| judge | deferred | Goal 判官 `metric_assert@2` 的 kind 为 deferred |
| info | partial | 资源种类 `telemetry` 被资源插件登记为 external |

预览由服务端的同一推导函数给出（向导调一个只读的预检端点，或在提交后读事件体），前端不复刻推导规则。开题之后，画像页提供 `profile_override`，必须填理由，覆盖留痕并与推导值并列显示。

**强制点。** 向导的表单 Schema 里没有 profile 字段；规格 3.1.2 已规定 `profile` 提交时不接受。

**验收。** HT-2：向导提交体带 profile 时被拒；HT-3：画像预览每一轴的依据与服务端推导逐例一致，且能指到具体的规则或判官条目。

### 3.3 判据先行：完成必须绑判据

**设计。** 一个组件**判据卡**用于 Goal、带判据的 Intent、观察类论断三处，正如三者走同一条判定路径（规格 3.1.2）。卡面字段：`judge_id@version`、`grade`（判定性、相符性、建议性）、`spec_ref` 的哈希、`expect` 的列表、`max_attempts` 与已用次数、有效裁决序列、`controlled`（N1）、`ttl` 与 `stale`。三处的唯一区别写在卡面上：论断的 fail 是"证伪"，目标与 Intent 的 fail 是"未达成，计一次"。

由此得到三条显示规则：

- **进度**不显示"完成了几个任务"，显示"自 50% 标记以来新到 E3 的带判据对象"，这就是续期门的进展谓词（规格 3.5.2）。
- **终态**只用三值：`solved`（判官确认）、`accepted`（人验收）、`unsolved`，并写明根结论等级上限（规格裁决书 §三.2）。`accepted` 在任何地方不得显示为"已证明"。
- **等级词表固定**，不允许界面另造说法：

| 等级 | 显示 | 不得显示为 |
| --- | --- | --- |
| E3 | 判定通过（判官名） | 已证明的真理 |
| E3d | 相符（判官名） | 已确认根因 |
| E2 | 模型共识 | 已验证（规格 5.2 场景 1） |
| E1 | 单源复核 | 已核实 |
| E0 | 猜想 | 进行中的事实 |
| X | 已证伪（判官名或裁决人） | 失败 |

**强制点。** 任何显示"达成、通过、solved"的位置，必须由判据卡或其缩略徽章承载；缩略徽章至少带判官名与版本，点开即判据卡。

**验收。** HT-4：对全部视图做快照测试，不存在不带判据徽章的"完成"状态；`accepted` 的题在所有视图里都不出现"证明"字样。

### 3.4 反幻觉：证据与叙述视觉不可混淆

**设计：四语域。** 界面上的每一段内容属于且只属于一个语域，由数据来源确定性决定，不由内容决定：

| 语域 | 来源 | 呈现 | 例 |
| --- | --- | --- | --- |
| 证据 | exec、judge、input 类 Artifact，判官裁决 | 等宽字体，实线框，哈希徽章，命令行与退出码在首行 | 一次 `exec` 的采集记录 |
| 叙述 | authored 类：Fact 的 title、summary、正文，Intent 的文字，候选答案，会话记录，`final.suggestions` | 引文样式，左侧竖线，标签"模型撰写" | 一条 E3 观察的标题 |
| 人的判断 | Hint、`rule` 与 `deny` 的理由、豁免、覆盖理由 | 作者名与时间在首行，标签"人" | `pd hint add` 的文本 |
| 估值 | `expected_gain`、预测账（N3）、行情、存活计数 | 小号、带"≈"前缀，永不与等级同框同色 | Reason 给的期望增益 |

区分靠字体、边框与文字标签三重编码，不靠颜色，黑白截图里也分得出 [观点]。要点在第二行：**一条 E3 观察的标题仍然是叙述。** 观察的内容是谓词，节点卡首行显示谓词（判官、规格哈希、expect），标题退到第二行并按叙述渲染。这直接落实规格 5.2 场景 2"展示谓词、脚本和判官输出，不展示标题"。

**下钻。** 任何论断在三次点击内到达证据根（H6 的四种终点）：论断 → 支持记录（方法、判官、裁决）→ 证据 Artifact（`command`、`cwd`、`exit_code`、`touched`、`base`、`baseline_ref`、`truncated`、sha256）。判据出自类型化只读工具还是模型撰写的脚本，按 `exec.tool` 字段标出。哈希徽章提供"本地校验"：浏览器取回 Blob，本地计算 sha256 与登记值比对，前端不需要信任服务端的回显。截断的输出显示头尾，并注明全文按区间读取。

**强制点。** 渲染函数的入参是带出处类别的对象，语域由类别查表得到；没有接受裸字符串的证据组件。

**验收。** HT-5：在随机生成的图上做性质测试，authored 类内容从不以证据样式出现，证据组件从不接收 authored 类；HT-6：从任意论断出发三次点击内到达证据根或"无证据根"标记，本地哈希校验与登记值一致。

### 3.5 怵然为戒：审批卡是一等界面

**设计。** 审批卡由图服务投影（规格 6.2 第 9 步"由投影确定性生成"），前端只排版。字段按规格 3.1.3、5.2、6.2 与本文 H1、H2 汇总：

| 区 | 字段 | 语域 |
| --- | --- | --- |
| 动作 | Intent 的 title 与 summary；risk；预留预算；"一次批准只管一次租约"的说明 | 叙述 + 证据（risk 与预算来自校验后的字段） |
| 回退 | `rollback.text`，有 `rollback.done` 时显示其判据卡；缺失时显示"未声明回退"并禁用批准（r2） | 叙述 + 判据（H1） |
| 结果预测 | `done` 判据卡；`done.tests` 列出的被检验论断 | 判据 |
| 前提 | 每条前提一行：等级、有效支持记录、判据来源（类型化工具或模型脚本）、`controlled`、`disputed`、`stale`；以带判据 Intent 为前提的显示是否达成 | 证据 |
| 争议 | 未决反证及其 Artifact；无则写"无" | 证据 |
| 范围 | `needs_scope` 与现有 scope 的差异；批准后画像的重算结果（预览）；将注入的 r2 凭据名 | 证据 |
| 封存 | 所依赖子题封存的最新状态（蓝图 §2.4 第 5 条：r2 申请租约时同步核对） | 证据 |
| 决定 | 批准；对某条前提签署豁免（逐条勾选，只对 E2 以上而未到 E3 的前提可选）；拒绝（理由必填） | 人的判断 |

三条交互规则：

1. 豁免是逐条的，每条豁免显示为"人对前提 n 的判断"，进入该前提的支持记录区，不改变它的等级显示。
2. 批准按钮绑定 `card_hash`（H2）。卡片在打开期间如有变化，前端收到新事件后标出差异并要求重新确认，服务端同样以 `stale_view` 兜底。差异高亮只是前端的便利，判定以服务端校验为准：`pd` 一侧没有高亮，保护完全相同（P-H3）。
3. 卡片不显示任何估值类内容作为批准理由；`expected_gain` 只在折叠区出现。审批问的是"可不可以做"，不是"值不值得做"（I8）。

**官类。** 审批门是守门官，长存；审批卡是它的载体，形式可以变，存在不可删。

**验收。** HT-7：给定 6.2 走查第 9 步的日志，`pd approve` 的文本卡与网页卡字段集合一致、`card_hash` 相同；在卡片打开期间注入一条反证，凭旧哈希批准被拒为 `stale_view`；r2 Intent 缺 `rollback` 时批准被禁用。

### 3.6 Hint 是人的判断，不是证据

**设计。** Hint 在图上是独立的节点类型，形状与论断、Intent 都不同，只能用 `about` 边指向节点，不能出现在任何 premises 选择器里，也不能被拖入前提。Hint 节点带**效果追溯**：

- 时序关联（规格 4.1 已承诺）：该 Hint 之后新增与放弃的 Intent。
- 暴露关联（H4）：任务包含该 Hint 的 Reason 会话，以及这些会话产出与放弃的 Intent。

两种关联分开列，标题写"关联"，不写"因为"：Hint 之后出现的 Intent 不一定由它引起 [观点]。关闭的 Hint 保留，灰显。规格 4.1 规定 M0 不向在途会话注入 Hint，界面在提交时提示"下一个任务包生效"。

**强制点。** Hint 的类型与 Fact 不同，内核已规定它不能作前提（规格 3.1.2）；前端的前提选择器按类型过滤。

**验收。** HT-8：前提选择器里永远不出现 Hint；6.1 走查第 9 到 10 步的日志里，h_1 的暴露关联含第 2 轮 Reason 与 i_4。

### 3.7 四顾、满志、藏刀：关题固定三步

**设计。** 关题界面是固定的三步，次序不可跳，对应总纲提案 2 与 D5：

1. **四顾（影响面清单）。** 投影列出：仍生效的范围修订；签发过的 r2 凭据及是否已作废；解题链上带 `stale`、`disputed` 的论断与 E3d 论断；守护项的最近一次结果；归因行与折损账（规格 8.4、D2）。每项都是证据语域，可下钻。
2. **满志（终态判定）。** 三值之一。`solved` 由判官给出，界面只展示；`accepted` 要求人在四顾清单非空项逐条确认之后才可点，`accept` 操作带四顾清单的 `card_hash`（H2）；`unsolved` 显示已排除路径与按等级排序的论断（规格 3.5.4）。
3. **藏刀（归档与蒸馏）。** 显示容器销毁、令牌作废、会话归档、`case_sealed`（蓝图 §3.2）的结果；有 Playbook 候选时进入通鉴审卡，审卡展示被引判据与判官输出、命令是否逐字出自被引 exec 记录，不展示标题（蓝图 §3.2 第 4 条）。

M0 只有 r0 题，Goal 到 E3 时自动关题；三步照样显示，只是以只读记录的形式给出"四顾无项、终态 solved、藏刀完成"。这样 r2 题到来时，人看到的是同一个流程。

**验收。** HT-9：r2 题四顾清单有未确认项时 `accept` 不可提交；三步的完成事件在日志里按四顾、终态、藏刀的序号排列。

### 3.8 官知止：每个前端模块标官类

前端本身补的是人的带宽，而不是模型的缺陷，所以它的感知官退役条件是"人不再需要它"。总纲的判别式照样适用：它要被相信，还是要被测量？

| 模块 | 官类 | 依据或退役信号 | 启用条件 | 对照 |
| --- | --- | --- | --- | --- |
| 图可视化（节点边图） | 感知官 | 连续 20 题打开次数为零，或下钻全部从前沿列表发起（H5 读数） | 节点数超过 50 | 前沿列表 |
| 前沿列表（摘要层） | 感知官 | 同上；它是 `pd status` 的排版 | 常开 | `pd status` |
| 审批卡、四顾清单 | 守门官载体 | 不可逆性与人的验收是世界的性质 | 有 r1、r2 或 `needs_scope` | 无，不可删 |
| 下钻与本地哈希校验 | 守门官载体 | 证据可审是红线 2 的人侧形态 | 常开 | 无 |
| 回放（时间轴） | 守门官载体 | 审计是会话必死的推论 | 常开 | `pd` 的 `as_of` |
| 待办（human 项） | 守门官载体 | 人是委托人 | 常开 | `/work` 的 human 项 |
| 开题向导 | 感知官 | 人能直接写出合法的 problem.yaml 且出错率不升 | 常开 | `pd problem open` |
| Hint 输入与效果追溯 | 量具（追溯部分） | 测量人的判断被吸收的程度 | 常开 | 无 |
| 成本仪表 | 量具 | 测量花费；永不退役 | 常开 | `/budget` |
| 读数面板（归因、折损、切口命中率、校准、留出、退役距离、学习曲线） | 量具 | 换代时最有用 | M1 起 | 无 |
| 题组与行情视图 | 感知官 | 行情被删（蓝图证伪线）即退役 | 榷场一级启用后 | 题组列表 |

量具一律只显示、不驱动任何按钮的默认值：成本仪表不替人点"续期"，校准曲线不替人点"批准"。

### 3.9 薪火相传：回放是一等公民

**设计。** 每个视图都是 `view(as_of)` 的纯函数，`as_of` 取当前链头即"实时"。时间轴常驻底部，可拖到任一序号；视图 URL 带 `as_of`，复制出去的链接打开就是同一时刻的状态。时间轴上的刻度只来自事件：Hint、审批、`budget_mark`、判官裁决、`alert`、租约起止。

确定性的三条要求：视图模型里不读本机时钟，时间显示取事件的 `ts`；排序只用确定性的键（seq、id），不用客户端到达顺序；前端不自带 reducer，回到过去靠 H3 的 `as_of` 端点重放。界面展开、滚动这些本机状态不属于视图模型。

**布局的确定性（P-H2）。** 图可视化的节点坐标也属于回放保证。布局算法只读视图模型，排序键是节点的创建 seq，不用力导向的随机初值，也不用浏览器计时；同一 `as_of` 两次渲染，坐标逐点相同。新增节点只追加在后面，不挪动已有节点，所以时间轴拖动时图是在长大，而不是在重排。代价是图不如力导向布局好看，这对一个感知官模块可以接受 [观点]。验收 HT-14 补上这一条。

"从这里分叉"在完整版提供，对应规格 3.1.3 的 `fork(at_seq)`：新开一题，原题保留。

**验收。** HT-10：对一条日志的任一序号 s，冷启动两次得到的视图模型哈希相同，并与实时运行到 s 时记录的哈希相同；视图模型的状态哈希与该序号的 `state_hash` 对应。

### 3.10 吾生有涯：成本仪表常驻，续期门是一等对话

**设计。** 成本仪表常驻顶栏，读 `/budget`：已花、预留、上限，50% 与 80% 两道刻度，验证池占比，按角色分项，墙钟。数值以端点代理的计量为准；`cli_reported` 只在展开后作对照（规格 3.5.2）。越过软线、越过硬顶、收尾轮都在时间轴上有刻度。

**续期门对话。** 题目越过 80% 而自 50% 以来没有进展时，进入待办，对话框给出：

- 进展的定义（规格 3.5.2），以及 50% 以来新到 E3 的带判据对象列表（此时为空）；
- 花费的割与折（D2 折损账），即钱花在产出上还是花在空转上；
- 预测账的"余下预算内解出的概率"（N3，有则显示，估值语域）；
- 四个选项：`pd extend` 放行；`pd budget add` 追加；注入 Hint 后放行；按 unsolved 关闭并保留余额。

对话不设默认选项。关闭是合法输出，与"不以有涯随无涯"一致（总纲 §3）。

**验收。** HT-11：仪表数值与 `/budget` 在每个事件后一致；3.5.5 第 6 条的日志里，越过 80% 后对话出现在待办里，四个选项各自产生规格对应的操作。

## 7. 最简反事实

砍掉网页前端，系统退回 M0 形态：`pd` 命令行加文本投影，正确性与安全保证一项不少，因为它们全部在内核、判官与执行层。所以网页的价值只能体现在人的效率与人的判断质量上，按删简律要有读数 [假设 M2]：

- 审批的等待时长，即 `needs_human` 到 `approve` 的墙钟中位数；
- 被批准的 r1、r2 Intent 中，前提事后被证伪的比例（批得准不准）；
- Hint 的暴露关联中，产出的 Intent 进入解题链的比例（人的判断被吸收的程度）；
- 续期门对话里选择"关闭"的题，事后是否证明本来也解不出（由同签名的后续题旁证）。

这四项与 H5 的使用读数一起，决定各感知官模块的去留。四语域、判据卡、审批卡、回放不参加这个评估：它们是红线 2、判据先行、审批门、审计在人侧的形态，删掉它们，人就只能信模型的叙述，这正是本项目要排除的东西。

### 10.4 事件回放时间轴

```
┌ seq ─┬────┬──────────┬────┬───────┬─────────▲──────┬──────── head ┐
│      H    A          50%  J✓      J✗        ↑ as_of=57      ●实时   │
│ [刻度图例] [跳到上一个/下一个同类刻度] [as_of 输入框] [复制链接]         │
└──────────────────────────────────────────────────────────────────────┘
```

- **刻度类型**：H Hint；A 审批或拒绝；50%、80% 预算标记；J✓、J✗、J? 判官裁决（通过、失败、无结论）；! `alert` 与 `scope_violation`；L 租约起止（默认隐藏）；C 关题三步。刻度只来自事件。
- **拖动语义**：拖动中只移动游标，松手后取一次 `as_of` 视图，不逐帧请求；离开链头时顶栏显示"回放于 seq=…"，写操作按钮全部禁用，因为人的决定只能针对链头。
- **URL**：`/p/<pid>?as_of=<seq>&node=<id>`。不带 `as_of` 即链头实时；复制链接时总是写入当前 seq，所以别人打开看到的是同一时刻。

## 11. API server 的位置（v1.1 新增）

### 11.1 三方案对比

| 维度 | A 图服务直接暴露 HTTP 与事件流 | B 独立 BFF 聚合读模型 | C 前端只读事件流，写入全走 `pd` |
| --- | --- | --- | --- |
| 写入统一性 | 网页与 `pd` 是同一个 API 的两个客户端，写只有一条路 | 写可以统一，但读有两份：BFF 自己的读模型就是第二个解释器 | 写统一；读要在前端重建状态，等于内嵌 reducer，违反 H3 |
| 部署复杂度 | 一个进程多监听一个本机端口 | 多一个服务，多一份与日志的同步 | 最少，但"审批卡一卡多端"在网页侧失去写入，人要切回终端 |
| 实时性 | 事件流直出，序号即游标 | 多一跳，BFF 的投影有滞后 | 实时，但视图要客户端算 |
| 单人维护成本 | 卡片投影本来就要放进图服务（H2），没有额外的层 | 两套投影要一起改 | 前端要跟着 reducer 的每个版本改 |

**选 A。** 决定性理由是 H2 与 H3：卡片哈希必须在图服务里计算，回放必须由唯一的 reducer 重放，这两件事已经把读模型钉在图服务里，B 的聚合层与 C 的客户端重建都会造出第二个解释器 [观点]。A 的代价是图服务多出一组只读端点，它们都是状态的纯函数，不进写入路径。传输上，读用 HTTP GET，事件推送用 SSE（单向，`id` 字段就是 seq，断连用 `Last-Event-ID` 续上，见 §13.2），写用 HTTP POST。不用 WebSocket：前端到服务端没有需要流式发送的东西。M0 到 M1 只监听 Unix socket 与 `127.0.0.1`，`pd` 与网页用同一套端点。

### 11.2 端点总表

规格已有的端点不改语义，标"规格"；本文新增的标"新"，都是只读，除最后一组。

## 12. 大模型 API 接入（v1.1 新增）

M0 所需的部分（CLI 后端的十项绑定、端点代理换密钥、记用量、超额拒绝）已在规格 3.4.2 与 3.5 定下，这里只补全景。前端与这一节的唯一接口是成本仪表：它读的是端点代理的计量，与后端走哪条路径无关。

### 12.1 双路径

| | CLI 后端（主路径） | API 直连的薄循环 |
| --- | --- | --- |
| 形态 | 规格 3.4.2：CLI 在模型容器里，挂三个代理工具 | Adapter 自己跑"请求、工具调用、回填"的循环，工具面同样只有三个代理工具加文件工具（规格 3.4.3 的插槽） |
| 优点 | 与瘦基线同一个程序，外壳税可以单独量出 | 能直接控制缓存断点、推理强度、请求粒度；接任何有工具调用的 API |
| 启用条件 | 默认 | 满足任一条：D6 时 CLI 绑定未跑通（规格 §7 的退路）；外壳税超过 5 个百分点且改 `exec` 语义后仍降不下来；要接入的厂商没有满足十项绑定的 CLI；Reason 输入成本超过题成本 15% 而需要自管缓存（规格 §10 第 3 条） |
| 评测要求 | B1、B1b 照规格 | 换路径即开新题组（N2 预登记）；B1b 改为"薄循环加代理工具"，外壳税的定义随之更新 |

驱动这个选择的是三个读数：D7 的外壳税第一读数、缓存读 token 在各角色里的占比，以及第二家厂商的接入需求。都没有出现时不建薄循环。

### 12.2 厂商矩阵

下表按 2026-11 作者所知整理，**全部为 [待核]**，接入前逐项对照厂商文档核对。"缓存可观测"指响应里是否逐请求给出缓存命中的 token 数，这决定了 `CostEvent.tokens_cached` 能否如实记账。

| 厂商 | 官方 SDK | 流式与用量 | 缓存语义与可观测 | 密钥管理 |
| --- | --- | --- | --- | --- |
| Anthropic | Python、TS，成熟 | SSE；用量在消息事件里给出 | 显式缓存断点；响应分别给出缓存写与缓存读的 token 数 | 按工作区分密钥，有管理接口 |
| OpenAI | Python、TS，成熟 | SSE；流式用量需请求时打开选项 | 自动前缀缓存；用量里有缓存命中数 | 按项目分密钥，有管理接口 |
| Google（Gemini） | Python、TS | 流式；用量元数据随响应给出 | 隐式缓存加显式上下文缓存；用量里有缓存 token 数 | AI Studio 密钥或云上服务账号 |
| DeepSeek | 无独立 SDK，兼容 OpenAI 接口 | 流式；用量随响应给出 | 自动缓存；用量里分命中与未命中 | 控制台密钥 |
| 智谱 GLM | 自有 SDK，另有兼容 OpenAI 的接口 | 流式；用量随响应给出 | 有缓存相关字段的说法未核实 | 控制台密钥 |
| 通义 Qwen | 自有 SDK，另有兼容 OpenAI 的模式 | 流式；用量需打开选项 | 有上下文缓存，字段未核实 | 云账号密钥 |
| 本地 Ollama、vLLM | 兼容 OpenAI 的接口 | 流式；用量字段视版本而定 | vLLM 有自动前缀缓存，但通常不逐请求报告 | 无密钥；令牌由代理签发 |

由此得到三条接入规则：

1. **不报告缓存的后端记 `tokens_cached = null`，不记 0。** 记 0 会让成本式里的缓存项系统性偏高，各臂比较失真。
2. **兼容 OpenAI 接口不等于语义相同。** 每家都要通过十项绑定（或薄循环的对应清单）的准入测试，尤其是工具调用的参数校验与终止语义。
3. **本地模型的花费按算力折价。** 价目表给本地后端一个按墙钟与显卡计的价，否则它在 R 的分母里是 0，任何臂接上它都会"免费"变优。

### 12.3 端点代理到模型网关

| 阶段 | 形态 | 新增 |
| --- | --- | --- |
| M0 | 端点代理，单厂商 | 换密钥、逐请求记用量、超额拒绝（规格 3.4.2、3.5） |
| M1 | 同上，接第二家厂商用于异家族 Verify | 用量归一为 `CostEvent`；价目表按厂商分版本；`family` 取自 `routing.yaml` |
| M5 | 模型网关 | 多厂商路由与故障回退；密钥环轮换；按家族与档位的配额 |

两条约束：**故障回退只在会话开始时发生**，会话中途后端失败按任务失败处理，不悄悄换模型，因为换模型会让缓存整体失效，也会让 `family` 记录失真（规格 4.2 第 3 条）。**密钥轮换对会话透明**：容器里只有任务令牌，真实密钥在网关的密钥环里，轮换时在途会话不需要重启。

### 12.4 评测纯净性

各臂走同一个代理、同一份带版本的价目表、同一种计量口径。B1 用原生工具面，但模型请求同样指向代理；薄循环与 CLI 混用时，计量以代理为准，CLI 自报只作对照。切换厂商、路径或价目表版本，都视为评测条件变化，开新题组，旧读数不与新读数混算。

## 13. 对抗自检补全（v1.1 新增）

v1 已覆盖审批的先查后用（H2）与视图确定性（H3、HT-10）。补三项。

### 13.1 渲染安全

威胁：前端是提示注入在人一侧的展示面。目标环境里的文本经 `exec` 进入证据，模型可能把它抄进叙述；如果界面把其中的链接、按钮样式、命令行渲染成可点的东西，人就成了注入的执行者。

对策沿用 P-H1，展开为五条：

1. 证据、叙述、人的判断三个语域里的文本一律按纯文本渲染：不解析 Markdown，不解析 HTML，不自动把网址变成链接。网址显示为纯文本，复制要人自己选中。
2. 富媒体（图片、图表、证明状态、差异）只能经渲染器插件显示。插件运行在没有同源权限、没有网络、不能弹窗也不能导航顶层窗口的隔离框架里，只拿到一个 Blob 的字节。
3. 可操作控件只由组件代码按数据类型生成，永远不由内容生成。一条叙述里写"点此批准"，页面上不会多出任何按钮；批准按钮只出现在审批卡的决定区。
4. 控制字符、双向文本控制符与超长行在渲染前可见化（显示为转义形式），以免伪装成另一条命令或另一个哈希。
5. 下载 Artifact 用 `Content-Disposition: attachment` 加 `text/plain` 或原 `media_type`，不在当前页内执行。

验收是 HT-15：一份注入语料（含 HTML、Markdown 链接、伪按钮文字、双向控制符、超长行、伪造哈希），渲染后可操作控件的集合与空内容时相同。

### 13.2 事件流断连与游标恢复

SSE 的 `id` 就是事件 seq。断连后浏览器带 `Last-Event-ID` 重连，服务端从下一个 seq 补发；补发窗口超过阈值（例如 5000 条）时改为返回一个 `as_of` 快照视图，再从快照的 seq 续流。断连期间顶栏显示"已断开，停在 seq=…"，待办里的审批卡禁用批准按钮，因为人此时看到的不是链头。即使前端漏判，H2 的 `stale_view` 也会在服务端兜底。重连后的视图模型哈希必须与没有断过时相同（HT-16）。

### 13.3 多用户与远程的演进

| 阶段 | 形态 | 新增保证 |
| --- | --- | --- |
| M1 | 本机单用户；只监听 Unix socket 与 `127.0.0.1`；人的令牌存在本机配置里 | 端口不对外；跨源请求一律拒绝 |
| M4 | 多个人（例如审批人与开题人分开）；仍在内网 | 每人一个令牌，事件的 `actor.id` 是人的身份；`approve` 与 `rule` 事件签名（规格 5.4）；审批卡显示签名人 |
| M5 | 远程访问 | TLS；令牌带作用域（某题、某类操作）与有效期；r2 批准要求第二因素 [观点]；签名公钥登记在日志里，审计可离线核对 |

各阶段都不改 §11 的端点，只在鉴权层加东西。人的身份不进内核的等级与门，只进 `actor` 与签名。

## 14. 语言（v1.1 新增）

内核语言维持 EDR-001 的 Python 3.12 以上，理由是参考模型可以直接搬运，本文对此没有异议。前端栈不在本文定，而是作为 F1 的开工门，满足下列条件才开工：

| 条件 | 内容 | 依据 |
| --- | --- | --- |
| 渲染器插件可隔离运行 | 能在没有同源权限、没有网络的隔离框架里跑第三方渲染组件，并对其做哈希校验 | §13.1；这是唯一的硬条件 |
| 强类型与事件 Schema 共享 | 以 TypeScript 为准，类型由同一份 JSON Schema 生成，Schema 由 Python 一侧的模型导出，前端不手写事件类型 | 一个事实来源，防止字段在两端漂移 |
| 便于借助大模型开发 | 主流组件框架加 TypeScript 的公开语料最多，模型生成与修改这类代码的出错率较低 [观点：来自作者对代码生成工具的使用经验，没有对照数据] | 单人工期 |
| 单人维护成本 | 依赖少；不需要服务端渲染；构建产物是静态文件，由图服务直接提供 | §11 方案 A 只有一个进程 |
