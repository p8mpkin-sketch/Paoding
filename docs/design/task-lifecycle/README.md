## 0. 一页结论

1. **工作台从此只有一张图。** 一件任务从“人想要它被完成”到“结果被验收”，固定经过十二站（S0 到 S11，[01](./01-journey-map.md)）。今天已有的每个页面和组件都钉在某一站上：今日与待办是 S7–S8 的观察面，四步向导是 S4 的高级编辑，任务库是 S10 的索引，读数页是 S11 的量具，实时工作区横跨 S6–S8。以后任何新需求都写成“修订地图”的 PR（§3 的修订规程），先改图，再改代码。
2. **每站只有一个责任方**：人、系统（确定性代码）、智能体（模型）。智能体只出现在三站：S2 起草、S6 执行、S11 沉淀里的复盘起草。凡是让一个量成为事实的站（S3 校验、S5 登记、S7 判定、S9 关题），责任方都是系统，并且路径上没有模型。这是“写路径无模型”和“判官独立”在产品层的落点。
3. **两类任务、两条默认路径**（[02](./02-default-paths.md)）。有标准答案的（练习、评测）走 **A 道：零确认**，系统校验全部过关就直接开题，人第一次出现是在结果页；没有标准答案的（自由任务）走 **B 道：一步确认**，确认卡上一次看完目标、验收清单、授权和预算。两条道都有同一组**不可省略的人的点位**：扩权、r2 每次执行、续期门、B 道的验收。
4. **设置分两层，任务级只许收窄**（[03](./03-settings.md)）。模型档案、端点、密钥槽、全局硬顶、练习预算上限、预算先验源都在全局设置页。任务只能在全局之内选：预算不超硬顶，模型只能从已登记的档案里挑，授权只能比草案更窄。密钥按“人的令牌”同级管理：只活在端点代理进程的内存里，不进配置文件、不进日志与事件、不进任何导出物，并有一条金丝雀测试来证明。
5. **缺口清单**（[04](./04-gaps-roadmap.md)）共 49 个位置：完整 27、部分 15、无 7（2026-11-19 按 main 重核；v0.4 加运行时扩权 Q29，内核一半已在 #93）。入口与设置层已基本落地（#87、#88、#89）；最大的洞是 B 道的终点（内核只接受 `accept: judge`，没有标准答案的任务今天开不了）和运行时扩权（Q29）。分期建议四步：L1 入口与设置层 → L2 无答案路径与验收 → L3 人的点位补齐（续期门、扩权卡、任务级模型偏好）→ L4 沉淀与并行，跟在 M2 的既定排序后面，不插队到 M1 的 G1 读数之前。
6. **每项功能都有一条人能自己判断的验收标准**（[05](./05-acceptance.md)），写法是“人做什么、看到什么才算做好”，并对上一条自动化测试。
7. **关键页面交互稿**（[06](./06-frontend.md)，截图在 `wireframes/`）延续第四版的纸、墨、朱印、界栏和编号：地图总览、设置·模型与密钥、设置·预算与先验、一步确认卡、验收三步、工作区站位条。
8. **外部组件只在图外对接**（[01 §4](./01-journey-map.md#4-外部组件站位)）：题库服务与评测台不是站，它们只经命名的端口接到 S0、S1、S5、S11，不另画第二张图。

## 1. 硬约束与它们在图上的落点

不可破的约束逐条对到站。任何一次修订地图，若让下表某一格变空，即视为破约束，PR 不收。

| 约束 | 含义 | 落点（站） | 强制机制（已有或待建） |
| --- | --- | --- | --- |
| 判官独立 | 是否做成由判官或人裁，不由干活的智能体自报 | S7、S9、S10 | 判官运行器在洁净容器里重放（规格 3.3）；B 道终态最多 `accepted`，不呈现为“已证明” |
| 判据先行 | 怎样算做完，在动手前登记，之后不可改（I4） | S3、S5 | Goal `check` 随 `open_problem` 写入；B 道的验收清单也在开题时登记（[02 §3](./02-default-paths.md#3-b-道自由任务一步确认)） |
| 写路径无模型（I1、红线 1） | 让一个量成为事件的路径上没有模型 | S3、S5、S7、S9 | 草案不是事件；草案校验器与 `validate` 都是纯函数；起草模型的输出只能经人或 A 道的放行规则交给 `open_problem` |
| 最小权限（I5） | 能力 ≤ Intent 风险 ≤ 授权范围 | S2、S3、S6、S8 | 开题零出站，扩权只经人或确定性白名单（运行时扩权，[runtime-grants](../runtime-grants/README.md)）；`touches` 只许收窄；执行层只编译校验过、未撤销的集合 |
| 预算硬顶（I6） | 硬顶在容器之外执行 | S0、S3、S6 | 全局硬顶由设置层给出、端点代理执行；任务预算在校验时夹在硬顶之内 |
| 八不变量 | 规格 2.2 的 I1–I8 | 各站，见 [01 §2](./01-journey-map.md#2-八不变量逐站核对) | 规格里的强制点不动；本文不新增绕过它们的路径 |
| 智能体不得自行扩大授权 | 智能体只能申请，不能给自己批 | S6、S8 | `needs_scope` 使 Intent 进入 `needs_human`；放行由 `gate()` 这一确定性闸门执行，批准只来自人的令牌 |
| 视觉语言延续第四版 | 纸、墨、朱印只标“需要你”，界栏、编号、刻度 | 全部页面 | [06](./06-frontend.md) 的交互稿只用 v4 的 `kit.css` 与 `screens.css` 已有的类 |

## 3. 修订规程：新需求等于修订地图

1. **先定位。** 新需求必须先回答“它在哪一站，或者它是不是一个新站”。回答不出来的需求不进实现，先在本目录开修订 PR。
2. **一张表改到底。** 修订 PR 同时改三处：[01](./01-journey-map.md) 的站表（责任方、组件），[04](./04-gaps-roadmap.md) 的缺口行（状态和分期），[05](./05-acceptance.md) 的验收行。三处的编号必须一致（站号 S#、缺口号 Q#、已有位置号 K#、验收号 AC#）。
3. **过约束表。** 修订后的图对 §1 的每一行仍有落点；新增的智能体站必须写明“它的产出在哪一站被确定性代码接住”。
4. **官的声明。** 新结构按规格 2.3 回答四问（哪类官、退役信号或长存依据、启用条件、对照臂）。
5. **版本。** 本文版本号随每次修订加一位小版本，附录记修订人与裁决。实现 PR 在描述里引用它落地的缺口号。

### 5.1 附加条件

1. **D3 附加。** 验收清单 `goal.acceptance[]` 的条目来源与一句话开题同规则：只能是原文区间指认或人写，模型不得起草清单内容。终态 `accepted` 只经 B 道（`accept: human` 的题）产生，A 道与 B1 不出现 accepted。统计与读数永远把 accepted 与 solved 分开呈现，不合并成“完成数”或“成功率”的同一个分子。落点：[02 §3.3](./02-default-paths.md#33-验收清单b2-的判据先行)、[05 AC10.3、AC-M6](./05-acceptance.md)。
2. **D4 附加。** 设置页的密钥一节明示“密钥重启后失效，可用环境变量持久注入”。金丝雀测试（密钥不进日志、事件、导出物）纳入**每一期**的验收标准，不只是 L1。落点：[03 §4.2](./03-settings.md#42-注入的两条路)、[05 AC-M5](./05-acceptance.md)、交互稿 `set-models`。
3. **D1 附加。** 地图补一节“外部组件站位”，写明题库服务与评测台在图外的对接关系（练习题来源、对照读数来源），避免出现第二张图。落点：[01 §4](./01-journey-map.md#4-外部组件站位)。
