## 0. 一页结论

1. **批评成立，而且问题不止一处。** 庖丁把“先登记怎么算做完”当成了执行的前提。这个前提适合考试，不适合干活：真实任务里，人不知道答案才来问。问题分三层，只开门不够（§1）：
   - 入口拒题：没有答案键或检查命令就不许创建；
   - 执行形态按“交卷”设计：提示词告诉智能体“找到正确答案交给判官比对”，并把一次求解切成三种互相隔离的小会话；
   - 终态只认“判官判过”或“人按清单验过”，其余一律记“未解决”。
2. **原则从“判据先行”改成“证据随行”。** 开始干活不需要判据；交付结论时必须带上证据、自检和没验证的部分。验证从“入口的门”变成“结果的附件”，从必须变成按需。
3. **默认道改为开放道。** 一句话进来就执行：不要答案、不要检查命令、不要验收清单、不出确认卡。智能体自己规划、自己决定何时交付。人看结果，可以追问、采纳、不采纳，或者什么都不做。
4. **严格道降为可选。** 现有的判官判定（答案键、检查命令、外部平台回执）原样保留，只在人明确选择时启用：练习、评测、平台导入。它的用途是度量智能体，不是使用智能体。
5. **开放道不冒充“已解决”。** 新终态“已交付”（`delivered`），读数单列，不进解出率。系统对开放道结果只承诺三件事：这是智能体的答案；这些是它实际执行并留档的证据；这些是它没有验证的部分。
6. **庖丁留下来的东西照常生效**：事件账、预算硬顶、开题零出站与扩权审批、密钥隔离、闸门唯一出站点。这些是开放道比“先干后看”类工具多出来的部分，也是唯一值得保留的差异。
7. **最小可用第一步**（§11）：内核认 `accept: open` 与“交付”操作，开题校验把拒绝改成开放道，新增单会话的求解角色。完成后，今天被拒的那句提示词能从输入走到一份带证据的答案。

## 1. 现状：三层都假设“答案已知”

### 1.1 入口

`qicao/vet.py` 的判据推导只有四条出路：外部平台、答案键、检查命令、验收清单。四条都不成立时写 `no_criterion` 并拒绝（第 225 行），就是 cz 看到的那句话。内核同样把关：`open_problem` 要求 `goal.check` 指向一个已注册的判官，`goal.accept` 只取 `judge` 或 `human`，`human` 还必须带非空的验收清单。

这几轮做的外部裁决（#94）和人工验收（#103、#104）都是在这道门上加出路，门本身没动：默认仍然是拒绝，人工验收也要求先写清单。

### 1.2 执行

即使把门打开，现在的执行形态也做不好开放任务。

- 公共提示词（`adapter/prompts/common.md`）写的是：“最终目标：找到正确答案并用 claim_done 提交给判官验证。这是系统判断‘已解决’的唯一标准。”没有判官的任务，这句话让智能体无所适从。
- 一次求解被切成 bootstrap、reason、explore 三种会话。reason 不能执行命令，只能写 Intent 等 explore 认领；explore 一次只做一个 Intent。会话之间只靠图里的论断传递信息，而观察类论断必须带判官重放条件和证据引用。
- 这套切法来自攻防竞赛的黑板架构，前提是题多、可并行、有 flag 可验。对“调研三个框架写份对比”这类任务，它把一个连贯的思考过程打碎了，每一段都要重新读图建立上下文，还要为每个中间发现写出可重放的判据。

zcode 这类工具效果好，核心原因不是模型更强，而是它们让一个会话带着全部工具和完整上下文一直做到完。庖丁的会话底层用的是同一类命令行智能体，但只给了它三个代理工具和一个被切碎的任务。

### 1.3 终态

终态只有三个值：`solved`（判官判到 E3）、`accepted`（人按清单逐条验过）、`unsolved`。一个没有判官、没有清单的任务，无论做得多好，只能记 `unsolved`。统计上它拉低解出率，界面上它显示“未解决”。

### 1.4 根因

设计之初把庖丁定位成“收口类问题，以判官为中心”（`docs/research/paoding-design-implications.md` §1），所有机制围绕“可验证”展开。这个定位让评测读数可信，代价是把“不知道答案”的任务全部排除在外。而后者才是使用智能体的主要场景。

这不是实现上的缺陷，是定位选择。修法也不是继续加出路，而是把默认方向掉过来。

## 2. 新原则：证据随行

| | 判据先行（今天） | 证据随行（开放道） |
| --- | --- | --- |
| 开始的条件 | 登记了判官能执行的判据 | 有一句话就够 |
| 完成的信号 | 判官判 pass | 智能体交付，或预算用完，或人叫停 |
| 正确性由谁保证 | 判官，开题时定死 | 没有人保证；系统给出证据供人判断 |
| 系统的承诺 | 结论已被独立验证 | 结论有哪些证据、哪些没验证，如实列出 |
| 人何时出现 | 开题前（写判据、确认） | 结果出来后（看、追问、采纳） |
| 适用 | 练习、评测、平台赛题 | 其余一切 |

要点：**开放道降低的是开始的门槛，不是诚实的标准。** 它不声称答案正确，但要求每条关键主张都能指到一次真实执行的留档。这一点靠庖丁已有的机制就能做到：所有命令经执行层，输出自动登记为 Artifact，带来源和哈希，模型伪造不了。

## 3. 端到端流程

```
一句话 ──▶ 起草与校验 ──▶ 立即创建 ──▶ 求解会话 ──▶ 交付 ──▶ 人看结果 ──▶ 关闭
            （不再拒绝）   （零出站、      （单会话     （答案+证据   （追问/采纳/
                           默认预算）      连续工作）    +自检）       不采纳/不理）
                                            │  ▲            │
                                    扩权卡 ◀┘  └─ 续期门    └▶ 复核（可选，只给读数）
```

### 3.1 创建

1. 人输入一句话，回车。可以附材料，可以不附。
2. 起草模型照旧只指认原文区间（目标陈述、提到的地址）。校验的判据推导改为：
   - 人填了答案栏，或选了“严格判定”，或从平台导入：走严格道，行为与今天完全一样；
   - 其余全部走开放道，包括原文里出现了命令的情况（见 §12 第 2 条）。
3. 开放道**不出确认卡**，直接创建。理由：确认卡原本确认的是判据和授权。开放道没有判据；授权在运行时扩权（#91，`grants.runtime` 已默认开启）之下开题为零出站，工作区之外什么都碰不到。剩下唯一有风险的量是预算，由默认档位和单题硬顶兜住。
4. 创建后页面直接进入任务，能看到智能体在做什么。

校验仍然会拒绝的情况只剩真正无法继续的：原文为空、超过长度上限、人选了严格道却没给判据。

### 3.2 求解

开放道新增一个会话角色 **solve**，替代 bootstrap、reason、explore 三段式。

- **一个会话做到底。** 带执行、文件读写、扩权申请、交付这几样工具，自己规划、自己执行、自己决定何时交付。规划写在工作区的文件里（会话自己的待办清单），不要求写成图里的 Intent。
- **不要求写论断。** 图里的 Fact 和 Intent 在开放道是可选的笔记。审计不依赖模型主动记录：每次执行的命令、输出、出站请求本来就由执行层和闸门自动留档。
- **上下文用完时接力。** 会话因回合或上下文上限结束而未交付时，收尾轮写一份进度笔记（做了什么、排除了什么、下一步）到工作区，调度器启动下一个 solve 会话接着做。工作区和笔记是接力的载体。接力次数有上限（建议 5），用完转人介入。
- **并行是后话。** solve 会话今后可以派出子任务并行探索，放在第四步，不进最小可用。

需要出站时走 #91 已有的 `request_access`：申请、人批、热加闸门。等待期间会话继续做不依赖该地址的部分。

### 3.3 停止：没有判据时怎么知道做完了

停止信号按优先级：

1. **智能体交付**（正常出口）。提示词给的交付标准是三条，都是它自己能判断的：
   - 原话里问的每一件事都有了回应（答了，或说明为什么答不了）；
   - 每条关键主张至少有一处它亲眼看到的执行输出支撑；
   - 自检做过一轮（见 §4.2）。
   满足即交付，不为追求更完美而继续消耗预算。做不下去时也交付，结局标为“部分完成”或“受阻”，写明卡在哪里、需要人提供什么。
2. **预算到顶。** 预算留出一小份收尾保留（建议 10%）。花费到达保留线时，会话被要求立即交付当前最好的结果。这保证预算耗尽时人手里有东西，而不是一个空的“未解决”。
3. **人叫停。** 任何时候可以停，停时同样触发一次收尾交付。
4. **停滞。** 无新事件超时，按现有哮天犬规则回收，转人介入。

没有判官，就没有“判错了重试”的循环。`goal.max_attempts` 在开放道不适用。

### 3.4 交付

交付是一个新的内核操作 `deliver`，内容：

| 字段 | 含义 |
| --- | --- |
| `answer` | 答案或交付物：一段文字，或指向工作区产物的引用 |
| `outcome` | `answered` 完整回答、`partial` 部分完成、`blocked` 受阻 |
| `claims[]` | 关键主张，每条带 `refs[]`：支撑它的执行留档或输入材料的 ArtifactId |
| `self_check[]` | 自检项：查了什么、怎么查的、结果、留档引用 |
| `unverified[]` | 没有验证的部分和所做的假设 |
| `needs[]` | 仅 `partial`、`blocked`：需要人提供什么 |

内核对交付只做机械检查：引用的 Artifact 存在、属于本题、类别是执行留档或输入材料。**内核检查“引用是真的”，不检查“结论是对的”。** 没有任何引用的主张允许存在，界面上标成“无留档支撑”。

交付不关题。交付之后任务进入“待看”，人可以继续（§3.5）。

### 3.5 人看结果

结果页自上而下：答案；结局与一句“本结果未经独立判定”；主张与证据（点开能看到那次执行的命令和输出原文）；自检；未验证项；花费。

人能做四件事，都不是必须的：

- **追问**：写一句话，任务回到求解，带着之前的全部工作区和上下文笔记继续。这是与“先干后看”工具对齐的关键一环：一次交付不是终点，是对话的一轮。追问消耗剩余预算，不够时走续期门。
- **采纳**：一键，关闭任务，记“已采纳”。
- **不采纳**：一键加可选理由，关闭任务，记“未采纳”。
- **不理**：闲置超过设置的天数（建议 7 天）自动关闭，不记反馈。

### 3.6 复核（可选）

交付后可以起一个独立的复核会话：全新上下文，可配不同模型，只读交付内容与留档，逐条核对“这条引用是否真的支撑这条主张”，能重跑的自检重跑一遍，尝试找反例。输出是读数（例如“7 条主张，6 条有据，1 条引用与主张不符”）和具体意见，附在结果页。

复核只给读数，不改终态，不拦交付：结果先给人看，复核结果稍后补上。花费从预算的验证份额（现有 `verify_share`）里出。

自我评价不可靠，这是所有“先干后看”工具共同的弱点。复核是庖丁能在这里做得更好的地方，但它是增值项，不是门。

## 4. 智能体怎样自主规划与自评

### 4.1 规划

不规定流程。solve 的提示词只给目标、工具、约束和交付标准，大意：

> 你在处理一个任务，原话如下。没有人知道标准答案，你的工作就是把它找出来或做出来。自己决定怎么做。把计划和进度记在工作区的笔记文件里，方便自己回看和接力。需要访问外部地址时申请授权，等待时先做别的。完成后用 deliver 交付。

不预设角色，不预设步骤，不要求把思考写成结构化节点。这与调研结论一致（`docs/research/` 三份综述）：外部编排结构正在被模型能力吸收，约束越少的框架在强模型上表现越好。

### 4.2 自检

交付前要求做一轮自检，内容由智能体按任务性质决定，提示词给出方向：

- 能跑的就跑：写了代码就执行它，声称某接口返回某值就再请求一次；
- 对照原话：逐句核对有没有漏掉的要求；
- 交叉验证：关键事实尽量有两个独立来源；
- 原文里出现的检查命令（如“跑 make test 通过”）当作必做的自检项，结果如实报告。

自检有预算上限，只做一轮。自检失败不阻止交付，但必须写进 `self_check` 和 `unverified`。

### 4.3 不做的事

- 不让模型给自己打置信度分数。数字没有校准依据，人会误读。用“哪些有证据、哪些没有”代替。
- 不让模型起草的验收条目变成权威清单（宪章附加条件 ① 不变）。模型的自检项只是自检项。

## 5. 终态与读数

### 5.1 终态

关题时的终态从三值扩为四值：

| 终态 | 条件 | 显示 |
| --- | --- | --- |
| `solved` | 严格道，判官判到 E3 | 已解决 |
| `accepted` | 开题时登记了验收清单，人逐条验过 | 已验收 |
| `delivered` | 开放道，至少有一次 `answered` 或 `partial` 的交付 | 已交付 |
| `unsolved` | 其余：严格道未通过；开放道没有任何交付，或只有 `blocked` | 未解决 |

人的反馈是 `delivered` 上的附加属性，不是终态：`feedback` 取已采纳、未采纳、无。

`delivered` 的含义只是“智能体交出了东西”。界面和导出里凡是出现它的地方，都带“未经判定”字样。证据梯（E0 到 E3）在开放道不适用于 Goal：没有判官就到不了 E3，也不显示等级，改显示“主张 n 条，有留档支撑 m 条”。

### 5.2 读数

- 开放道单独成表：创建数、交付数、各结局占比、采纳率（只在有反馈的任务里算）、每次交付的花费、复核读数。
- **不进解出率，不进任何 G1 对照读数。** `by_authority` 现有 local、external、human 三列之外新增一列 `self`（自述），四列永不合并。
- 评测台只跑严格道。开放道任务不作为评测样本。

### 5.3 从开放到严格：答案找到之后

开放道任务被采纳后，人可以一键把它转存为练习题：原话作题面，采纳的答案作答案键。此后它在严格道里用来回归度量智能体。

这回答了“我都知道答案了还要智能体干什么”：第一次是开放道，没人知道答案，智能体去找；找到并被人认可之后，这道题才进入严格道，用途变成检验下一个版本的智能体还能不能做出来。严格道是开放道的下游，不是上游。

转存只写到应用自己的数据目录，不涉及本机题库与校准目录（硬规则不变）。

## 6. 与“先干后看”类工具的对照

| | zcode 与常见 harness | 庖丁开放道 | 取舍 |
| --- | --- | --- | --- |
| 开始 | 输入即执行 | 输入即执行 | 照搬 |
| 执行 | 单会话循环，工具全开 | 单会话循环，工具经执行层 | 照搬形态；工具仍走代理，换来留档 |
| 完成 | 模型说完成 | 模型交付，带主张、证据、自检 | 多一步结构化，成本是交付时多写几行 |
| 后续 | 继续对话 | 追问 | 照搬 |
| 权限 | 危险操作前询问，可全放开 | 开题零出站，每个新地址申请一次 | 更严；对联网任务有摩擦（§10） |
| 花费 | 无硬上限或软提示 | 单题硬顶，到顶先交付 | 保留 |
| 密钥 | 在工具进程里 | 模型容器里只有任务令牌 | 保留 |
| 审计 | 会话记录 | 事件账，每条主张可追到留档 | 保留 |
| 度量 | 无 | 采纳的结果可转成回归题 | 保留，改成可选 |

**放弃的**：对所有任务承诺“结论经过独立验证”；默认的三段式角色分工；强制的论断格式。

**要承认的**：做完第一步，开放道在求解质量上最多与这些工具持平，不会更好。质量来自循环本身的打磨（提示词、上下文管理、工具面），需要用同一批提示词与这些工具做对照来迭代。庖丁多出来的是治理和留档，这些对“一个人问一个问题”的场景价值有限，对无人值守、花真钱、碰真实系统的场景才有分量。是否值得，由 cz 判断；本稿不替现有设计辩护。

## 8. 内核改动面（供评估，不是实现）

- `goal.accept` 增加 `open`。`open` 时 `goal.check` 与 `judges` 可以为空，`acceptance` 可选。
- 新操作 `deliver`（会话令牌）、`follow_up`（人）、`feedback` 并入 `close_problem`（人）。
- 派工：`open` 题只派 solve；未交付且无在场会话时派一个；交付后不再派，直到有追问。
- 终态四值；`authority` 增加 `self`。
- 已有事件的回放结果不变：所有新字段缺省时行为与今天一致。

规格里与此相关的红线与不变量（单写者、令牌决定身份、Artifact 类别可采信性、预算硬顶、最小权限）都不动。动的是“Goal 必须有判官”这一条契约。

## 9. 安全与风险

| 风险 | 说明 | 处置 |
| --- | --- | --- |
| 自信地给出错误答案 | 开放道的固有风险，所有同类工具都有 | 不假装能防住。靠证据引用、未验证项、可选复核和“未经判定”标注让人有判断依据 |
| 没有判官叫停，预算空转 | 模型可能反复打磨 | 交付标准明确写“满足即交”；单题硬顶；收尾保留保证到顶有产出 |
| 零确认创建被滥用 | 一句话就开跑 | 开题零出站且只有工作区；花费有硬顶；出站与高风险执行仍逐次审批 |
| 读数被污染 | 开放道结果混入解出率 | 终态与 `authority` 分列，评测只跑严格道 |
| 原文里的指令注入 | 材料里夹带“访问某地址” | 与今天相同：原文不产生授权，访问必须申请并由人批 |
| 交付内容引用伪造 | 模型编造证据编号 | 内核机械校验引用存在且类别可采信 |

## 10. 已知的不足，不在第一步解决

- **联网摩擦。** 找答案常常要查资料。今天每个新地址都要人批一次，没有检索工具，只能经执行层用命令行请求。这会明显拖慢调研类任务。可选的缓解是设置层的通用只读白名单（#91 待裁决第 4 条当时选了“等读数”），见 §12 第 5 条。
- **求解质量。** 第一步只保证“能跑通并诚实交付”，不保证做得好。提示词和上下文管理需要对照迭代。
- **长任务。** 接力靠工作区笔记，信息会有损耗。更好的上下文压缩留到后面。

## 11. 迁移步骤

每一步独立可合、可回滚；严格道的行为和已有事件的回放在每一步都不变。

| 步 | 内容 | 做完后能怎样 |
| --- | --- | --- |
| **1 最小可用** | 内核：`accept: open`、`deliver`、终态 `delivered`、solve 派工。校验：`no_criterion` 改为进开放道。适配层：solve 角色与提示词、收尾保留、接力。命令行：创建、看交付、关闭。 | 今天被拒的那句话能从命令行和现有网页创建入口走到一份带证据的答案 |
| 2 结果页与追问 | 网页结果页（答案、主张与证据、自检、未验证）、追问、采纳与不采纳、闲置自动关闭 | 完整的“干、看、再问”回路 |
| 3 复核与读数 | 复核会话、开放道读数表、`self` 列 | 结果带独立读数；统计分列 |
| 4 默认翻转与地图 | 新建页默认开放道，严格判定收进“高级”；宪章地图修订；D3 并入；并行子任务 | 开放道成为产品默认形态 |
| 5 转存练习题 | 采纳的结果一键转成严格道题目 | 开放道喂养严格道 |

**第一步的验收**：一组开放提示词（建议 10 条，由 cz 指定或认可，不取自本机题库）逐条跑通：没有一条被拒；每条都以交付或如实的“部分完成、受阻”结束；每条交付的引用都通过内核校验；预算到顶的用例有收尾交付；全部严格道既有测试不变。同一组提示词在一款对照工具上也跑一遍，结果并排记录，作为之后迭代求解质量的基线。

**回滚**：设置项 `lanes.open`（开、关）。关掉后校验恢复拒绝，已创建的开放道任务照常可读、可关。
