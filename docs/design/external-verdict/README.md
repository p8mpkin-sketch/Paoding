## 0. 一页结论

1. **复现成立。** 用一个只有四类端点（清单、说明、提交、回执）的平台模拟，四个表现全部复现（§1）。另外发现一个比"被拒"更糟的结果：说明里带一段提交示例时，唯一不被拒的路是把**提交命令**登记成 `replay` 判据（§1.2 用例 1b）。
2. **假设部分成立，要改写。** "开题时强制预先确定三样"只说中了一半。I4 要求判据在动手前登记，这条是对的，不能动。真正的毛病是：开题契约只会登记**值**（答案、命令、地址、秒数），不会登记**来源**，也就是"谁说了算、经哪条登记过的通道、在什么界内、什么时候交付"。时限一维还多一个独立的根因：`budget.wall_s` 一个字段同时当"花费轨"和"自开题起的墙钟"用（§2）。
3. **根因九条（§3），每条附证据。** 判据形态是封闭枚举；判官没有"判定权在外"的形态，也不会等待；唯一退路会错绑；时限与花费混成一个字段；外部时钟的原点不在开题时刻；人工裁决没接通；判官一侧的外部通道与凭据无处安放；资源运行时发现（#91 已解）；读数分不出判定来源。
4. **一个机制：定源登记。** 开题契约的三维，每一维都可以登记成"值"（今天的做法），也可以登记成"源"：`{来源, 通道, 界}`，值到运行时才经登记过的通道交付，**交付一次即固定**。登记的那份"源"之后不可改，判据先行就这样延伸过来，没有被破坏（§4）。
5. **三维各落一处，复用既有机制。**
   - 判据维：判定权有三种来源，本地 / 外部 / 人。外部的那种是一类判官插件，叫"外部裁决连接器"（`kind: deferred`），走规格早就留好的"提交接口的插件位"和 `due_at`、`recheck_at`。人的那种就是 D3，本稿不重新设计。
   - 资源维：完全归 #91，本稿只补一个接口：连接器把运行时拿到的服务地址登记成一份 input 类"资源公告"，智能体照 #91 申请扩权。
   - 时限维：把"外部时限"从预算里拿出来，单独成一个 `deadline`，可以运行时绑定、只绑一次。`budget.wall_s` 回到规格 3.5 的花费轨含义。单题硬顶一个字都不放宽，只是不再拿它去卡一个不是花费的东西。
6. **推荐路线甲（§6）。** 定源登记，外部裁决做成判官插件，判官代为提交。并列对比了：乙，人转述回执；丙，智能体自己提交，再用 `record_match` 判；丁，补丁式，明确不采。
7. **与既有机制的边界（§7）。** #91 管智能体的出站，连接器的出站不进 `Problem.scope`；D3 管"人说了算"；判官插件机制管"怎么判"，本稿只给它加一个属性 `authority` 和一种运行器 `connector`。

## 2. 诊断：这一类任务的共性契约

### 2.1 从面上归纳

把四个表现放到一张表里，看每一维**由谁说了算、什么时候才知道**：

| 维 | 本地任务（今天能开的） | 平台裁决型 | 资源运行时发现型 | 人工裁决型 | 时限外部规定型 |
| --- | --- | --- | --- | --- | --- |
| 判定权 | 本地判官，值在开题时给出（答案、命令） | **平台**，回执异步到达 | 本地 | **人**，事后 | 本地 |
| 资源 | 开题时写明（#91 之后：运行时申请） | 服务地址领题时才分配 | **运行时由外部返回** | 视情况 | 本地 |
| 时限 | 本地预算 | 平台规定，从领题开始计时 | 本地 | 本地 | **外部规定**，可能超过本地硬顶 |

这一类任务的共性契约，一句话说：**三维里至少有一维的权威不在本地，它的值要经过某个外部方（平台、外部服务、人）、在运行时（或事后）才交付。** 本地能在开题时确定的，是"谁来交付、经哪条通道、可信到什么程度、最晚何时"，不是值本身。

### 2.2 对第二节假设的检验

| 假设的说法 | 结论 | 依据 |
| --- | --- | --- |
| 开题时强制预先确定"资源" | 成立，已由 #91 解决 | 用例 2；#91 §1.2 |
| 开题时强制预先确定"判据" | **部分成立，要改写**。"判据在开题时登记、之后不可改"（I4）是对的，必须保留。失效的是"判据只能以**值**的形态登记"：本地持有的答案（sealed）或本地能跑的命令（replay）。判定权在外部时，开题时根本拿不到值，但完全可以登记**来源** | 用例 1、1b、5；`draft.py:18` 的 `FORMS`；规格 3.3.2 早就留了"提交接口的插件位"，`due_at`、`recheck_at` 也在 JudgeRequest、JudgeVerdict 的类型里 |
| 开题时强制预先确定"时限" | **一半被推翻**。用例 4 里时限在开题时是**已知的**（6 小时），被拒的原因不是"不知道"，是把一个外部截止时刻塞进了本地花费预算，再拿花费的硬顶去卡它。另一半成立：平台从领题开始计时，绝对截止时刻要到运行时才知道 | 用例 4、4b；`watchdog/dog.py:119` 与 `graph/work.py:143-162` 对同一字段的两种用法 |
| 三维是同一个设计假设的失效 | 成立，表述要换：失效的不是"预先确定"，是"**只有值，没有来源**"。另外假设漏了三处：判定的**时序**（异步，等待期间不能被当成停滞或超时）、判官一侧的**外部通道与凭据**、读数里的**判定来源** | §3 的 R2、R7、R9 |

## 4. 方案：定源登记

### 4.1 一句话

开题契约的每一维，都可以登记成两种形态之一：

| 形态 | 登记什么 | 值何时到 | 谁交付值 | 之后能不能改 |
| --- | --- | --- | --- | --- |
| **定值**（今天的做法） | 值本身：sealed 答案、检查命令、scope 规则、`wall_s` | 开题时 | 人 | 不能（I4） |
| **定源**（新增） | 来源 `{source, channel, bounds}`：谁说了算、经哪条登记过的通道、在什么界内 | 运行时或事后 | 登记的那条通道（确定性代码或人），路径上没有模型 | 源不能改；值**交付一次即固定** |

"判据登记后不可改"在定源形态下是这个意思：登记的是判定的**程序**（连接器档案的版本与摘要、平台任务号、回执到裁决的映射表），之后不可改；运行时交付的是这个程序的**输出**（回执）。这与今天的 `sealed` 同一个思路：内核从来不看答案，只登记 `VaultRef` 和加盐摘要。

### 4.2 三维的落点

```
                       定值（今天）                      定源（新增或已裁决）
  判定权  goal.check   exact_match{sealed} | replay{spec}  ├ 外部：外部裁决连接器判官（本稿 §5.1–5.4）
                                                           └ 人：accept=human + acceptance[]（D3，已裁决，L2）
  资源    scope        开题时的规则                        运行时申请 → grant_scope（#91，已裁决，#93 已合入）
                                                           └ 连接器把运行时分到的地址登记成"资源公告"（§5.5，只是接口）
  时限    deadline     （没有这一项，混在 budget.wall_s 里） deadline{source: local|external}，运行时绑定一次（§5.6）
  花费    budget       usd_milli、wall_s（花费轨）          不变；单题硬顶不变
```

内核里多出一个**派生**量 `goal.authority ∈ {local, external, human}`。它不由提交方声明，由 Goal 判官快照的 `authority` 与 `goal.accept` 推出，与画像同法（`_derive_profile`）。所有读数按它分列（§5.7）。

### 4.3 四个表现各自怎么被覆盖

| 表现 | 哪一维定源 | 由谁交付值 | 开题时登记什么 | 本稿新增的东西 |
| --- | --- | --- | --- | --- |
| 1 平台裁决型 | 判定权（外部）、时限（外部）、资源（运行时） | 连接器判官 | `goal.check = {judge_id: <连接器判官>, spec_ref: <绑定单>}`，`deadline.source = external`，`scope = workspace` | §5.1–5.7 全部 |
| 2 资源运行时发现型 | 资源 | 智能体申请，人或白名单批（#91） | `scope = workspace` | 只有"资源公告"这个接口（§5.5）；批准规则归 #91 |
| 3 人工裁决型 | 判定权（人） | 人逐条勾选验收清单（D3） | `accept: human`，`goal.acceptance[]` | 无新设计；只把它放进 `authority` 这一轴，读数统一分列 |
| 4 时限外部规定型 | 时限 | 原文（定值）或连接器（定源） | `deadline`；`budget.wall_s` 只管花费，照旧受单题硬顶约束 | §5.6 |

表现 4 不一定有平台：一个人说"对方要求周五 18:00 前交"，也是外部时限。它走同一个 `deadline`，`source = local`，值由人在确认卡上给出（绝对时刻由前端传入当前时间换算，kaiti §12 第 3 条的做法）。

## 5. 机制细节（路线甲）

### 5.1 外部裁决连接器：一类判官插件

判官注册表（`judgebox/judges.d/`）里加一种条目，规格 3.3.2 的类型不变，只多两个字段：

```yaml
# 外部裁决：判定权在外部平台，本判官只做确定性的交付与回执读取，路径上没有模型
id: ext_receipt
version: "1"
kind: deferred                 # 规格已有：裁决在 due_at 之后给出，到期前目标带 pending，等级不变
grade: decisive                # 对"平台回执为通过"这一论断是判定性的（§10 第 4 条）
authority: external            # 新增：判定来源。缺省 local，旧条目不受影响
applies_to: [goal]
runner: {type: connector, base: builtin}   # 新增运行器类型：不起容器，不碰 Problem.scope
timeout_s: 30                  # 单次读回执的超时；等待不算在这里
max_cost: {usd_milli: 0, wall_s: 30}
auto: true
flake: {reruns: 0, require: all}
```

连接器档案是另一类数据（`judgebox/connectors.d/*.yaml`，与判官注册表同级，启动时加载）。平台的领域词只出现在这里（红线 3）：

```yaml
id: platform-a
version: "2"
match: {hosts: ["platform-a.example"]}          # 一句话开题按地址查表认出平台；纯展示之外的唯一用途
task_ref: {pattern: "T-[0-9]+"}                 # 平台任务号的形状；必须是原文逐字子串
credential: {key_slot: platform-a}              # 钥匙环里的槽位名；值只在连接器进程内存（#87 D4）
endpoints:
  list:    {method: GET,  path: /api/tasks}
  brief:   {method: GET,  path: "/api/tasks/{task}"}
  submit:  {method: POST, path: "/api/tasks/{task}/submissions", body: {answer: "$candidate"}}
  receipt: {method: GET,  path: "/api/submissions/{sid}"}
fields:                                         # 回执与说明里哪个字段是什么，JSON 指针
  submission_id: /submission_id
  status: /status
  instance: /instance
  time_limit_s: /time_limit_s
  max_submissions: /max_submissions
verdict:                                        # 回执状态 → 裁决。表外的值一律 inconclusive(unsupported)
  accepted: pass
  rejected: fail
  pending: pending
deliver: judge                                  # 谁提交：judge（推荐）| worker，见 §10 第 2 条
poll: {first_s: 10, max_s: 600, settle_s: 3600} # 轮询间隔、上限，以及截止之后还等回执多久
```

注册表加载时把档案的版本与摘要并进判官快照：`judge_snapshot[ext_receipt] = {version, grade, kind, authority, max_cost, connector: {id, version, digest}}`。重放不读档案文件，与判官版本、练习道信封同法。

### 5.2 开题时登记什么

```
goal.check = { judge_id: "ext_receipt",
               spec_ref: <input 类 Artifact：绑定单> }
绑定单（JSON，规范化）= { connector: "platform-a", task: "T-17", max_submissions: 3 }
goal.max_attempts ≤ 绑定单.max_submissions   （内核核对；本地次数上限永远不超过平台额度）
deadline = { source: "external" }              （值待绑定，§5.6）
scope    = [ workspace r0 ]                    （#91：开题零出站）
```

内核在 `open_problem` 的 `validate` 里多三条检查，都不读领域数据：Goal 判官快照里 `authority = external` 时，`spec_ref` 必须存在且是 input 类；绑定单里的 `connector` 必须等于快照里的连接器 id（内核解析这份 JSON 只取这一个键和 `max_submissions`，与解析 `practice.yaml` 同样只认结构）；`max_attempts ≤ max_submissions`。

### 5.3 判定的时序：待定

交付与读回执分两步，都由判官运行器做（`deliver: judge`）：

1. 智能体照常 `claim_done`，候选是答案文件（与 `exact_match` 相同）。图服务派生判官请求，次数上限照 `max_attempts` 计（`reducer/judge.py` 现有逻辑，按不同候选计数）。
2. 判官运行器领到租约，按档案的 `submit` 交付候选，拿到 `submission_id`。交付回执登记成 judge 类 Artifact。幂等键是 `(problem, candidate)`：同一候选重复请求时，只读回执，不重交。
3. 读回执。`pending` 时，裁决记 `inconclusive`，原因码新增 `pending`，并带 `recheck_at`（规格 3.3.2 已有这个字段）。无结论不进裁决序列（今天就是这样），所以等级不变，目标显示"待定"。
4. 到了 `recheck_at`，图服务派生复判项（`work.py` 里已有 `rejudge` 这类派生项，沿用同一候选，不消耗次数）。判官读回执，按映射表给出 pass 或 fail，回执登记成 judge 类证据。
5. Goal 判定性 pass，于是到 E3，图服务按现有规则自动关题，终态 solved，`authority = external`（§5.7）。

为什么不新增一个"待定"事件：`inconclusive` 加 `recheck_at` 正好就是"这次没有结论，某时再来"。内核只需把 `pending` 加进 `INCONCLUSIVE_REASONS`，再让 `work.py` 在 `recheck_at` 之前不派生复判。改动最小，而且就是规格留的那两个字段。另一种做法（专门的 `judge_pending` 事件）列在 §10 第 5 条。

### 5.4 判官独立怎么守

| 风险 | 守法 |
| --- | --- |
| 智能体自报"平台说通过了" | 智能体不碰提交端点，也不碰回执端点（`deliver: judge` 时这两个端点从不出现在 `Problem.scope` 里）。裁决只来自判官运行器读到的回执，回执登记为 judge 类，Worker 的令牌登记不了这一类 |
| 回执映射里藏着模型 | 映射是一张确定性表；表外的值给 `inconclusive(unsupported)`，不猜 |
| 平台中途改了规则 | 档案的版本与摘要在开题时进快照；运行时档案不一致，判官拒绝运行，记 `inconclusive(env_error)`，与今天判官版本不一致的处理相同（`runner.py:184`） |
| 穷举平台 | `max_attempts ≤ max_submissions`，次数由内核计；平台自己的 429 记 `inconclusive(env_error)` |
| 凭据外泄 | 令牌只在钥匙环槽位和连接器进程的内存里，请求头当场注入；金丝雀测试（宪章 AC-M5）把连接器的全部路径纳入：日志、事件、Artifact、会话转录里逐字搜不到 |

`deliver: worker`（智能体自己提交，判官只读回执）也能守住，但要多两条：智能体在 `claim_done` 里给的是 `submission_id`，判官必须向平台核对这次提交确实属于绑定单里的任务，而且发生在开题之后；提交端点要经 #91 申请，风险按风险表给（会消耗外部额度，至少 r1）。所以推荐 `judge`，`worker` 只留给"平台判的是环境状态，没有可交付的载荷"这一种情况（§10 第 2 条）。

### 5.5 资源：只补一个接口，批准归 #91

- 连接器在**领题**时，把说明全文与分到的服务地址登记成一份"资源公告"。登记方取决于领题发生在什么时候（今天 `refmodel.REGISTRAR` 只许人的令牌登记 input 类，判官令牌只能登记 judge 类）：
  - **开题时领题**（"从平台导入"入口，v1 的缺省）：连接器服务替人取回说明，由人的令牌登记为 input 类，挂进 `origin.materials`。
  - **运行时领题**（平台要求先领题才分配实例、才开始计时）：判官运行器执行 `brief`，登记为 judge 类 Artifact，带 exec 出处，与判官输出同法。
- 智能体读到公告里的地址，照 #91 `request_scope` 申请。风险查表，人或练习道白名单批准。本稿**不**规定公告能否作为自动批准的依据；这一条是 #91 的事，经协调转给那条线程（§7.1）。
- 连接器自己访问平台 API 的出站**不进** `Problem.scope`，它是档案里登记的固定通道，与端点代理访问模型 API 同类。

### 5.6 时限：deadline 与花费轨分开

```ts
Problem.deadline?: { source: "local"|"external",
                     at?: number,                 // 绝对时刻（毫秒）。source=local 时开题即给；external 时运行时绑定
                     bound_by?: ArtifactId }      // external：证明这个时刻的回执（开题时领题为 input 类资源公告，运行时领题为 judge 类领题回执）
```

- **绑定一次。** 开题时领题的，`at` 在开题时就由连接器从说明里的 `time_limit_s`（或平台直接给的截止时刻）换算出来，`bound_by` 指向资源公告（input 类），之后不可改。运行时领题的，新增内核操作 `bind_deadline {at, evidence}`：只接受 judge 令牌，只在 `source = external` 且 `at` 未设时接受，证据必须是本题的 judge 类 Artifact（领题回执）。绑定之后同样不可改。
- **`budget.wall_s` 回到花费轨。** 它的含义改成规格 3.5 的原义：各任务租约墙钟的累计（`work.py` 今天已经这么累计）。单题硬顶照旧卡它，一个字不放宽。
- **哮天犬分开执行三件事。** 花费墙钟累计 ≥ `budget.wall_s`：停所有工作租约。到了 `deadline.at`：停所有工作租约，但**判官请求保留**，档案的 `settle_s` 之内照常复判，之后再关题。"题的最长存活"另设一个设置层全局值（例如 7 天）：只防僵尸题，不按题设。
- 用例 4 的结果因此变成：`deadline.at = 领题时刻 + 6 小时`，`budget.wall_s = 14400`（花费轨，不超硬顶）。智能体最多干 4 小时的活，平台给的 6 小时窗口里等回执、等人的时间不计费。
- **开关。** 设置层新增 `budget.wall_mode: elapsed | spend`，缺省 `elapsed`，也就是今天的行为：哮天犬按开题墙钟关题，没有 `deadline` 与最长存活。取 `spend` 时，上面三件事分开执行。开关的取值随设置摘要进开题事件体（宪章 D5），重放不读设置；评测各臂取同一个值，写进 `meta.json`。一期落地时缺省不变，翻缺省另行放行。
- 迁移影响：所有题的 `wall_s` 都从"墙钟"变成"花费墙钟"。连续跑的题两者几乎相等，长时间停滞等人的题会活得更久，由全局最长存活兜底。评测各臂同时换，可比性不受影响，换的那一版写进 `meta.json`。只对带 `deadline` 的题换语义的做法列在 §10 第 6 条。

### 5.7 读数与终态

- 终态仍是三值（solved / accepted / unsolved），refmodel 不动。
- 每道题带派生的 `authority`。今日、任务库、读数页、`pd status`、`pd report`、评测记录里，solved 按 `authority` 分两行："本地判定" 和 "外部判定（平台名）"。"成功率""每解成本"一类分子默认只取本地判定，外部判定另列。这是宪章裁决附加 1（accepted 与 solved 永远分开）往外再推一格。
- 工作区的 Goal 卡片写"由 platform-a 判定 · 待定（下次查询 14:32）"，不写"已证明"。

### 5.8 开题入口

| 入口 | 适用 | 怎么走 |
| --- | --- | --- |
| **从平台导入**（推荐的主入口） | 已登记档案的平台 | `pd connector tasks platform-a` 或网页"从平台导入"：连接器调 `list` 端点，人勾选任务，逐题生成结构化的 `ProblemInput`（题面取说明全文），走导入页同一条提交路（`app/submit.ts`）。没有起草模型 |
| **一句话开题** | 人贴了一段平台任务的描述 | 前置抽取已有的地址区间，按档案的 `match.hosts` **查表**认出平台；任务号按档案的 `task_ref.pattern` 从原文里抽出逐字区间。起草的 `check.form` 多一种取值 `external`，模型只能指认"平台区间"和"任务号区间"。`vet` 再核对一遍：平台查表命中、任务号是逐字子串、判官取档案对应的那一个 |

两个入口的统一约束：

- **command 判据一律显式警告**（往返意见 a）。平台没登记时，`vet` 认不出平台，原文里的提交示例仍可能被指认成检查命令（用例 1b）。所以只要判据是 command 形态，确认卡就不再只给一行提示（今天的 `command_criterion`），而是显示一条警告：

  > 判官会在洁净容器里**重放**这条命令，按退出码判定。如果它是向外部平台提交，它就不是检查：重放会再提交一次，或者因为出不去网被判失败。外部平台说了算的任务，请先[登记这个平台](#)，再从平台导入。

  警告分两档，判定都是确定性的，词表放在 `kaiti.d/intake.yaml`，不进代码：
  - **普通警告**：command 形态都给。
  - **加重警告**：命令里含有外发的形状。具体是三种之一：URL 或 `host:port` 区间、写方法的 HTTP 动词（`-X POST`、`--data`、`-d` 等）、原文里出现"提交"一类的词。这时"开题"按钮要先勾一项"我确认这条命令只检查、不提交"才可用；`pd kaiti` 要加 `--yes-command` 才放行。勾选记进出处账，来源记"人"。

  这是一条提示，不是拒绝：本地的检查命令（如 `make test`）照常可用。真正的修法仍是登记平台，登记之后 `vet` 认出平台，提交示例只作材料，不成为判据（§9 用例 1b）。
- 外部裁决的题**永远走确认道**，不进零确认。交付是对外动作，会消耗平台额度。练习道信封不变（判官只许 `exact_match`），所以内核也会拒绝。
- 平台没登记档案时拒绝，降级路改为四条：补答案或检查命令；人工验收（D3）；进高级模式；**去设置页登记这个平台**（新增）。
- 判据形态改由注册表驱动：起草提示里的形态目录、`vet` 的分支都从注册表里 `applies_to` 含 `goal` 的条目生成，不再在 `draft.py` 里写死（修 R1）。`answer`、`command` 两条照旧，相当于 `authority: local` 的两条注册表条目。

## 6. 路线对比

| | 甲 定源登记 + 连接器判官（推荐） | 乙 人转述回执 | 丙 智能体提交 + `record_match` | 丁 补丁式（不采） |
| --- | --- | --- | --- | --- |
| 做法 | §5 | 外部裁决的题一律开成 `accept: human`；人在平台上看回执，截图或粘贴作依据，逐条勾选 | 智能体经 #91 拿到提交与回执端点，自己提交；执行层的类型化只读工具取回执，登记为 exec 类；Goal 判官是 `record_match`，对回执求谓词 | `vet` 加 `form = platform`；内核白名单加一个 `accept` 值；对"外部时限"豁免单题硬顶 |
| 覆盖 | 四个表现全部 | 平台、人工；时限要另做 | 平台、资源；时限要另做 | 只盖住被拒的那几个分支 |
| 判官独立 | 强：智能体不碰交付与回执 | 弱：等于由人担保 | 中：智能体决定交哪次、交几次；回执是执行层取的，但取哪一个由智能体指 | 无从谈起 |
| 内核增量 | 小：`authority` 派生、`pending` 原因码、`deadline` 与 `bind_deadline`、开题三条检查 | 零（D3 之外） | 中：`record_match`（规格完整版，未实现）、类型化工具 | 小，但每个新平台都要再补 |
| 人的负担 | 登记一次平台档案；每题确认一次 | 每题都要人看回执、勾选 | 每题批提交端点的扩权 | — |
| 读数诚实 | solved 按来源分列 | accepted，不冒充 solved | solved，但判定来源被藏进谓词里 | 混 |
| 时机 | 依赖 D3 吗：不依赖（人工那一维本来就是 D3） | 依赖 D3（L2） | 依赖 #91 与 `record_match` | — |

取舍：乙是甲落地之前的**过渡办法**，可以随 D3（L2）免费得到，但每题都要人看回执，而且永远只能 accepted。丙更接近"智能体自主"，但把"交几次、交哪次"放在了被判的一方手里，平台额度也由智能体消耗。甲把"交付与读回执"都放到判官一侧，智能体只做它该做的：找到答案。

丁明确不采：它只修拒绝分支，R2（不会等）、R4（时限语义）、R7（凭据与通道）、R9（读数）一条都没碰，开出来的题会被哮天犬提前关掉，或者判不了。

## 7. 与既有机制的边界

### 7.1 #91 运行时扩权（第一步实现 PR #93 已合入）

| 本稿管 | #91 管 |
| --- | --- |
| 连接器的出站与凭据（档案登记的固定通道，不进 `Problem.scope`） | 智能体的一切出站（`request_scope` / `grant_scope` / `revoke_scope`） |
| 把运行时分到的服务地址登记成"资源公告"（input 类） | 智能体据此申请、谁批准、风险从哪来 |
| `deliver: worker` 时，提交端点需要扩权这件事本身 | 提交端点的风险档、批准方式 |

要经协调转给 #91 线程的一条待议（本稿不替它决定）：资源公告出自已登记的连接器，不出自模型。这样的地址能不能作为练习道白名单之外的另一种自动批准依据？本稿的推荐是**不能**，v1 一律由人批，读数够了再议。

`bind_deadline`、`pending` 原因码都不碰 `Problem.scope`，与 #93 的 `grants.py` 没有交叉。`goal.authority` 的派生与 #93 里随扩权重算画像（`_derive_profile`）是同一个函数，实现时要合并，不要各改一份。

### 7.2 D3 人工验收（已裁决，L2 未实现）

本稿不改 D3。它在本稿里只是"判定权 = 人"那一格。新增的两条对齐：`authority` 由 `accept = human` 推出 `human`；读数里 accepted 那一行就是 `authority = human`，与 solved 的两行并列。表现 3 的验收标准、清单来源（只许原文区间或人写）、`accept` 的事件体，全部以宪章 02 §3.3 为准。

### 7.3 判官插件机制（既定路线）

连接器判官就是注册表里的一类条目，走同一个加载、快照、版本校验、成本入账流程。新增的只有：

1. 条目属性 `authority`，缺省 `local`；
2. 运行器类型 `connector`：不起容器，按档案发 HTTP，按映射表给裁决；
3. 连接器档案目录与它的摘要快照。

规格 3.3.2 的"提交接口的插件位"，在本稿里落地为 `deliver: judge`。

### 7.4 一句话开题（#83、#89）

三层不变：抽取、起草、校验。变的是判据形态的来源（注册表驱动，§5.8），以及拒绝页多一条降级路。练习道信封、零确认开关都不动。

## 8. 宪法逐条核对

| 条目 | 成立吗 | 依据 |
| --- | --- | --- |
| 红线 1 写入路径无模型 | 成立 | 连接器是确定性代码加数据；绑定单、`bind_deadline` 的值来自平台回执，经判官令牌提交，`validate` 与 `apply` 仍是纯函数 |
| 红线 2 反幻觉 | 成立 | 回执登记为 judge 类证据；资源公告是 input 类，不能当证据；模型只指认区间 |
| 红线 3 领域知识不进内核 | 成立 | 平台的端点、字段、状态词都在 `connectors.d/`；内核只认 `authority`、`kind: deferred`、绑定单里的 `connector` 和 `max_submissions` 两个键 |
| 红线 4 删简律 | 成立 | 连接器判官是一类可删的注册表条目；开关 `connectors=off`：拒绝页回到三条降级路，读数照旧 |
| 红线 5 诚实对照 | 成立 | 评测仍从 `eval/problems.d` 开题；外部判定的 solved 不进成功率默认分子；`wall_s` 语义换版各臂同时换，版本记进 `meta.json` |
| I1 写入无模型 | 成立 | 同红线 1 |
| I2 证据只认可采信 Artifact | 成立 | 外部裁决的证据是判官运行器登记的 judge 类回执 |
| I3 等级不可写 | 成立 | 等级照旧由裁决序列重算；`pending` 不进序列 |
| I4 判据先行、之后不可改 | 成立（延伸） | 登记的是判定程序（判官版本、连接器摘要、任务号、次数上限），之后不可改；`deadline` 绑定一次即固定 |
| I5 能力 ≤ 风险 ≤ 授权 | 成立 | 智能体的授权全走 #91；连接器的通道不进 Worker 容器 |
| I6 硬顶在容器外 | 成立 | 全局硬顶、单题硬顶不变；连接器 `max_cost` 入账，计入验证池 |
| I7 等级不出题 | 不涉及 | |
| I8 估值不进等级 | 成立 | 平台的分数（`score`）只作材料，不进等级与消费门；映射表只认状态 |
| 判官独立 | 成立 | §5.4 |
| 外部凭据按钥匙环管理 | 成立 | `credential.key_slot`；只在内存；金丝雀覆盖 |

## 9. 怎么证明它可用（验收门的草案）

1. **复现用例翻转。** `test_external_verdict_repro.py` 的七条，按下表改断言，作为实现的验收门：

   | 用例 | 今天 | 之后 |
   | --- | --- | --- |
   | 1 | refuse / `no_criterion` | 平台已登记：confirm，`judge = ext_receipt`；没登记：refuse，降级路含"登记这个平台" |
   | 1b | confirm / `replay` 判那条 `curl` | 平台已登记：认出平台，提交命令只作材料，不成为判据。平台未登记：仍是 confirm，但确认卡给加重警告，不勾确认项开不了题（往返意见 a） |
   | 2 | 草案里没有服务地址 | 开题后连接器登记资源公告；智能体申请扩权（#91 的测试兜底） |
   | 3 | `M0 只实现 accept=judge` | D3 落地后接受（不属本稿的验收） |
   | 4 | 裁剪 / `over_budget` | `deadline.at = 领题 + 21600`，`wall_s ≤ 14400`，不裁、不拒 |
   | 4b | 花费 0 也被关题 | 两种取值各跑一遍（往返意见 b）。`wall_mode = elapsed`（缺省）：照旧关题，断言与今天相同，证明缺省行为没变。`wall_mode = spend`：花费墙钟未用尽、`deadline` 未到、最长存活未到，不关；三件事各自越线时分别关，各一条用例；`deadline` 到了而判官请求待定时，`settle_s` 之内不关，之后关 |
   | 5 | 没有外部判官、回执 pending | 两次 `inconclusive(pending)` 后 pass，Goal 到 E3，终态 solved、`authority = external` |

2. **端到端。** 平台模拟加假智能体（`fakecli`），从导入到关题跑通。平台日志里的提交次数等于内核里的判官请求数（不同候选），回执登记为 judge 类。
3. **变异测试（内核）。** 档案摘要改一个字节，判官拒绝运行；`max_attempts > max_submissions`、`spec_ref` 缺失、绑定单的 `connector` 与快照不符，开题一律被拒；`bind_deadline` 第二次、非 judge 令牌、证据不是 judge 类，一律被拒。
4. **金丝雀。** 平台令牌注入钥匙环槽位，跑完上面全部路径，数据目录、日志、事件、导出物、会话转录里逐字搜不到。
5. **读数。** 外部判定与本地判定分列（宪章 AC-M6 的文案扫描扩到 `authority`）。

## 10. 裁决

cz 2026-11-19：九条全部采纳"推荐"一列，"否则"一列作废，留作记录。

| # | 问题 | 推荐 | 否则 |
| --- | --- | --- | --- |
| 1 | 总体路线 | 甲：定源登记 + 连接器判官 | 乙作为唯一做法（等 D3，每题人看回执，终态只有 accepted）；或丙 |
| 2 | 谁向平台交付 | 判官（`deliver: judge`），智能体不碰提交与回执端点；`worker` 只留给"平台判环境状态、没有载荷"的档案 | 一律由智能体提交，判官只读回执并核对归属 |
| 3 | 外部判定的终态呈现 | 终态仍是 solved，按派生的 `authority` 分列，成功率默认分子只取本地判定 | 新增第四个终态（如"外部通过"），refmodel、报告、读数都要改 |
| 4 | 连接器判官的 `grade` | `decisive`：它判的论断是"平台回执为通过"，这个论断它能确定地判 | `consistent`：Goal 最多到 E3d，不会自动关题，每题要人关 |
| 5 | 待定怎么表达 | `inconclusive(pending)` 加 `recheck_at`（规格已有的字段），复用复判派生 | 新增 `judge_pending` 事件，请求保持未裁决 |
| 6 | `wall_s` 语义 | 全体改回花费轨，另设 `deadline` 与全局"最长存活" | 只对带 `deadline` 的题改语义，其余照旧按开题墙钟 |
| 7 | 连接器档案放哪 | `judgebox/connectors.d/`，与判官注册表同类，启动时加载、摘要进快照；凭据走钥匙环槽位，设置页只读呈现 | 放进设置层（#87），网页可编辑，变更即换版本 |
| 8 | 开题入口 | 两个都做，"从平台导入"为主；外部裁决的题永远走确认道 | 只做导入，一句话开题遇到平台描述就指向导入 |
| 9 | 资源公告能否作自动批准依据 | 不能，v1 一律人批（此条最终归 #91，经协调转达） | 公告地址视同白名单段，练习道题可自动批 |

## 12. 开放问题

1. 平台只给"分数"不给"通过 / 不通过"（例如部分得分）。v1 的映射表只认状态，分数只作材料。要不要支持"分数 ≥ 阈值即通过"，阈值随开题登记？这会让人在开题时选一个阈值，属于定值，可以做，但先等真实需求。
2. 一个平台账号同时跑多道题时，平台额度是按账号算还是按题算。档案里要不要再加一个账号级的并发与额度上限，放在连接器里执行？
3. 平台回执本身被平台撤回或改判（复核后改成 rejected）。规格的"有效期 `ttl_s`"可以用：档案给 `ttl_s`，到期复检。v1 不做，记为已知局限。
