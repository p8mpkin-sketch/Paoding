# 授权时机重排：开题零出站，执行时按需扩权（设计 v1，已裁决）

> 上位约束：[规格 v1.5](../base-layer-spec-v1.md)（五条红线、八条不变量、3.1.2 Problem 契约、3.6.2 执行层、3.1.9 卡片）、[一句话开题](../kaiti/README.md)（#83，§4 授权、§4.4 信封）、[工作台宪章](../task-lifecycle/README.md)（#84，S8 人介入、04 分期）、[设置层](../task-lifecycle/03-settings.md)（#87）。
>

>
> 本稿只出设计，不含实现代码。§14 列出待裁决项，每项附推荐。

## 0. 一页结论

1. **开题默认零出站。** 一句话开题的 `scope` 恒为一条 `workspace`（r0，只读写本题工作区，不开任何出站）。原文原样登记为任务描述。抽取出来的地址只在确认卡上高亮，供人阅读，不生成规则，也不参与道别判定。
2. **执行时按需扩权。** 智能体第一次要访问一个新的外部资源时，调用申请工具，生成一条扩权申请事件 `request_scope`。批准只有两种来源，路径上都没有模型：
   - 人在扩权卡上批；
   - 练习道的确定性白名单判定自动批。条件是地址在白名单段内、风险表给出 r0、题目落在练习上限内。
   
   批准事件 `grant_scope` 把规则追加进 `Problem.scope`，画像随之重算。每次扩权都写进事件账，审计、四顾清单、时间轴都看得到。
3. **闸门仍是唯一的出站执行点。** 变的只是规则的来源，从"开题预测"换成"运行时批准"。`compile_spec` 仍只编译 `Problem.scope` 里已批的规则。批准之后，正在运行的沙箱热加一个闸门（推荐），或等下一个租约重新编译（保底）。撤销是热撤销。
4. **判据先行不动。** 练习道有答案键时，sealed 答案自动成为判据；自由任务走验收清单（`accept: human`，宪章 D3）。判据仍在开题时登记，之后不可改（I4）。扩权只动授权，不动判据。
5. **四臂对照的可比性定义在策略层。** 四臂用同一份授权策略：同一信封、同一风险表、同一批准规则，以摘要为证。各臂实际得到的授权随执行路径不同，这不算破坏对照。实际授权作为协变量记进 `meta.json`。这条写进 `eval/SPEC.md`。
6. **顺手修一个缺陷。** 今天经人批准的 `Intent.needs_scope` 从来没有编进容器：`compile_spec` 只读 `Problem.scope`，批准也不修订它（§1.3）。规格 3.6.2 写的"`approve --scope-amend` 修订全题范围"一直没有落地。本稿的 `grant_scope` 就是这一步的落地，`needs_scope` 改为它的一种入口。

## 1. 现状与问题

### 1.1 今天的授权在开题时一次定死

- 一句话开题 §4.1 从原文前置抽取 `host:port` 与 URL。模型标"入口"或"参考"，入口生成 `net` 规则，风险查风险表，未命中按 r2。
- 练习道（零确认）的条件之一是：每条规则都在信封白名单内、都是 r0（#89 已进内核）。
- 执行层 `compile_spec` 在租约起沙箱时读 `Problem.scope`，按 Intent 风险上限、r2 批准与 `touches` 过滤，编出 `ExecSpec.egress_rules`。运行时 `_start_gates` 为每台授权主机起一个闸门容器，顶着目标的主机名。白名单外的主机名在沙箱网络里根本解析不到。

### 1.2 摩擦从哪来

授权要在开题这一刻写全，但执行时要碰什么只有执行时才知道。于是：

- 原文没写端口、写的是域名而不是 `host:port`、写成"那台题目机"这类说法时，抽取器认不出入口，规则缺失。任务做不成，或者被推进确认道，让人补。
- 原文写了地址，但只是参考材料，模型却标成了入口：规则多出一条，被风险表或信封挡下，同样走确认道。
- 想把练习道判对，就得不断给抽取器补形状，比如 URL 换端口、IP 段、主机名模板。这正是 cz 说的"症状"：在错误的时刻解一个本来不必解的问题。

### 1.3 现有的扩权通道没接通

规格 3.6.2："扩大范围只能由 Reason 提出带 `needs_scope` 的 Intent，进入 `needs_human`，由人用 `approve --scope-amend` 决定。范围修订对全题生效，画像随之重算，此后编译的容器（含判官容器）都带上它。"

代码里的现状：

| 位置 | 做了什么 | 缺什么 |
| --- | --- | --- |
| `reducer/intent.py` `_v_add_intent` | 接受 `needs_scope`，风险上限把它算进去 | — |
| `refmodel.gate` | 带 `needs_scope` 的 Intent 要先有 `approve` | — |
| `reducer/intent.py` `_a_approve` | 记批准的 seq | **不修订 `Problem.scope`** |
| `adapter/session.py` `_launch_sandbox` → `compile_spec(p["scope"], …)` | 只编 `Problem.scope` | **`needs_scope` 从不进容器** |

所以今天一个经人批准的扩权申请，放行的只是 Intent 的消费门，闸门照旧不开。这是实打实的缺陷，与本稿的改向无关，但本稿的内核操作正好补上它（§4.6）。

### 1.4 运行时看不到"想访问而没被允许"

闸门只为已授权的主机存在。智能体连一个没授权的主机，在沙箱里表现为解析失败，执行层没有任何记录。规格 3.6.2 的 `scope_violation` 事件因此一直没有产生方。所以"首次访问"不能靠拦截流量来发现，必须由智能体**显式申请**（§6）。拦截探测可以作为观察面另做（§6.3），永远不触发批准。

## 2. 新流程总览

```
S2/S3 开题（零出站）                S6 执行                                    S8 人介入
────────────────────                ───────────────────────────────            ──────────────────────
原文 → 抽取（只高亮）              智能体：request_scope {rule, why}           扩权卡：差异视图
scope = [workspace r0]                       │                                   批准 / 拒绝（理由）
判据照旧（sealed / 验收清单）               ▼                                   风险只可上调
open_problem                         validate：风险查风险表（不信自报）              │
                                     判定 auto = 练习道白名单？                     │
                                       │yes                    │no                │
                                       ▼                       ▼                  ▼
                                  graph 追加 grant_scope   挂起，进待办 ─────▶  人的 grant_scope
                                  （同一事务，带信封摘要）                         （带 seen.card_hash）
                                       └───────────────┬───────────────────────────┘
                                                       ▼
                                      Problem.scope 追加规则，画像重算（写进事件体）
                                                       ▼
                                      执行层：在跑的沙箱热加闸门；此后编译的容器都带上
```

不变的部分：唯一写入者仍是图服务；`validate` 与 `apply` 仍是纯函数；闸门仍是唯一出站点；r2 凭据仍只注入获批的那一个 Intent；判官容器上限仍不超过 r1。

## 3. 开题：默认零出站

### 3.1 一句话开题

- `vet` 产出的 `scope` 恒为 `[{resource: workspace, pattern: "", actions: [read, write], risk: r0}]`，与 `vet` 今天"原文里没有入口"时给出的那一条相同（`qicao/vet.py`；`workspace` 插件见 `executor/compile.py`）。
- 抽取器照旧找出 `host:port`、URL、主机名，结果进 `Vetted.mentions[]`（新字段，纯展示）。在确认卡上，这些地址作为原文高亮出现，旁边写"执行时如需访问，会按需申请"。它们不生成规则，不进事件体，不影响道别。
- 道别里与授权有关的条件全部去掉。练习道只看三样：判据是 `exact_match` 且有 sealed 答案、预算在练习上限内、`max_attempts` 在上限内。确认道是其余有判据的任务。拒绝道是判据表达不出来的任务，照旧给三条降级路。
- 确认卡上"每条规则的风险三选一"这个控件撤掉，卡上人能改的只剩预算的金额与时限。授权的人工决定挪到 S8 的扩权卡上，一事一卡。

### 3.2 高级模式、导入与评测

人在向导（`/new/advanced`）、导入页或 `eval/problems.d/*.yaml` 里手写的 `scope` 仍然接受。人写下的就是人批过的，这与今天一样，不算"预测"。这类题在运行时同样可以再申请扩权。是否保留这条路见 §14 第 6 条，推荐保留：评测题要把授权写死在题面里，才能逐臂比较。

### 3.3 内核这一侧

`open_problem` 的校验不变。#89 的练习道信封检查仍然成立：零出站开题的 scope 只有 `workspace r0`，自然落在信封的资源与风险之内。信封的 `allow.net_patterns` 不再用于开题，改为运行时自动批准的白名单（§4.4）。它是同一份数据，同一个摘要，只是使用的时刻后移了。

## 4. 内核扩权操作

三个新操作，全部走提议通道，全部进事件账。它们不进等级函数，不进消费门的等级部分。

### 4.1 `request_scope`：申请

| 项 | 内容 |
| --- | --- |
| 提交者 | 任务令牌的会话（bootstrap、reason、explore；判官与 idler 不行），或人 |
| 事件体 | `{rules: [{resource, pattern, actions}], why: string, intent?: IntentId, risk: [r…], auto: bool, policy?: {version, digest}, settings: {version, digest}}` |
| 提议方填的 | `rules` 的 resource、pattern、actions，`why`，可选 `intent` |
| 图服务填的 | `risk`：逐条查风险表，未命中取 r2，提议方自报的风险一律不接受；`auto`：§4.4 的判定结果；`policy` 与 `settings`：当时信封与设置的摘要 |
| 校验 | 题目未关；资源种类已登记；`net` 的 pattern 是 `host:port`（与 `split_address` 同一条规则）；actions 只取 `[connect]`（`CONNECT_ACTIONS`）；规则不与现有 scope 或待决申请重复；同一题里被人拒过的同一规则直接 `forbidden_op`；会话配额（`cfg.scope_request_quota`，缺省 4）；`intent` 若给出须是本题的 Intent |
| 状态 | `state.scope_requests[r_<seq>] = {id, problem_id, rules, why, risk, auto, session, intent?, status: pending}` |

`why` 是模型写的文字，在卡上按"模型"语域标出（四语域表），不作证据。

### 4.2 `grant_scope`：批或拒

| 项 | 内容 |
| --- | --- |
| 提交者 | 人（必须带 `seen {seq, card_hash}`，绑定扩权卡，HMI H2）；或图服务自己（actor `graph`，只在 `auto = true` 时由 followup 追加） |
| 事件体 | `{request, decision: approve \| deny, risk?: [r…], reason?, seen?, policy?, profile}` |
| 校验 | 申请存在、属于本题、仍是 pending；人拒绝须写理由；人只可上调风险，不可下调到风险表给出的值以下（推荐，§14 第 5 条）；`actor = graph` 时，`validate` 当场重算 §4.4 的白名单判定，必须成立，否则 `forbidden_op`。图服务的身份不是信任来源，判定才是 |
| 应用 | approve：把规则追加到 `Problem.scope`，每条带 `granted: {seq, by, request}`，`profile` 取事件体里重算好的值（与 `open_problem` 同法，重放不读注册表）。deny：申请标 denied，记下理由。两者都把申请转为终态 |

`Problem.scope` 只追加，不删，不改下标。原因是 `touches` 与 `work.holds` 按下标引用规则。

### 4.3 `revoke_scope`：撤销

| 项 | 内容 |
| --- | --- |
| 提交者 | 只有人 |
| 事件体 | `{rule: int, reason, seen}` |
| 应用 | 规则带上 `revoked: seq`。`compile_spec` 跳过已撤销的规则（执行层一行改动）。`touches` 指向它的 Intent 照旧存在，只是那条能力不再编入 |

开题时写下的规则也可以撤销。撤销进四顾清单（规格 §673 本来就列"范围修订及是否仍生效"）。

### 4.4 练习道白名单：确定性自动批准

`request_scope` 的 `validate` 计算 `auto`，以下条件全部成立才为 true：

1. 题目开在练习道：`origin.draft.lane = practice`，且带 `policy` 戳。
2. 当前加载的信封摘要等于题目开题时戳下的摘要。信封改过版本的题，扩权一律交给人。题目只按它开题时签过的那一份策略自动批准。
3. 每条规则的资源在 `allow.resources` 内，`net` 的 pattern 匹配 `allow.net_patterns` 之一（与 #89 的 `violations` 同一套 fnmatch）。
4. 风险表给出的风险 ≤ `allow.max_risk`（r0）。
5. 题目的预算仍在练习上限内（开题后若追加过预算并越过上限，不再自动批）。

`auto = true` 时，图服务在同一事务里由 `work.followups` 追加 `grant_scope`（actor `graph`，带 `policy` 戳）。这与今天自动追加 `budget_mark`、自动 `close_problem` 是同一种机制。判定是纯函数，输入只有事件体、状态与已登记的策略。模型不在路径上。

确认道的题不自动批准，一事一卡（§14 第 4 条讨论要不要在设置层开一个通用白名单，推荐 v1 不开）。

### 4.5 风险从哪来

风险只来自两个地方：设置层的风险表（#87 已有 `settings.risk`，有序规则表，未命中取 r2），或人在卡上的上调。智能体在申请里写的风险不进事件体。这与 I5（能力 ≤ Intent 风险 ≤ 授权）的方向一致：授权的风险是人定的数据，不是模型说的话。

### 4.6 与 `needs_scope` 的关系

- `add_intent` 带 `needs_scope` 时，图服务在同一事务里追加一条 `request_scope`（`intent` 指向它）。今天的语义保留：这个 Intent 进 `needs_human`，直到申请有了结果。
- 人在审批卡上批准这个 Intent 时，卡上同时列出它的扩权申请。批准一并提交对应的 `grant_scope`，这就是规格写的 `approve --scope-amend`。§1.3 的缺陷由此修好：批了就真的编进容器。
- `refmodel.py` 是参考模型的逐字节副本，不改。`gate` 读的"已有批准"仍是 `approve`。扩权申请是否获批，由执行层编译时读 `Problem.scope` 体现，不进消费门。

### 4.7 宪法逐条核对

| 条目 | 是否成立 | 依据 |
| --- | --- | --- |
| 红线 1、I1 写入路径无模型 | 成立 | 模型只提交申请，申请不是授权；批准来自人的令牌或纯函数判定；`validate`、`apply` 仍是纯函数 |
| 红线 2 反幻觉 | 成立 | `why` 标模型语域，不作证据；扩权不产生任何支持记录 |
| 红线 3 领域知识不进内核 | 成立 | 地址形状、风险表、白名单是数据；内核只认结构化字段与资源种类登记表 |
| 红线 4 删简律 | 成立 | 开关 `grants.runtime = off` 即回到开题预测（§12.2） |
| 红线 5 诚实对照 | 成立 | §9 |
| I4 判据先行 | 成立 | 扩权不碰 `goal.check` 与验收清单 |
| I5 能力 ≤ 风险 ≤ 授权 | 成立 | 编译仍只取已批规则；风险来自表或人；自动批准限 r0 |
| I6 硬顶在容器外 | 成立 | 不涉及预算轨 |
| I7 等级不出题 | 成立 | 扩权只作用于本题；跨题引用照旧 `scope_mismatch` |
| I8 估值不进等级 | 成立 | 不涉及 |
| 判官独立 | 成立 | 判官容器仍取修订后的范围、上限 r1；判官不能申请扩权 |
| 闸门唯一出站点 | 成立 | 热加的是闸门容器本身，不在沙箱里开任何别的路径 |

## 5. 闸门重编译时机

执行层的事实（`executor/runtime.py`）：每个沙箱一张 `--internal` 网络；每台授权主机一个闸门容器，顶着目标主机名，只为规则写明的端口开转发；闸门只认执行容器的源地址。

### 5.1 两种时机

| | A. 租约边界（保底） | B. 热加闸门（推荐） |
| --- | --- | --- |
| 做法 | 批准后什么都不做；下一个租约起沙箱时 `compile_spec` 读到新规则 | Adapter 看到本题的 `grant_scope` 后，对本题每个在跑的沙箱重算 `compile_spec`，与旧 spec 求差，只对新增主机调 `executor.extend(sid, rules)`，后者复用 `_start_gates` 为它起闸门，等 `ready` 再回告 |
| 智能体的体验 | 申请后本轮会话只能做别的事或结束；练习道的自动批准也要重开一个会话 | 自动批准在一次工具调用内可用（申请、批准、闸门就绪，秒级）；人批的等人回来后同一会话接着用 |
| 改动面 | 无 | 执行层加 `extend`、`shrink` 两个方法；Adapter 订阅事件流 |
| 风险 | 无新增 | 闸门在沙箱活着时加入网络。须补 3.6.4 的隔离测试：新闸门只认执行容器源地址、只开写明的端口、其他主机仍不通 |

推荐 B，把 A 作为执行器不支持 `extend` 时（例如未来的虚拟机隔离）的退路。两者的语义相同：都只编 `Problem.scope` 里已批未撤的规则。区别只在生效的早晚。

### 5.2 只增不减与撤销

- 一个沙箱活着时，规则只按批准增加，不会因为别的原因变少。
- `revoke_scope` 例外，而且要立即生效：Adapter 调 `executor.shrink(sid, rules)`，停掉对应闸门容器（主机名随之解析不到），进行中的连接断开。撤销比批准更急，所以撤销一律热执行。
- 风险上限与 r2 批准的过滤照旧在 `compile_spec` 里做。热加时用的是同一个函数，不另写一套判断。

### 5.3 判官容器

判官容器在判定时起，读的是那一刻的 `Problem.scope`，上限 r1（规格 3.6.2）。判定进行中不热加：判官的运行应当只看它被请求那一刻的授权，便于复现。

## 6. 智能体侧：申请工具

### 6.1 工具

Adapter 加一个工具 `request_access {target: "host:port", why}`（MCP 工具名与已有工具同一命名风格）。返回三种结果之一：

- `granted`：已批（自动批准或人已批过同一规则），闸门已就绪，可以直接连。
- `pending`：已进待办，等人。工具不阻塞，智能体可以先做别的；批下来后，下一次 `exec` 之前 Adapter 把新状态写进回显。
- `denied {reason}`：人拒绝了，附理由。同一规则在本题不能再申请。

工具说明里写清楚：连不上一个地址时，先用它申请，不要猜别的地址或换端口重试。

### 6.2 提示词与读数

Adapter 的系统提示加一段："本任务开始时没有任何出站权限。需要访问外部地址时，调用 `request_access`，写明为什么需要。"每次申请的结果进会话记录，供读数页统计：申请数、自动批准率、人批的等待时间、拒绝率。

### 6.3 越界探测（可选，观察面）

在沙箱网络里加一个兜底解析：所有未授权主机名解析到一个 sink 容器，它只记录并拒绝连接，生成规格 3.6.2 的 `scope_violation {task, resource, target}` 事件，并在 `exec` 回显里提示"这个地址没有授权，可用 `request_access` 申请"。sink 永远不触发批准。它只让"想访问但没申请"变得可见，并接上哮天犬"同一任务 3 次越界即终止"这条规格。推荐放在第二步做（§12），不挡第一步。

申请挂起不暂停任务。会话继续做不需要这个地址的事；没别的可做就正常结束租约。司南的 `/work` 把"等扩权"当成一种阻塞原因显示，与"等审批"同类。人长时间不批时，任务照常走预算与停滞的已有规则，不另设超时。

## 8. 判据先行不动

- 练习道：答案键在开题时进保密库，判据 `exact_match` 带 `sealed`，与今天完全一样。
- 自由任务：判据走验收清单（`goal.accept = human`，`goal.acceptance[]`，宪章 D3、kaiti 增量 16），清单随开题登记，之后不可改。
- 扩权不改 `goal`，也不改判官快照。任何一条扩权都不能让判据变宽。

## 9. 四臂对照的可比性

建议写进 `eval/SPEC.md` 的一段（"对照臂"一节之后）：

> **授权策略相同，实际授权可不同。** 四臂必须在同一份授权策略下运行：同一信封（摘要相同）、同一风险表与设置（设置摘要相同）、同一批准规则（运行时扩权开或关，自动批准的白名单相同）。评测运行器在开跑前比对四臂的这三个摘要，不一致即拒跑。各臂实际得到的授权（扩权申请与批准的序列）随执行路径不同而不同，这是被比较的行为的一部分，不算破坏对照。`meta.json` 记录 `grants: {requested, auto, human, denied}` 与授权集合的摘要，作为协变量进归因表。评测题若在 `problems.d/*.yaml` 里写死了 `scope`，四臂从同一份开题授权出发；评测运行时人不在场，确认道的扩权申请一律按拒绝处理并计数（`grants.denied_unattended`）。

理由：对照比的是编队与机制，不是授权。要求四臂的实际授权逐条相同，等于要求它们走同一条执行路径，那就没有对照可言。真正要固定的是"什么会被批准"这条规则。

## 11. 金丝雀与安全测试（怎么证明它可用）

1. **变异测试（接 #89 的写法）**：对一条合法的自动批准申请逐字段变异，每种都必须落到人：白名单外地址、风险表给 r1、题目不是练习道、信封摘要变了、预算追加越过练习上限、资源种类不在信封里。
2. **图服务身份不是信任来源**：伪造一条 `actor = graph` 的 `grant_scope`，判定不成立时必须 `forbidden_op`。
3. **风险不信自报**：申请里带 `risk: r0` 的字段，结果必须是 `schema_error`。风险表未命中时，事件体里是 r2。
4. **热加隔离**：热加闸门后，新主机的写明端口通，同主机的其他端口不通，其他主机不通，别的容器接进网络也过不了闸门（3.6.4 的 1、4 在热加后重跑一遍）。
5. **热撤销**：撤销后下一次连接失败，进行中的连接断开。
6. **needs_scope 缺陷的回归测试**：人批准一个带 `needs_scope` 的 Intent，之后编出的 `ExecSpec.egress_rules` 必须含那条规则。今天这条测试会失败。
7. **重放**：所有扩权事件重放得到同一状态，换掉或卸掉信封与设置不影响。

## 12. 迁移与回滚

### 12.1 分步

| 步 | 内容 | 前提 |
| --- | --- | --- |
| 一 | 内核三操作与 `state.scope_requests`；`compile_spec` 跳过已撤销规则；`needs_scope` 接上扩权（修 §1.3 缺陷）；`pd scope`；设置 `grants` 一节，缺省 `runtime = off`。验收门：§11 第 6 条在修复前失败、修复后通过 | 本稿裁决 |
| 二 | Adapter 的 `request_access` 工具与提示；执行层 `extend`、`shrink` 与隔离测试；越界 sink（可选） | 一 |
| 三 | 网页扩权卡、待办与工作区横幅、时间轴节点 | 一；与地图线程的 L1 修订同步 |
| 四 | 一句话开题切到零出站：`vet` 不再生成 net 规则，确认卡撤掉风险控件，道别去掉授权条件；设置 `grants.runtime = on` | 二、三；测试方确认读数口径（§10.1 最后一行） |
| 五 | `eval/SPEC.md` 写入 §9；评测运行器比对三份摘要 | 一 |

第一步本身就修了一个缺陷，即使后面几步搁置也值得先做。第四步是唯一改变人的体验的一步，放在最后。

### 12.2 回滚

- **开关**：设置 `grants.runtime = off` 时，`request_scope` 返回 `not_enabled`，一句话开题退回开题时预测授权的旧逻辑（`vet` 的旧分支保留一个版本周期）。这就是红线 4 的对照臂：`grants=off`。
- **事件不能回滚**：日志只追加，已写下的 `request_scope`、`grant_scope` 必须永远能重放。所以三个操作的 `apply` 永不删除。关掉开关只拒绝新申请，不影响旧事件。
- **已批的规则**：关掉开关时，已经追加进 `Problem.scope` 的规则照旧生效（它们是人或策略批过的）。要收回，用 `revoke_scope`。
- **热加闸门出问题**：Adapter 的配置项 `grants.hot = off` 退回到租约边界（§5.1 的 A），内核与界面都不受影响。

## 13. 不做的事

- 不让模型判断一条申请"看起来安全"，不做语义相似度批准。批准只有人和白名单两种。
- 不做"本任务内同一主机的所有端口一律批准"。端口照旧写明（异议 006 第 1 项）。
- 不做跨题的批准记忆，比如"上次批过 q7.lab，这次自动批"。它会让授权出题（I7 的精神）。如果将来要做，走设置层的白名单，由人显式加进去。
- 不改 `refmodel.py`。
