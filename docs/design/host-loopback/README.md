# 沙箱访问宿主机回环服务（设计 v1，待裁决）

> 上位约束：[规格 v1.5](../base-layer-spec-v1.md)（3.6.2 执行层、I5 能力 ≤ 风险 ≤ 授权）、[运行时扩权](../runtime-grants/README.md)（#91，已裁决）、[执行层规格](../../../executor/SPEC.md)（出站闸门、热加与热撤销）、[开放道](../open-lane/README.md)（求解会话的风险上限 r1）。
>
> 来源：cz 2026-11-21 实测。把写着 `127.0.0.1:8810` 的任务贴进一句话开题，智能体交付“受阻（连接被拒）”。cz 要的结果：扩权批准后，沙箱能访问宿主机回环上已批准的服务；沙箱仍然只经闸门出站，不放开整个网络。
>
> 本稿只出设计，不含实现代码。§12 列出待裁决项，每项附推荐。文中“宿主”指跑焚决全栈（`scripts/run.py`）的那台电脑。

## 0. 一页结论

1. **今天连不上有三层原因，三层都要补，只补一层没有用。** 沙箱里的 `127.0.0.1` 是沙箱自己；执行层只认本机题目容器作出站目标；风险表没登记的地址按 r2，而开放道求解会话的上限是 r1，批了也不开（§1）。
2. **批准之后，任务里写的原地址原样可用。** 在沙箱的网络命名空间里放一个“回环垫片”，它监听沙箱里的 `127.0.0.1:8810`，把连接交给闸门。智能体不用改写地址，HTTP 的 `Host` 头、证书、跳转都和在宿主上直接访问一样。同时闸门顶着 `host.docker.internal` 这个名字，写这个名字也通（§3）。
3. **闸门仍是唯一出口，按端口放行。** 闸门只为批准的端口开转发，上游固定为宿主回环的同一端口。闸门怎么够到宿主按平台分两条通路：Linux 上由执行层进程在一张专用内部网络的网关地址上开转发口，闸门自己仍然没有任何外网路由；macOS（Docker Desktop）上闸门另接默认网桥、经 `host.docker.internal` 到宿主，与 #141 的端点中继同法（§4）。
4. **登记为一种新的资源种类 `host`，不混进 `net`。** 这样 `net` 的通配规则、练习道白名单、只读白名单都碰不到宿主回环；扩权卡上能明确写“你这台电脑上的本地服务”。`host` 一律人批，不自动批准（§2、§5）。
5. **焚决自己的端口永远不开。** 图服务、端点代理、工具端点都监听宿主回环，沙箱够到它们就绕过了信任根。执行层硬拒，申请工具提前告知（§6.1）。
6. **顺带发现一个现有缺口。** 执行层给沙箱建的内部网络没有隔离网关。Linux 上，沙箱今天不经任何授权就能连到宿主上监听全部接口（`0.0.0.0`）的服务。已实测确认。模型容器的网络（`adapter/container.py`）早就用了隔离网关，执行层漏了。建议作为第零步先修（§7）。

## 1. 现状：三层原因

| 层 | 现状 | 依据 |
| --- | --- | --- |
| 沙箱内 | `127.0.0.1` 与 `localhost` 是沙箱自己的回环，连接在沙箱内就被拒，到不了任何闸门。闸门靠“在沙箱网络上顶替主机名”工作，IP 字面量不经名字解析，顶替不了 | `executor/SPEC.md` 出站闸门：名字解析 |
| 执行层 | 出站目标必须是本机的容器，否则 `ScopeError`（“M0 只支持本机题目容器作为出站目标”）。#142 之后这种情况会照实告诉模型“已批准，但执行层开不了这个出站目标” | `runtime.py` 的 `launch` 与 `_reconcile`；已知缺口 2 |
| 风险 | 风险表缺省是空的，未命中的规则按 r2。开放道求解会话的上限是 r1（`solve_ceiling`），r2 规则不编入。人在扩权卡上只能上调风险，所以一个没事先登记的地址，批了也不开，工具返回“风险高于本任务的风险上限” | `settings_hub.defaults`、`grants.py` 的 `risk_of` 与人批路径、`tools.py` 的 `_compiled`；试算脚本 `scripts/trial/trial.py` 为此要先往风险表里写一行 |

内核这一侧没有阻碍：`net` 的 pattern 形状今天就接受 `127.0.0.1:8810`，申请能提、能批，只是批下来的规则没有执行手段。

## 2. 规则怎么登记：新资源种类 `host`

### 2.1 形状

```
{resource: "host", pattern: "127.0.0.1:8810", actions: ["connect"], risk: …}
```

- 含义：宿主回环上的 TCP 端口 8810。pattern 只有一种规范写法 `127.0.0.1:<端口>`。
- 申请工具把这些写法都归一成它：`localhost:P`、`127.x.x.x:P`、`host.docker.internal:P`、`[::1]:P`。归一是纯字面规则，写在 Adapter 的申请工具里，模型不参与判断。
- 登记表三处各加一行（都是数据，不是内核逻辑）：
  - `RESOURCE_EXTERNAL["host"] = True`。宿主上的服务在题目之外、可能变化，画像的信息轴随之为 partial，与 `net` 相同。
  - `RESOURCE_REQUESTABLE["host"]`：pattern 须是 `127.0.0.1:<1–65535>`，动作只有 `connect`。
  - `READONLY_ACTIONS` **不加** `host`。只读白名单因此永远批不了它（§5）。
- `net` 的申请形状同时收紧：主机部分是回环字面量（上面那几种写法）时拒绝，提示改用 `host`。否则同一个服务会有两种登记法，其中一种没有执行手段。
- 执行层加资源种类插件 `HostLoopback`，编出 `ExecSpec.host_rules`（`((端口, 动作…), …)`），与 `egress_rules` 分开。闸门的对齐（`reconcile`）按同样的求差办法处理它。

### 2.2 为什么不用 `net` 加回环字面量

| | `host` 新种类（推荐） | `net` + `127.0.0.1:P` |
| --- | --- | --- |
| 风险表 | 行按资源种类匹配，`net` 的通配行（例如 `*:443`）不会带上宿主回环 | 一条写得宽的 `net` 行就把宿主端口定成低风险 |
| 自动批准 | 练习道信封的 `allow.resources` 里没有 `host`，只读白名单也没有，天然不自动批 | 要在两处判定里各加一条特例 |
| 扩权卡 | 能按种类写清楚“你这台电脑上的本地服务” | 人看到的是一条普通的网络地址 |
| 含义 | 明确：跑全栈的那台电脑的回环 | `net 127.0.0.1` 在题面里指谁有歧义 |
| 改动 | 登记表三行、执行层一个插件、设置校验与卡片文案认一个新种类 | 改动少一点，但特例散在几处 |

内核不理解 resource（红线 3），所以新增种类不动 `validate` 与 `apply` 的逻辑，也不动 `refmodel.py`。

### 2.3 这条规则管到哪

- 只管宿主回环、同一端口。沙箱里的 `127.0.0.1:P` 对应宿主的 `127.0.0.1:P`，不做端口改写。
- 不含宿主的局域网地址、别的机器、互联网主机。互联网主机是执行层已知缺口 2，另案裁决（§10）。
- 只有 TCP。
- 规则的含义是“执行时跑全栈的那台电脑”。换一台电脑重放事件，状态相同；真去重跑，连到的是那台电脑上的同一端口。评测题因此不许写 `host` 规则（§12 第 11 条）。

## 3. 沙箱一侧：原地址原样可用

### 3.1 回环垫片

批准并编入之后，执行层为这个沙箱起一个垫片容器：

- 用 `--network container:<sid>` 加入沙箱的网络命名空间。它不是一张新网络，也不带来任何新路由：垫片看到的网络就是沙箱那张内部网络。
- 在这个命名空间的 `127.0.0.1:<端口>`（有 IPv6 回环时也在 `::1`）上监听，每条连接原样转给闸门（`host.docker.internal:<端口>`）。
- 与闸门同一套加固：`--cap-drop ALL`、`no-new-privileges`、只读根、非 root、不挂卷、不带环境变量，带 `paoding.role=shim` 标签，随沙箱销毁，孤儿清扫同样覆盖。源码经 `python -c` 传入，用闸门的同一个镜像。
- 它与执行容器不共享进程命名空间与文件系统。沙箱里的进程看不见它、杀不掉它，也改不了它的转发目标。
- 垫片发出的连接，源地址就是执行容器的地址（同一个命名空间），所以闸门“只认执行容器源地址”这条不用改。

实测（Linux，Docker 29.10，与执行层相同的建网与加固参数）：沙箱里 `127.0.0.1:<端口>` 与 `localhost:<端口>` 都通到宿主服务；未批准的端口照旧被拒；外网照旧不通；沙箱里再去占同一端口得到“地址已被占用”；闸门看到的来源是执行容器的地址。

### 3.2 为什么不只给一个别名让智能体改写

只给别名（`host.docker.internal:8810`）更省事，但有三个实际问题：

- 很多本地服务检查 `Host` 头。Vite、Django、带防 DNS 重绑定保护的开发服务器会拒绝 `Host: host.docker.internal:8810`。垫片方案里请求是对着 `127.0.0.1:8810` 发的，`Host` 头不变。
- 证书、OAuth 回调、服务自己返回的跳转与绝对链接都写着 `localhost` 或 `127.0.0.1`，改写之后一跳就又回到连不上的地址。
- 依赖模型每次都记得改写。任务原话、仓库里的配置文件、脚本里写死的地址都要改，漏一处就失败。

所以推荐两样都给：原地址经垫片可用，别名也可用。别名不靠垫片，垫片起不来时（见下）仍是退路。

### 3.3 边界情况

| 情况 | 行为 |
| --- | --- |
| 沙箱里已有进程占着同一端口（热加时） | 垫片绑不上。工具返回“已批准；沙箱里的 127.0.0.1:8810 被你自己的进程占着，停掉它，或改用 host.docker.internal:8810” |
| 批准之后智能体想在沙箱里自己起一个 8810 的服务 | 绑定失败（地址已被占用）。工具返回与系统提示里都写明：批准期间这个端口在沙箱里指向用户的电脑 |
| `localhost` 解析到 `::1` | 垫片同时监听 `::1`。沙箱没有 IPv6 回环时，客户端回落到 IPv4，实测可用 |
| `reset(sid)` 重建沙箱 | 网络命名空间换了，垫片与闸门一起重建 |
| 撤销 | 垫片、闸门、宿主通路一起停，进行中的连接断开；沙箱里的 `127.0.0.1:8810` 回到“连接被拒” |
| 宿主上那个端口没有服务在监听 | 与已知缺口 3 相同：`connect()` 成功后立即被重置。通路就绪时执行层从闸门一侧探一次，工具返回里写明“已开通，但用户电脑上这个端口现在没有服务在监听” |

## 4. 闸门一侧：怎么够到宿主

闸门的职责不变：只为批准的端口监听，只认执行容器的源地址，逐连接记录。新增的只是上游从“上游网络上的题目容器”换成“宿主回环的同一端口”。宿主回环从容器里没有统一的到达办法，按平台分两条通路。配置项 `executor.host_route`（`forwarder | desktop`，缺省按平台），与 #141 的 `backend.transport` 同一种做法。

### 4.1 Linux：执行层进程开转发口（`forwarder`）

```
执行容器 ─ 垫片 ─<sid>-net─ 闸门 ─<sid>-host-net─ 网关地址:临时端口 ─ 执行层进程 ─ 宿主 127.0.0.1:8810
           （内部、隔离网关）      （内部，只有闸门）    （转发口，只认闸门地址）
```

- 每个沙箱另建一张内部网络 `<sid>-host-net`，上面只有这一个闸门。这张网不隔离网关，所以闸门到得了它的网关地址（这个地址在宿主上）。
- 执行层进程在这个网关地址上为每个批准的端口开一个转发口（临时端口），只接受源地址是闸门的连接，转给宿主的 `127.0.0.1:<端口>`。转发口随沙箱销毁；执行层进程退出时它们一起消失，通路失败即关闭。
- 闸门的两只脚（现在是三只）都在内部网络上，自己仍然没有任何外网路由。“闸门自身出不了外网”这条保证原样成立。
- 宿主上的服务看到的来源是 `127.0.0.1`（执行层进程连它），与本机程序访问它没有区别。扩权卡上要把这一点写明（§5.2）。
- 实测依据：内部网络（不隔离网关）上的容器连得到网关地址上的宿主服务，连不到外网，也连不到只监听宿主回环的服务。后一条正是需要转发口的原因。
- 已知依赖：宿主的防火墙若拦了容器到网关地址的入站，通路不通。就绪自检（§4.3）会在告诉模型“已开通”之前报出来。

### 4.2 macOS（Docker Desktop）：闸门加一只默认网桥的脚（`desktop`）

```
执行容器 ─ 垫片 ─<sid>-net─ 闸门 ─默认网桥─ host.docker.internal:8810 ─（Docker Desktop）─ 宿主 127.0.0.1:8810
```

- Docker Desktop 的容器跑在虚拟机里，执行层进程在 macOS 上，没法在虚拟机的网桥上开转发口。能到宿主回环的只有 Docker Desktop 提供的 `host.docker.internal`，它要求容器有一条非内部网络的路由。
- 做法与 #141 的端点中继相同：闸门另接默认网桥，带 `--add-host host.docker.internal:host-gateway`，上游写这个名字。执行容器仍只在内部网络上。
- **如实说明代价：** 这条通路上，闸门容器在网络层有了外网路由。它出不去靠的是闸门程序本身：上游地址与端口在启动参数里写死，程序只做字节转发，不解析内容，沙箱没有任何办法改它的配置。实测确认带网桥脚的闸门容器在网络层连得到外网。这与 #141 的中继是同一个信任假设，但执行层规格里“闸门自己也出不了外网”那一句，在这条通路上要改成“闸门只向写死的上游转发”。
- 这条通路在云端的 Linux 环境里验证不了。Docker Desktop 上“内部网络到不了 `host.docker.internal`、接了默认网桥就到得了宿主回环”这两点，依据是 #141 实战中中继的表现，实现第一步要在 cz 的电脑上先验（§11 第 0 项）。

### 4.3 就绪自检

通路起来之后、告诉模型“已批准”之前，执行层从闸门里对每个端口走一次连接：

- 通路本身不通（防火墙、Docker Desktop 的名字没解析到）：报 `unsupported`，写明原因与换通路的办法，照 #142 的路径照实告诉模型。
- 通路通、但宿主端口没有服务：照常开通，工具返回里写明（§3.3 最后一行）。

### 4.4 另外两种做法与取舍

| 做法 | 好处 | 代价 |
| --- | --- | --- |
| 全平台都给闸门加网桥脚 | 一套代码 | Linux 上白白放弃“闸门没有外网路由”；Linux 的 `host-gateway` 到不了只监听回环的服务，照样要转发口 |
| 全平台走 `docker exec` 标准流隧道：监听程序跑在闸门里，连接的字节经 `docker exec -i` 的标准输入输出复用到执行层进程，再由它连宿主回环 | 闸门在任何平台都没有外网路由，一套机制，不依赖宿主防火墙与 Docker Desktop 的名字 | 要在信任根里写一个连接复用协议；吞吐与延迟更差，一条慢连接可能拖住别的；`docker exec` 流中断时的恢复要另做 |

推荐按平台分两条通路。标准流隧道列为备选：如果 cz 认为 macOS 上“闸门有外网路由”不可接受，就改用它，代价是实现与测试量明显更大。

### 4.5 访问摘要

闸门照旧逐连接记录。`touched` 里这类连接写成 `host:127.0.0.1:8810`，与 `net:` 前缀并列，来源仍只有闸门的记录。Linux 通路上转发口另记一行（宿主端是否接通），只用于排错，不进出处字段。

## 5. 批准

### 5.1 一律人批

- 练习道信封的 `allow.resources` 不含 `host`，`rule_violations` 自然挡下，不自动批准。
- 只读白名单（地图 Q36）不认 `host`：TCP 层没有“只读”，连上本地服务就能调它的全部接口，包括会写的。
- v1 不提供任何让 `host` 自动批准的设置项。

### 5.2 扩权卡

沿用现有扩权卡（#99），按资源种类换文案：

```
┌ 申请访问你这台电脑上的本地服务 ──────────────────────────────┐
│ 新增   本机服务  127.0.0.1:8810  connect   风险 …（见 §5.3）   │
│ 理由〔模型〕 任务第 1 段给的接口在这个地址上                    │
│ 原文提到〔人〕 ① “服务在 127.0.0.1:8810”                       │
│                                                              │
│ 批准后：任务里的智能体可以像你电脑上的程序一样访问这个端口上    │
│ 的全部接口，包括会修改数据的接口。只开这一个端口。              │
│ 随时可撤销，撤销后进行中的连接立即断开。                        │
│                    [ 批准 ]   [ 拒绝… ]                        │
└──────────────────────────────────────────────────────────────┘
```

卡片哈希、`stale_view`、待办入口、时间轴节点都不变。时间轴与四顾清单里这类规则标“本机服务”。

### 5.3 风险（连带 `net`，需要裁决）

§1 第三层的问题不限于宿主回环：任何没事先写进风险表的地址，人在卡上批了，开放道的沙箱里也不开。#91 §14 第 5 条裁的是“人只可上调，下调等于改风险表”。这条的前提是风险表给了值；表里没有这一行时，规格 3.1.2 的原话是“风险由授权的人逐条标注，缺省 r2”，此时人在卡上标注并不是在改表。

三种办法：

| | 做法 | 影响 |
| --- | --- | --- |
| a（推荐） | 风险表未命中时，卡上让人标注 r1 或 r2，缺省选中 r2，并写明“标 r2 的话本任务的沙箱里不会开”。表命中时照旧只可上调 | 是对 #91 §14 第 5 条在“表未命中”这一种情况下的修订，`net` 同样适用。内核改动只在 `grant_scope` 的校验里 |
| b | 不改规则。卡上写明“风险表里没有这一行，按 r2，本任务不会开”，给一个到设置页风险表的直达链接；批准时按当时的风险表重查一次 | 人要先去设置页加一行再回来批，两步，但完全守住原裁决 |
| c | 不动 | cz 这次的任务，批了也仍然不开，除非事先登记 |

`host` 规则不设种类级的缺省风险，跟这里的裁决走。

## 6. 安全边界

### 6.1 焚决自己的端口永远不开

图服务与网页（缺省 8100）、端点代理、工具端点都只监听宿主回环；开发时还有 vite（5173）。沙箱够到端点代理就可能绕过预算轨去调模型，够到图服务与工具端点就是直接面对信任根。

- 全栈组装时把自己在听的端口交给执行层（`reserved_ports`）。执行层编译 `host` 规则时，端口在这个集合里就拒（`ScopeError`），不看规则是谁批的。
- 申请工具先查同一个集合，命中就直接告诉模型“这是焚决自己的端口，不能申请”，不提交申请，不打扰人。
- 端点代理与工具端点用的是临时端口，每次启动不同，所以这个集合是进程内的事实，不进设置，也不进事件体。

### 6.2 逐条核对

| 条目 | 是否成立 | 依据 |
| --- | --- | --- |
| 沙箱只经闸门出站 | 成立 | 垫片在沙箱的命名空间里，只能连到同一张内部网络上的闸门；执行容器不接任何新网络 |
| 端口级放行 | 成立 | 闸门只监听批准的端口；垫片只监听批准的端口；Linux 转发口每端口一个 |
| 闸门只认执行容器 | 成立 | 垫片与执行容器同一个地址；别的容器过不了闸门 |
| 闸门自身出不了外网 | Linux 成立；macOS 改为“只向写死的上游转发” | §4.1、§4.2 |
| 红线 1、I1 写入路径无模型 | 成立 | 模型只提申请；批准只有人；地址归一是字面规则 |
| 红线 3 领域知识不进内核 | 成立 | 新种类是登记表数据；内核逻辑不变 |
| 红线 4 删简律 | 成立 | 开关见 §9 |
| I5 能力 ≤ 风险 ≤ 授权 | 成立 | 仍由 `compile_spec` 按风险上限、r2 批准、撤销过滤；热对齐用同一个函数 |
| 判官独立 | 成立 | 判官容器照旧在判定时编译、上限 r1、不热加、判官不能申请 |
| 凭据 | 成立 | 不向沙箱、闸门、垫片传任何宿主凭据；宿主服务若把回环来源当作已认证，那正是这次批准的含义，卡上已写明 |

### 6.3 宿主服务一侧的保护

- 每个转发口（Linux）与每个闸门端口设并发连接上限（建议 64），防止沙箱里的程序把本地服务的连接数占满。
- 不限速、不看内容。闸门是字节转发，这条不变。

## 7. 顺带发现：沙箱网络没有隔离网关

`DockerExecutor.launch` 用 `docker network create --internal` 建 `<sid>-net` 与 `<sid>-up-net`。内部网络没有外网路由，但网桥在宿主上仍有一个网关地址，容器连得到它。

实测（Linux，Docker 29.10，同样的建网与 `--cap-drop ALL` 参数）：

| 目标 | 结果 |
| --- | --- |
| 网关地址上、宿主监听 `0.0.0.0` 的服务 | **连得上**，不需要任何授权，不经闸门 |
| 只监听宿主 `127.0.0.1` 的服务 | 被拒 |
| 外网 | 网络不可达 |
| 建网时加 `com.docker.network.bridge.gateway_mode_ipv4=isolated` 之后的网关地址 | 被拒；闸门的别名解析与转发不受影响 |

影响：在 Linux 上部署时，宿主上监听全部接口的服务（数据库、开发服务器、未加保护的管理端口）今天对沙箱是敞开的，`touched` 里也看不到。macOS 的 Docker Desktop 上网关在虚拟机里，够到的是虚拟机而不是 macOS，影响小得多。焚决自己的端点只监听回环，不在其中。

修法：两张网络都加隔离网关选项，老版本 Docker 不认时的退路与 `adapter/container.py` 的 `_internal_net` 相同。加一条回归测试：沙箱连网关地址上的宿主服务必须被拒。这一条与本稿的功能无关，建议第零步单独修。本稿 §4.1 的 `<sid>-host-net` 是唯一故意不隔离网关的网络，上面只有闸门。

## 8. 智能体一侧

- 系统提示（`request_access` 的那一段）加两句：任务里写的 `127.0.0.1`、`localhost` 指用户的电脑，不是沙箱；连不上时用 `request_access` 申请同一个地址，批下来后原地址就能用，不要换端口或猜别的地址。
- `request_access` 的 `target` 接受回环写法，归一后以 `host` 资源提交。返回值在 `granted` 时写明两种可用地址；其余状态（`pending`、`denied`、风险高于上限、执行层开不了）沿用现有文案。
- 一句话开题的原文高亮（`Vetted.mentions`）已经能认出 `host:port`，不用改。

## 9. 开关与回滚

- 设置 `grants.host`（`on | off`）。关着时，`host` 资源的申请返回 `not_enabled`，工具照今天的样子告诉模型连不了。已批的规则留在 `Problem.scope` 里，执行层在开关关着时不编入。
- 事件只追加：`host` 种类一旦登记就不能从登记表删掉，否则旧事件重放时资源种类不认。
- 通路出问题时，`executor.host_route` 可以显式指定；两条都不通时照 #142 的路径返回 `unsupported`。
- 缺省值见 §12 第 8 条。

## 10. 不做的事

- 不做互联网主机出站。那是执行层已知缺口 2，#142 已写明“单独裁决”。本稿 macOS 通路用到的“闸门带一只有路由的脚”在技术上与它相近，但本稿的闸门上游写死为宿主回环，不构成对外网出站的预先决定。
- 不做宿主局域网地址、端口改写、UDP。
- 不做“宿主全部端口”或端口段。一条规则一个端口。
- 不做任何形式的自动批准与跨题记忆。
- 不在批准之前由全栈去探测那个端口（批准前不产生任何对用户服务的连接）。
- Windows 上的 Docker Desktop 预计与 macOS 通路相同，未验证，v1 不承诺。

金丝雀（第二步，Linux 上真跑；macOS 通路在 Linux 上用“网关地址上开转发口”代替 Docker Desktop，与 #141 的测试同法）：

1. 批准端口通，原地址与别名都通；同宿主的其他端口不通；外网不通。
2. 保留端口：规则已批也编不进，申请工具不提交。
3. 别的容器接进沙箱网络，过不了闸门；接进 `<sid>-host-net` 连转发口被拒（源地址不对）。
4. 热撤销：进行中的连接断开，原地址回到被拒，垫片、闸门、转发口、专用网络都没有残留。
5. r1 的 `host` 规则热加进 r0 上限的沙箱不开。
6. 沙箱里先占住端口再批准：返回占用提示，别名可用。
7. 执行层进程被杀：转发口消失，沙箱连接失败；孤儿清扫收掉垫片、闸门与网络。
8. `touched` 只含真实发生的连接，写成 `host:127.0.0.1:P`；命令输出里伪造的不算。
9. macOS 通路的闸门：从沙箱一侧无论怎样连，都到不了写死上游之外的任何地址。
