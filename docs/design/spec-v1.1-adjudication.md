## 三、附带补充（三项新要求）

1. **判官资产的 vault 语义（必须，M0 内落地）**。判官资产分两级：
   - **结构级**：判官代码、公开配置——以 input 类 Artifact 哈希固定，可在 Worker 容器只读挂载（现行 5.2 场景 3 的表述对这一级成立）；
   - **含密级**：`exact_match` 的答案哈希、隐藏测试的期望输出等——以 `vault:` 引用登记，**仅判官容器内解引用，Worker 的两个容器均不可见**。
   现行 5.2 场景 3 写"（判官资产）在 Worker 的两个容器中只读"对含密级不成立，请改为分级表述。验收补一条：Worker 会话尝试读取含密级判官资产 → 不可见或被拒。
2. **终态三值显式化（建议，M0 报告规范）**。题目终态与 `pd status/report` 统一为 `solved`（判官确认）/ `accepted`（人验收）/ `unsolved` 三值；报告写明根结论等级上限。"已验收"在任何输出里不得呈现为"已证明"。
3. **基质接口映射附录（建议）**。A9 的事件日志+reducer 即协调基质的实现；请在规格附录给出九操作映射表（`adjudicate`=validate、`snapshot`=日志投影、`cas`=租约、`settle`=judge_verdict+close、`stable_dump`=任务包前段、`replay`=重放），注明未来更换基质（见 [coordination-substrates.md](./coordination-substrates.md)：阡陌 git / 榷场市场）时接口不动。目的：基座不被任何一次基质押注绑架。

## 四、立场撤回（裁决人自纠）

撤回 coordination-substrates.md §8 中"**M0 基质=阡陌（git）**"的建议，改为：**M0 基质=事件日志（SQLite + reducer）**。理由：① 参考模型已把 log+reducer 实现到 47 条测试可跑的程度，沉没成本真实且质量高；② 租约、幂等键、按题哈希链在服务内比 git refs 语义更干净；③ 阡陌"零基础设施、数天上线"的优势已被"百行 reducer + SQLite"基本抵消。阡陌/榷场降为**规模化备选**（文档保留），且 Bn 对照臂将实证检验"共享状态形态本身"的价值——若 Bn 与完整图无差异，基质之争自动降维。
